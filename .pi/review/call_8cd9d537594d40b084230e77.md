## 🔴 Critical

### JWT leg reads `sub` off the jose result wrapper, so every real betterbase JWT is rejected
**`concierge/src/auth.ts:53`** — found by correctness
The default `verifyJwt` returns the raw result of `jwtVerify` (line 46). In jose v6 (concierge/package.json pins "^6.0.0") `jwtVerify` resolves to a `JWTVerifyResult` object `{ payload, protectedHeader }`, NOT the decoded payload. The new code casts that object to `{ sub?: unknown }` and tests `payload.sub` (line 53/57), so for a genuinely valid JWT `sub` is always `undefined`; the branch is skipped and control falls through to `secretOk(token, sharedSecret)`, which is false for a JWT. Result: `createVerifyExternal` returns `null` for every JWT bearer. This is not confined to /boot — `requireExternal` (used by /wake, /assign, /status) previously returned `true` for any JWT that passed signature verification (old code did `await verifyJwt(token); return true;`), so the diff regresses the whole external tier: real users' tokens now get 401 instead of being accepted. The unit tests do not catch it because every test injects `verifyJwt` returning a bare `{ sub }` object, matching the new (wrong) assumption. Trigger: any live client call to the concierge with a bb session token.

**Fix**: Unwrap the result: `const { payload } = await verifyJwt(token) as { payload?: { sub?: unknown } };` (or make the default leg return `(await jwtVerify(...)).payload`) and tighten `VerifyJwt`'s return type so the wrapper shape is enforced at compile time; add a test that does not inject `verifyJwt`.

### JWT identity read from wrong object: every real betterbase JWT is rejected, breaking the auth tier
**`concierge/src/auth.ts:57`** — found by security
The default `verifyJwt` leg does `return jwtVerify(token, jwks, {...})` (line 46), and jose's `jwtVerify` resolves a `JWTVerifyResult` — `{ payload, protectedHeader }` — not the decoded claims. The new code then reads `payload.sub` (line 57) directly off that result object, where `sub` is always `undefined`; the actual claim is `payload.payload.sub`. So for any genuine production token (JWKS configured, no injected `verifyJwt` — confirmed in index.ts:70-75, no override) the `{ kind: "jwt", sub }` branch is never taken. The token is not the shared secret either, so `secretOk` fails and `verifyExternal` returns `null`. Consequences: (1) `requireJwtUser` returns 401 for every legitimate user, so the new `/boot` verb is unusable; (2) this is a regression of the pre-diff behavior (`await verifyJwt(token); return true`), so `requireExternal` now also rejects JWT bearers — `/wake`, `/assign`, `/status` all 401 for signed-in users. The tests pass only because every `verifyJwt` injection returns a bare `{ sub }` object, masking the shape mismatch.

**Fix**: Unwrap the jose result: `const { payload } = (await jwtVerify(...))` and return the payload, or read `(res as { payload?: { sub?: unknown } }).payload?.sub`. Add a test that exercises the real `jwtVerify`-shaped result (`{ payload: { sub } , protectedHeader }`) so the injected-shape assumption can't hide this again.

## 🟠 Important

### Discovery-first wakeCore re-points activeEnclave at the failing standby, defeating the standby-failure fallback and looping unboundedly
**`client/src/App.tsx:131`** — found by robustness, tests
The catch in run() (App.tsx ~line 197) is documented as the safety net for a standby that fails verification: when `activeEnclave !== ENCLAVE_URL` it re-enters wakeCore, whose comment promises 'fall back to the primary wake path (which resets activeEnclave)'. The new live branch added here runs `bootInstance(conciergeAuth)` BEFORE that reset and, on success, `activeEnclave = booted.url` (line ~133). For a user whose failing node was handed out as their own machine, /boot is idempotent: users.rebind() may miss the claimed `waddle-standby-N` name (it does not carry the `waddle-u<hash>-` prefix), but `users.bind(sub)` returns the already-claimed name from map/known when the pool is empty, and `pool.assign()` otherwise hands out a fresh standby — in both cases the returned URL is the same (or another equally-broken) standby host. verifyEnclave throws on an attestation failure (client/src/lib/attestation.ts:59,62), so run() throws again, `activeEnclave !== ENCLAVE_URL` is again true, and `autoWokeRef` is never consulted on that branch → wakeCore/ run() recurse indefinitely with only the ~2s pollUntilHealthy sleep between iterations. Result: a hot loop hammering /boot + attestation, warm standbys drained, user machines repeatedly (re)claimed/created, and the user stuck on 'verifying'/'asleep' instead of ever seeing the error screen. Previously (pre-diff) wakeCore only called wakeInstance, which set `activeEnclave = ENCLAVE_URL`, so this fallback terminated after one primary wake.

**Fix**: Make the standby-failure fallback bypass discovery: set `activeEnclave = ENCLAVE_URL` before calling wakeCore (or pass a `skipDiscovery` flag that makes wakeCore go straight to wakeInstance), so a standby that fails verification always re-targets the primary and the loop terminates. Add a guard so repeated failures surface the error screen rather than re-entering wakeCore.

### New /boot route and requireJwtUser auth tier ship with zero tests
**`concierge/src/index.ts:348`** — found by tests
The diff adds the only public path that mints/claims a machine and a brand-new auth tier: `requireJwtUser` (index.ts:253) returns the JWT `sub`, answering 403 when the bearer verified as a non-user (shared secret) and 401 when it did not — an explicitly documented contract ('the shared secret is NOT enough'). It also adds a new namespace-authorization rule in `allowedInstance` (index.ts:212: `USER_NAME_RE.test(instance) && users.known().has(instance)`). Every sibling module has a test file (auth, pool, platform, table, postbox, handoff, and the new user-machines.test.ts), but there is no concierge/src/index.test.ts, so none of the /boot branches are executed: the 403-vs-401 split, the warm-standby claim, the `createInstance` failure → 502, the `platform.ensure` failure → 502, and the status→HTTP-code mapping. The diff carefully tests the auth.ts `ExternalIdentity` value in isolation but not the consumer that turns `{kind:'secret'}` into a refusal — exactly the layer a regression would flip silently and grant machine access or deny every user.

**Fix**: Add an index-level test (extract the /boot handler or inject a fake verifyExternal/platform/pool) asserting: shared-secret bearer → 403, no/invalid bearer → 401, a JWT `sub` → 200/202 with the in-zone URL, create or ensure throwing → 502, and that allowedInstance rejects user names not in the registry's known-set.

### /boot re-claims a fresh warm standby on every call for users bound to a claimed standby
**`concierge/src/index.ts:354`** — found by correctness
`/boot` resolves the user's machine with `users.rebind(sub)` before falling through to `users.bind(sub)`. `rebind` (user-machines.ts:65-68) scans the known-set for the cattle prefix `waddle-u<hash6>-` only — it never consults the in-memory `map`. A user whose machine is a claimed warm standby holds a name like `waddle-standby-3`, which has no such prefix, so `rebind` returns null even though `map` still maps them to it. Execution then enters the warm-claim block (line 356): `pool.assign()` — and whenever the pool has a spare, the user is `claim`ed onto a brand-new standby, overwriting their mapping, while the previously claimed machine is abandoned. Each later `/boot` repeats this, so 'Later boots return the existing machine' (the route docstring) does not hold for standby-bound users, and every call strands a running machine. It is stranded long: the claim's `table.setStop(got.name, CLAIM_GRACE_MS)` (line ~360) is immediately nullified by the unconditional `table.userWake(name)` (line 381; table.ts `userWake` clears `stopRow`), so the only remaining bound on the abandoned machine is the backstop sweep's `HARD_STOP_MS` (index.ts:58, default 24h). Same blind spot applies right after a concierge restart, before the platform scan refills `known`.

**Fix**: Make the lookup map-first: in `rebind` (or in /boot) return `map.get(sub)` when it is still in `known`, and only then scan `known` by prefix; or call `users.bind(sub)` before attempting `pool.assign()` so an existing mapping is never overwritten.

### bootInstance zone check lacks a label boundary, unlike assignStandby
**`client/src/lib/concierge.ts:125`** — found by correctness, robustness
config.ts exports ZONE without a leading dot (e.g. `ddg-waddle.containers.tinfoil.dev`), and bootInstance defaults `zone = ZONE` (line 101) so App's `bootInstance(conciergeAuth)` call checks `host.endsWith(zone)` here. assignStandby, by contrast, is called with `standbyZone()` = `.${ZONE}` (App.tsx:72,217) and its own guard relies on that leading dot to reject hosts like `evilddg-waddle.containers.tinfoil.dev` that merely end with the zone substring. The two call sites therefore use the same ZONE constant with different suffix semantics, and the discovery path silently accepts any host whose string ends in the zone text rather than a host label-bound inside it. The client tests (client/src/lib/concierge.test.ts:127) pass a bare zone and only assert that a completely unrelated host is refused, so this boundary is unpinned.

**Fix**: Prepend the dot inside `bootInstance` (e.g. `zone.startsWith('.') ? zone : '.' + zone`) before the `endsWith` test, or have the guard compare against `.${zone}`; add a test with `https://evil-ddg-waddle.containers.tinfoil.dev`.

### 6-hex-char user hash can alias two users to the same machine via rebind
**`concierge/src/user-machines.ts:66`** — found by security
`hashSub` truncates sha256 to 6 hex digits (24 bits) and `rebind` (line 66-67) returns the first name in `known` whose prefix `waddle-u<hash6>-` matches, without any further check tying the machine to the requesting `sub`. Two distinct subs that collide in those 24 bits share a prefix: an attacker (or merely an unlucky user) hitting `rebind` can be handed the other user's machine name, which `/boot` then returns as their own URL (`https://<name>.<DOMAIN_BASE>`). Birthday-collision odds become non-trivial well before a few thousand users (~3% at 1k, ~50% at ~4.8k). The enclave's own JWT gate limits data exposure, but this defeats the per-user machine ownership invariant the diff introduces.

**Fix**: Widen `hashSub` to a full or sufficiently long (e.g. 16-byte) digest in the name, or verify ownership beyond the prefix (e.g. persist/derive a per-user binding) so a prefix collision cannot reassign a machine across users.
