### New JWT-accepting /handshake branch and k=1 /handoff/pull fallback ship with no test protection
**`concierge/src/index.ts:485`** — found by tests
The diff changes /handshake from secret-only to a two-tier resolver: a verified bb JWT now calls users.rebind(id.sub) and mints a session for the resolved machine (lines ~484-490), returning `instance`; and /handoff/pull gains a k=1 fallback (lines ~587-597) that, when exactly one armed row has an open fire window, releases that OTHER row and teaches its name. Both are auth-relevant behavior changes with side effects (session minting for a JWT holder; serving a credential the caller did not name). No test covers either: `find **/*.test.ts` shows concierge has only auth/handoff/platform/pool/postbox/table/user-machines tests — there is no index/route test file, and grep across all test files finds no reference to `/handshake` or `/handoff/pull`. The diff's only new test (handoff.test.ts `armed()`) exercises the helper in isolation and cannot reach the route logic. A regression here — e.g. the JWT branch resolving to the wrong machine, or the fallback serving on ambiguity (open.length > 1) — would pass CI silently.

**Fix**: Add route-level tests for /handshake (jwt → rebind-resolved instance, 404 when no registry row; secret tier unchanged) and /handoff/pull (single open window → credential + served name; zero or >1 open windows → 404). If a full concierge app harness is impractical, extract the fallback selection into a pure function and unit-test it directly.

### Adopting the resolved name moves wake-fire keys off the static ALLOWED set — the pool's canFill standby-steal guard goes blind
**`concierge/src/index.ts:490`** — found by correctness
The JWT branch of /handshake now returns `instance: resolved` (a dynamically minted user-machine name), and server/src/concierge.ts adopts it (adoptInstance), so every subsequent machine write — including /timer wake rows — is keyed by that real name. The table's wake callback calls `handoff.markWakeFired(instance)` with that key (index.ts:140), while the pool's steal guard at index.ts:694 is `canFill: () => ![...ALLOWED].some((i) => handoff.windowOpen(i))`. ALLOWED is a static env set (default `{"waddle"}`) that cannot contain names minted at runtime by users.bind/bind (user-machines.ts), and standby/claimed names aren't in it either. Before this change the machine self-reported `INSTANCE = "waddle"` and handshake minted the session for the body name, so fires were keyed `"waddle"` ∈ ALLOWED and the guard saw them; now they are keyed by the adopted real name, so `windowOpen` is never consulted for the instances that actually open windows and canFill returns true during an open release window.

**Fix**: Have canFill consider the same key set the wake table uses (e.g. iterate the live table rows / handoff.armed() rather than the static ALLOWED set), or track open windows in a set independent of instance-name enumerability.

### /handoff/pull k=1 fallback serves a fired machine's escrowed master secret to any shared-secret holder
**`concierge/src/index.ts:597`** — found by security
Before this change, /handoff/pull only returned a credential when a wake fire existed for the exact `instance` named in the body (handoff.release(instance) → notFound otherwise), so the fire-gate bound the served row to the requesting machine. The new fallback (lines 592-599) runs whenever release(instance) fails: it collects every armed row with an open fire window (`handoff.armed().filter(n => handoff.windowOpen(n))`) and, if exactly one exists, calls handoff.release(open[0]) and returns `{ credential: via.cred, instance: open[0] }` regardless of the instance the caller asked for. Auth is requireSecret — the single fleet-wide CONCIERGE_TOKEN (index.ts:61), which every machine is provisioned with (STANDBY_SECRETS includes CONCIERGE_SHARED_SECRET, index.ts:85) and which is also accepted as the external tier (/status). The escrowed credential is the opaque bag `{ secret, schedules[], snapshot? }` — the user's master secret. Consequence: any holder of the shared secret can poll /handoff/pull with an unrelated allowed instance name during any machine's default 3-minute release window and receive that machine's master secret, without knowing or naming it; the release is one-shot (firedAt.delete in handoff.release), so this also starves the legitimate schedule-boot and permanently denies it its credential until the next arm. This directly contradicts the route's own guarantee ('a boot that the concierge did not successfully deploy for a schedule gets 404'). The k=1 rationale in the comment ('exactly one fire window identifies its row') assumes the caller is that fire's boot, which nothing verifies.

**Fix**: Bind the served row to the requester before serving: e.g. require the puller to name the fired instance (no unnamed fallback), or gate the fallback on a per-machine attestation/name proof rather than a guessable 'exactly one open window'. At minimum, scope the fallback so a caller cannot receive a credential for an instance whose name it did not present and did not create, and log/deny the ambiguous k>1 case rather than silently serving.

### Legacy v1 AAD fallback is fed the already-adopted instance, so in-flight v1 blobs no longer open
**`server/src/index.ts:334`** — found by correctness
openPostbox/openSnapshot now open with `openAny(key, buf, [AAD_V2, AAD_V1(instance)])` (postbox.ts:46, snapshot.ts:27), relying on the v1 fallback to read blobs sealed before the cutover. Legacy v1 seals used the baked name "waddle" (`waddle-postbox-v1:waddle` / `waddle-snapshot-v1:waddle`, see the new tests). But the callers now pass `currentInstance()`, and at both production call sites the name has already been adopted before the open: at unlock (line 334) handshakeConcierge runs first and adopts the JWT-resolved name; at autonomous boot (line 852) pullHandoff adopts before openSnapshot. So `AAD_V1(currentInstance())` is `…waddle-u…`, which cannot match the legacy `…:waddle` AAD, and `AAD_V2` cannot match a v1 blob — openPostbox throws and the mail is silently dropped (re-fire / context-free boot). The added tests pass only because they open with "waddle", i.e. an un-adopted instance; the shared-secret handshake path likewise stays "waddle", so the failure is specific to the bb-JWT production path the fallback was written for.

**Fix**: Pass the baked boot name (not the adopted currentInstance()) as the v1 fallback candidate, or try both — e.g. openAny(key, buf, [AAD_V2, AAD_V1("waddle"), AAD_V1(instance)]) — so legacy blobs open regardless of adoption order.

### v1 AAD fallback uses the post-adoption name, so cutover blobs it exists for never open
**`server/src/postbox.ts:47`** — found by robustness
The legacy fallback builds `AAD_V1(instance)` from the `instance` argument, and every production caller now passes `currentInstance()` (server/src/index.ts:334 unlock, :556/:565 autonomous re-sleep). Pre-cutover, sealPostbox was called with the module constant `INSTANCE = process.env.WADDLE_INSTANCE ?? "waddle"` (the removed line), i.e. the baked name "waddle" — the machine provably cannot know its registry name (`waddle-u<hash>-…`), which is exactly why this diff introduces adoption. By the time the open runs in the production path, adoption has already happened: /unlock awaits the handshake (which calls `adoptInstance`, concierge.ts:87) before `openPostbox(secret, currentInstance(), blob)`, and the autonomous path calls `pullHandoff()` (which calls `adoptInstance`, concierge.ts:167) before any open. So `openAny(key, buf, [AAD_V2, AAD_V1("waddle-u…")])` can never match a legacy blob sealed under `waddle-postbox-v1:waddle`; it throws, the /unlock catch turns it into "postbox merge failed — degrading to re-fire delivery", and the unattended run's done-markers/tombstones are silently lost (the schedule re-fires). The new test at postbox.test.ts:92 passes `instance="waddle"` directly, so it exercises the fallback with the very value production no longer supplies and gives false confidence.

**Fix**: Derive the v1 AAD candidate from the baked/legacy name (e.g. `process.env.WADDLE_INSTANCE ?? "waddle"`) — or accept both the current and the pre-adoption name — instead of `currentInstance()`, and add a test that opens a `waddle-postbox-v1:waddle` blob after `adoptInstance` has set a registry name.

### Snapshot v1 fallback has the same post-adoption AAD mismatch
**`server/src/snapshot.ts:30`** — found by robustness
Same mechanism as postbox.ts: `openSnapshot(secret, currentInstance(), cred.snapshot)` (server/src/index.ts:851) runs after `pullHandoff()` has adopted the registry name, while pre-cutover snapshots were sealed with `AAD_V1("waddle")` (the removed `sealSnapshot(armSecret, INSTANCE, …)` with the baked constant). `openAny(…, [AAD_V2, AAD_V1(adoptedName)])` therefore fails on exactly the in-flight cutover blobs the fallback is documented (snapshot.ts:13-14) to support; the autonomous boot logs "snapshot restore failed — booting context-free" and the machine comes up without state. The added test (snapshot.test.ts:56) passes the literal "waddle", not an adopted name, so it does not catch this.

**Fix**: Include the baked/pre-adoption name in the v1 AAD candidate list (or stop sourcing it from `currentInstance()`), and cover the adopt-then-open sequence in a test.

## 🟡 Suggestion

### armed() test pins only fresh rows — does not exercise the expired-row semantics the new k=1 resolver depends on
**`concierge/src/handoff.test.ts:92`** — found by tests
`armed()` returns `[...rows.keys()]`, but `rows` is only lazily pruned by `release()`; rows whose `expiresAt` has passed (arm validates nothing, and `status()` never deletes) remain in the map and therefore appear in `armed()`. The added test arms two fresh rows and asserts the listing, so it cannot distinguish 'currently armed' (its title and the docstring 'Armed row names') from 'has ever been armed and not released'. The new /handoff/pull fallback at index.ts:587 does `handoff.armed().filter(windowOpen)` and serves only when the count is exactly 1, so a lingering expired row that still has a fire within the release window would make the count 2 and deny a legitimate wake boot its credential — the failure path the test does not cover. The pre-existing expiry test (lines 41-48) exercises `release`/`status` only, never `armed()`.

**Fix**: Extend the armed() test to (a) advance past ttlMs and assert the row's expiry behavior explicitly, pinning whatever semantics are intended, and (b) clear() a row and assert it disappears, so the resolver's count invariant is protected.

### k=1 fallback consumes the one-shot fire for any allowed shared-secret caller
**`concierge/src/index.ts:593`** — found by robustness
When a pull for `instance` is notFound, the handler serves whichever single armed row currently has an open window and calls `handoff.release(open[0])` (line 595), which does `firedAt.delete` (handoff.ts:107) — one-shot. The caller is only authenticated as *some* allowed instance holding the shared secret (the secret is shared by all machines), and there is no check that the fired row's waiter is the caller. A stray or duplicate pull (or a second secret-holding machine) that carries an allowed name with no fire therefore receives the credential (master secret + sealed snapshot) of the fired row and permanently consumes its window; the intended boot then gets a 404 and cannot run its schedule until the next fire — a non-recoverable consumption of the escrow. The code comment acknowledges the k>1 ambiguity but leaves the k=1 mis-delivery/denial path open.

**Fix**: Guard the fallback so it only fires for the expected waiter (e.g. keep the legacy shared name, or a pull marker minted at deploy time), and/or make the fallback non-consuming on a retry so a duplicate request cannot burn the window the intended boot needs.

### adoptInstance / currentInstance introduce untested name-adoption behavior
**`server/src/concierge.ts:32`** — found by tests
The diff replaces the module constant `INSTANCE` with a mutable `INSTANCE` plus `adoptInstance(name)` (guarded by NAME_SHAPE = /^[a-z0-9][a-z0-9-]{0,62}$/ and a `name !== INSTANCE` short-circuit) and exports `currentInstance()`. These gate the name used by every subsequent POST (post() body `{ instance: INSTANCE }`) and by the v1 AAD fallback at the openPostbox/openSnapshot call sites in server/src/index.ts. server/src/concierge.ts has no test file (see `find **/*.test.ts`), and nothing covers the guard: e.g. that an over-long/invalid name is rejected and leaves INSTANCE unchanged, that the same name is a no-op, or that pullHandoff adopts before returning the credential. A regression in the regex or the ordering would silently re-key writes to the wrong machine with no test failing.

**Fix**: Add a server/src/concierge.test.ts that stubs fetch: assert currentInstance() defaults to WADDLE_INSTANCE/'waddle', adoptInstance rejects names failing NAME_SHAPE, and handshakeConcierge/pullHandoff call adoptInstance with the response's `instance` (and only when session/credential resolution succeeded).
