## 🔴 Critical

### Context-free autonomous boot reads background off, so the whole autonomous sleep sequence is skipped
**`server/src/index.ts:473`** — found by correctness, robustness
The sleep block is gated on `conciergeActive() && autonomyEnabled() && backgroundTasksEnabled()` (line 473), and `backgroundTasksEnabled()` reads the on-disk preferences.json. On an autonomous boot the ONLY thing that can put that file back is the restored snapshot: the credential carries `{secret, schedules, snapshot?}` and no preference. The code explicitly supports a context-free arm — the snapshot is omitted when it exceeds MAX_SNAP_B64 (768 KiB, which the comment says a lived-in archive routinely exceeds) or when `createArchive`/`sealSnapshot` throws (lines 545-560). On that boot preferences.json is absent, `getPreferences()` (lazily cached, never re-read) returns `{background:false}`, and the guard is false. Consequences at re-sleep: deathFlare/wake rows (474-480) are skipped, the postbox is not posted (487), and the escrow is not re-armed (530) — so the just-completed run's transcript (held only in the ephemeral-volume master-sealed log, no bb grant on an autonomous boot) is lost, and no wake timer or credential survives, so recurring schedules fire at most once and then silently stop. The credential's very existence proves the user had background on; deriving the gate from the restored file conflates 'preference file missing' with 'user chose tier 0'.

**Fix**: Do not gate the autonomous post-run path on the persisted preference. Either carry `background` in the WakeCredential and use it here, or gate on `autonomous` (which is only set when a wake credential was accepted) instead of `backgroundTasksEnabled()` for the wake-row/postbox/re-arm block, keeping the on-disk preference for the user-session path only.

## 🟠 Important

### Master unlock secret is escrowed to the concierge, letting it decrypt all user state
**`server/src/index.ts:563`** — found by correctness, security, robustness
The sleep gate now calls armHandoff({ secret: armSecret, schedules, snapshot }, bearer, ttl) with the RAW 64-byte master (armSecret is the client's unlock secret, set at /unlock line 293 and at autonomous boot line 867). Previously the escrow carried HKDF(master,"autonomy") — a schedule-scoped subkey that could not derive the log/postbox/snapshot keys — and this change replaces it with the master itself. The sealed snapshot (snapshot.ts, key = HKDF(master,"waddle/snapshot")) is sealed with the same master that travels in the same credential bag, so sealing provides no confidentiality against the holder: a compromised concierge, or anyone who captures the armed credential from concierge memory, can decrypt the whole machine snapshot AND derive every other key domain (log, postbox) and fully unlock the machine. snapshot.ts itself documents "It is hygiene, not a boundary: the escrow holds the key too, by design". The BackgroundDialog discloses this, but the change still converts the concierge from a ciphertext-holder into a full-master holder.

**Fix**: Keep the concierge escrow schedule-scoped (subkey) and let the snapshot be sealed under a key the escrow cannot derive, or move the whole capability behind an explicit acknowledged platform-trust decision rather than the UX dialog.

### Master root secret written in cleartext to DATA_DIR on every sleep, contradicting the code's stated invariant
**`server/src/index.ts:573`** — found by correctness, security, robustness
At the sleep gate the dev file arm writes armWakeCredential({ secret: armSecret, schedules, snapshot, inferenceKey }) — the raw master plus a sealed snapshot — into DATA_DIR/wake-credential.json in plaintext (wakeboot.ts, mode 0o600). This is a regression in severity: before this change the file held only HKDF(master,"autonomy"). The stated invariant above armSecret (index.ts:799-801) is "never in DATA_DIR", and the only guard is a runtime check `!process.env.TINFOIL_API_KEY && autonomyEnabled()`. A prod deploy that is missing TINFOIL_API_KEY, or that sets WADDLE_WAKE_AUTONOMY=1 on a machine with a mounted persistent volume, writes the master to disk at rest — from which the log, postbox, and snapshot keys are all derivable. The archive excludes wake-credential.json, but the file itself is the exposure.

**Fix**: Never serialize the master secret to the file arm — keep the on-disk dev credential scoped to a derived key, or write only `{snapshot}` (already sealed) plus schedules and require the secret from the escrow.

### Warned delegation opt-in is client-side only — any authenticated session can enable full delegation
**`server/src/index.ts:728`** — found by correctness, security, robustness
The new WS `preference` handler accepts { type: "preference", background } and calls setPreferences({ background }) with no authorization beyond holding a valid session token. Because background=true is what causes the next sleep gate (line 530) to escrow the master secret and snapshot to the concierge, any holder of a session token (12h TTL, state.ts SESSION_TTL_MS; e.g. a token lifted from the WSS ?token= or localStorage) can unilaterally turn on full delegation and cause the master to be escrowed on the next sleep — a privilege escalation that does not require the warned dialog the UI presents. The code comment explicitly concedes the opt-in is "UX honesty, not the security boundary". The same applies to enabling via the /unlock `background` field (lines 295-306).

**Fix**: Treat the acceptance as server-side state (require an accepted flag/timestamp that only the warned opt-in UI can write) or document that the warning is not a security boundary and remove the false assurance from the code comments.

## 🟡 Suggestion

### Fresh-device preference adoption marks the warning accepted without ever showing it, untested
**`client/src/App.tsx:473`** — found by correctness, security, robustness, tests
In the unlock flow: `if (getBackgroundPref() === null && typeof unlocked.background === "boolean") { if (unlocked.background) acceptWarning(); else setBackgroundPref(false); setBackground(unlocked.background); }`. On a device that has never chosen, a machine whose snapshot reports background=true causes acceptWarning() — which sets both the ACCEPTED_KEY and PREF_KEY (client/src/lib/background.ts) — so the one-time delegation warning is recorded as shown-and-accepted on this device without BackgroundDialog ever rendering. The only client tests are client/src/lib/background.test.ts and bb-grant.test.ts (find shows no App/component test), so this adoption branch, the toggleBackground warn-gate (hasAcceptedWarning() → open dialog vs. send intent), and the server `preference` echo path (onServerEvent → setBackgroundPref/setBackground) are all unprotected: a regression could enable tier-1 delegation (master secret escrowed to the concierge) on a fresh device with no warning and no failing test.

**Fix**: Adopt only the preference value (setBackgroundPref) and let the first local enable still present the warning, as the toggle path does; add a test for the adoption branch.

### schedule_create's new delegation gate has no test asserting the refusal path
**`server/src/agent.ts:263`** — found by correctness, security, robustness, tests
The diff adds a delegation gate to schedule_create: `if (!backgroundTasksEnabled()) { return {content:[{type:"text", text:"Background tasks are disabled …"}]} }`, and backgroundTasksEnabled() reads server preferences (server/src/preferences.ts). There is no agent test file at all (find shows server tests for approvals/archive/bb-backup/input-map/log/memory/postbox/preferences/schedules/snapshot/state — no agent.test.ts), so nothing exercises either branch: with background off the tool must return the refusal text and NOT create a schedule; with background on it must fall through to createSchedule. A regression that drops or inverts the gate (e.g. deleting the early return, or reading a stale pref) would be invisible — schedules would silently be creatable at tier 0, which is exactly the delegation boundary this change is built around.

**Fix**: Add a test that sets the preference off and asserts execute returns the refusal text without creating a schedule, plus the enabled-path creation.
