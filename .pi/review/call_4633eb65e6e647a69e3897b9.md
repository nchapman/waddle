### /handoff/pull k=1 fallback serves a fired machine's escrowed master secret to any shared-secret holder
**`concierge/src/index.ts:601`** — found by correctness, security, robustness
The legacy fallback (concierge/src/index.ts ~611-618) classifies a caller as 'legacy' whenever the presented `instance` matches neither USER_NAME_RE nor STANDBY_NAME_RE (`legacyCaller = !USER_NAME_RE.test(instance) && !STANDBY_NAME_RE.test(instance)`), and then serves that open fire window's credential via `handoff.release(open)`. Two gates stand in front of it and neither binds the caller to the fired machine: `allowedInstance(instance)` still passes for an operator name such as `waddle` (it is in ALLOWED) even though it matches neither regex, and `requireSecret` only checks the single fleet-wide CONCIERGE_TOKEN (which every machine holds via STANDBY_SECRETS and the operator holds). So any shared-secret bearer can POST /handoff/pull with `{"instance":"waddle"}` and, when exactly one fire window is open, receive the escrowed `credential` of a machine that is not theirs — `credential.secret` is the master secret. That is cross-machine master-secret disclosure, exactly the prior review's finding; the diff does not touch this path, so it remains valid.

**Fix**: Bind the released credential to the requesting machine (attested identity or a per-fire nonce known only to the fired boot) rather than releasing on a bare shared-secret + single-open-window match, or require the caller to present the fired instance's name/token.

### Pool destroy callback swallows every error, defeating the pool's retry-on-failed-destroy contract
**`concierge/src/index.ts:690`** — found by correctness
index.ts's pool `destroy` dep previously let platform errors propagate (try/finally with no catch), so pool.ts's `destroyMachine` caught the rejection and kept the entry tracked: "The entry is removed ONLY on a successful (or already-gone) destroy — a failed one keeps it tracked so the next tick retries instead of orphaning a billing machine." The new body does `await platform.destroy(name).catch(() => undefined);` — deps.destroy can no longer reject, so `destroyMachine`'s catch branch (not-found → free slot; other → log + retry next tick) becomes dead code and the machine is always deleted from the pool's map. Concretely: platform.destroy rethrows a non-not-found delete error (platform.ts destroy returns "(already gone)" only for /not found|no such/i), but that throw is now swallowed, the still-running/billing standby is dropped from pool bookkeeping, and `poolNames.delete(name)` immediately frees the name so `nextName()` can mint the same name again while the old machine still exists. The inline comment ("a failed destroy retries with the name still held") is now false.

**Fix**: Do not swallow: `try { await platform.destroy(name); } finally { poolNames.delete(name); }` so the rejection reaches destroyMachine's retry path while the name still frees on every outcome. Let the janitor/backstop be the best-effort cleanup, not the pool dep.

### Orphan janitor can destroy live pool stock due to boot-time ordering race with scanLeftovers
**`concierge/src/index.ts:782`** — found by correctness, robustness, tests
The new janitor (index.ts:780-788) computes its spared set from `poolNames` (spared = users.known() ∪ poolNames ∪ ALLOWED) and destroys any STANDBY_NAME_RE instance not in it. poolNames is memory-only and is refilled by the separate `scanLeftovers` (index.ts:754, inside the pool block). Both `void scanLeftovers()` and `void scanUsers()` (index.ts:791) are fired in the same tick; each calls `platform.statuses()` → `listRows()`, and listRows memoizes only AFTER the CLI resolves (platform.ts:170-171), so the two calls issue independent `tinfoil container list` execs whose `.then` callbacks run in resolution order — not guaranteed. scanLeftovers populates poolNames synchronously inside its `.then` (index.ts:734-735); if scanUsers' `.then` runs first, poolNames is still empty, so every leftover standby is unmatched and the janitor calls `platform.destroy(name)` on all of them. Consequence: a concierge restart can delete the entire warm-standby stock it just inherited.

**Fix**: Make the janitor's standby handling independent of scan ordering — e.g. have scanLeftovers seed poolNames (await it) before scanUsers' janitor runs, or skip STANDBY_NAME_RE names in the janitor entirely and leave standby cleanup to the pool/adoption path.
