## 🔴 Critical

### Adopting Running leftovers lets the pool re-hand-out and then destroy a machine a user already claimed
**`concierge/src/index.ts:504`** — found by correctness, security, robustness
The leftover scan now pushes every standby-named instance the platform reports Stopped OR Running into pool.adopt() (index.ts:504). A machine a user already claimed via /assign keeps its `waddle-standby-N` name and is Running while in use, and the scan runs at boot and every POOL_SCAN_MS (5 min) — so a concierge restart/redeploy adopts it. adopt() tracks it as `booting` (pool.ts:139-146), the next tick promotes anything that answers health (health == platform status 'Running', index.ts:162/466) to `warm`, and assign() then hands that URL to the next /assign caller (pool.ts:139-148) while the first user is still using the machine. Independently, tick's reaper destroys on TTL alone (`if (expired || dead)`, pool.ts:93-115) via restInstance + `tinfoil container delete` (index.ts:452-459) — so a live session's machine is stopped and deleted ~STANDBY_TTL_MS (1 h in config/concierge-tinfoil-config.yml) after adoption. The inline rationale (index.ts:501-503) is wrong: it is not bounded by the claim grace, which is 12 h and only stops the machine (STANDBY_CLAIM_GRACE_MS, index.ts:318), whereas the pool TTL is 1 h and deletes it; and the pool's `poolNames` claim bookkeeping is memory-only, so a restart re-admits a claimed name. The new pool.test.ts case (lines 132-149) ratifies exactly this sequence (adopt → warm → assign → TTL destroy) without modelling a claimed/unlocked machine, and the doc block directly above the change (index.ts:481-488) still promises 'Running ones are never touched'.

**Fix**: Keep adopting Running leftovers, but never as an assignable standby: give them a distinct non-`warm` state that `assign()` ignores and reap them on the claim-grace clock (STANDBY_CLAIM_GRACE_MS) rather than STANDBY_TTL_MS — or gate adoption on the machine's own /health `locked` flag (server/src/index.ts:132 `hello(VERSION, !lock.unlocked, ...)`) so unlocked/claimed machines are left alone.

## 🟠 Important

### Wake handoff window opens before the deploy resolves; canFill does not cover in-flight boots, so the one-shot secret can be pulled by a non-intended machine
**`concierge/src/index.ts:208`** — found by security
handoff.ts's new contract (lines 58-62) states 'Callers must only invoke this after the deploy resolves — opening the window on the timer alone would let any boot in flight steal the one-shot (SME review).' This diff's caller does the opposite: handoff.markWakeFired(instance) runs synchronously at line 208, before `ensureInstance(instance)`. The claimed replacement mitigation, canFill (line 476), only defers *new* pool fills during an open window; it does nothing about a standby already in 'booting' state that comes up during the window, nor about the retry path — on deploy failure the row is re-armed (`table.setWake(instance, jobId, 2*60_000)`, line 216) up to 3 times, each fire refreshing the window, with no legitimate machine deployed. Any machine whose server starts during an open window runs `if (autonomyEnabled() && !lock.unlocked) { ... pullHandoff() }` (server/src/index.ts:679-680); because release() is keyed only on the instance name 'waddle' and the window (handoff.ts:77-92), that machine — not the intended schedule-boot — receives the user's unlock secret and inference key. This is a credential disclosure to an unintended machine.

**Fix**: Honor the handoff.ts contract: call markWakeFired only after the deploy resolves, and bind the release to the specific scheduled boot (one-time per-fire token minted at deploy time, or a per-boot nonce) rather than relying on instance name + time window; do not refresh the window from a failed-deploy retry.

### Wake-retry budget is keyed per schedule, never reset — the 3-retry bound is consumed across separate fires
**`concierge/src/index.ts:215`** — found by correctness, robustness
The retry counter added here uses key `${instance}:${jobId}` and is only ever incremented (`wakeRetries.set(key, n)` at 216; `if (n <= 3)` at 217; no `delete`/reset anywhere — `wakeRetries` is referenced only at 215-218 and declared at 233). `jobId` is not per-fire: the machine writes wake rows with `jobId: s.id` (server/src/index.ts:451), and `s.id` is the schedule's UUID (server/src/schedules.ts:68 `id: randomUUID()`), which survives every firing (`markRun` only stamps `lastRun`, schedules.ts:141-148). So for a recurring schedule the budget is spent over the schedule's lifetime, not per fire: occurrence 1 fails → n=1 (re-arm), occurrence 2 → n=2, occurrence 3 → n=3, and the *next* single transient failure (n=4) takes the `else` branch, logs "failed 3x — job abandoned", and does NOT call `table.setWake`, so the wake row is dropped and that schedule will not be woken again for the rest of the concierge process's life (until the user happens to unlock). It also never resets on a *successful* deploy, so a schedule that had 3 failures months apart loses retries permanently. (The off-by-one is cosmetic: `n<=3` yields 4 attempts while the log says 3x.)

**Fix**: Make the budget per fire: include the fire's due time in the key (e.g. `${instance}:${jobId}:${due}`) or store `{key, attempts}` and reset/delete the entry in the `.then` (deploy ok) branch and after the abandon branch, so repeated occurrences start from a fresh count.

### The new "session-tier only" rule doesn't close the row-write path: /handshake mints that session from the same external credential
**`concierge/src/index.ts:281`** — found by correctness, security
The new authorize() drops the external fall-through and its comment asserts the security property: 'the external tier (shared secret / any bb JWT) must never write table rows. A wake row written with the shared secret mints a handoff release window on demand — the fire-gate would be decorative.' But /handshake (concierge/src/index.ts:331-340) still authenticates with the same verifyExternal() tier and returns table.mintSession(instance).sessionToken. authorize() accepts exactly that token (line 273: `token === e.sessionToken`). So any holder of a valid betterbase JWT for the concierge's audience (or the shared secret) can: POST /handshake {instance:'waddle'} -> get session_token; POST /timer {action:'wake', due_ms:1000, job_id:'x'} with that session token -> write a wake row; the row fires -> markWakeFired() opens the release window; then POST /handoff/pull {instance:'waddle'} -> receives the escrowed user secret + inferenceKey. The exact 'decorative fire-gate' scenario the change claims to close is still reachable, so the change provides a false sense of protection while the escrow remains exfiltratable.

**Fix**: Separate the two trust levels instead of only blocking one route: don't accept the escrow/pull credential (or the shared secret generally) as the bearer for /handshake, or require wake-row writes to carry a credential that the pull path cannot mint (e.g. a per-machine token issued over the attested channel), and assert the invariant in a test that drives /handshake → /timer → /handoff/pull end to end.

### Failed destroy on a health-dead standby is no longer retried, and no test catches it
**`concierge/src/pool.ts:95`** — found by tests
The diff sets `m.state = "destroying"` before awaiting destroy. The reap predicate is `dead = m.state === "warm" && !health(...)`, so once state is "destroying" the machine is neither `dead` nor (pre-TTL) `expired`, and the generic-error branch (line 108) keeps it tracked with the comment/log 'retrying next tick' — but the next tick skips it until TTL. Before this diff state stayed "warm" and the retry worked. The existing test 'retries a failed destroy instead of orphaning the machine' only drives the TTL-expired path (it advances the clock 61_000 > ttl 60_000), so the health-death + failed-destroy failure path is untested and the regression is invisible; a warm-unhealthy standby whose destroy keeps failing lingers up to STANDBY_TTL_MS (default 1h) of billing.

**Fix**: Add a test that marks a warm machine unhealthy, makes destroy fail generically, ticks, and asserts a retry occurs on the next tick (this will fail today), then fix the reap predicate so "destroying" machines are re-attempted (e.g. track a destroying flag separately from the health gate).

### New canFill release-window deferral has no test coverage
**`concierge/src/pool.ts:126`** — found by tests
The diff adds a fill gate `if (cfg.size > 0 && live().length < cfg.size && !(deps.canFill && !deps.canFill()))` and the `canFill?()` dep, described in index.ts:476 as the sole replacement for the standby-steal guard removed from the fire-ordering (`canFill: () => !handoff.windowOpen("waddle")`). pool.ts is explicitly built to be unit-tested ('extracted so its semantics are testable without the service'), and pool.test.ts's harness (lines 18-38) constructs deps without `canFill`, and no test anywhere sets it (grep for `canFill` matches only index.ts/pool.ts). So the deferral branch — the entire mitigation for the standby-steal race — is never exercised: a regression that boots during an open window would ship green.

**Fix**: Add a pool.test.ts case that sets `deps.canFill = () => false`, ticks with `live().length < size`, and asserts no boot; then flip it true and assert the replacement boots on the next tick.

The new handoff.test.ts case ('windowOpen mirrors the release gate; clear disarms') passes an explicit `releaseWindowMs: 60_000`, and the other window test uses `60_000` too, so the default value — the one production actually runs — is never asserted; an accidental change back to a long window (the documented race risk) would not fail any test.

### Store contract for markWakeFired contradicts its only caller's deliberate fire-time ordering
**`concierge/src/handoff.ts:61`** — found by correctness
The new doc says "Callers must only invoke this after the deploy resolves — opening the window on the timer alone would let any boot in flight steal the one-shot". The only caller does the opposite on purpose: `handoff.markWakeFired(instance)` runs immediately when the timer fires, before `ensureInstance` is even called (concierge/src/index.ts:208-212, whose own comment explains the window must open at fire time or the intended machine pulls `no-fire`). The store enforces no ordering, so the documented precondition is false, and a future caller/maintainer trusting it will either mis-reason about the fire-gate or add a "fix" that reintroduces the live-caught race.

**Fix**: Reword the contract to what the code actually guarantees (the window opens when the timer fires and closes on first release or after releaseWindowMs) and record the compensating control (the pool's canFill deferral) next to it, so the two ordering constraints are documented in one consistent place.

### canFill hardcodes instance "waddle", so the release-window deferral silently no-ops for any other configured instance
**`concierge/src/index.ts:476`** — found by robustness
`canFill: () => !handoff.windowOpen("waddle")` checks the literal name while the fire hook calls `handoff.markWakeFired(instance)` with the instance that owns the fired row and every other path is parameterised by ALLOWED (CONCIERGE_ALLOWED_INSTANCES, index.ts:38-46). With `CONCIERGE_ALLOWED_INSTANCES=mybox`, windowOpen('waddle') is always false, the pool fills immediately, and the standby-steal protection the wake hook now explicitly relies on (index.ts:203-207: 'closed by the pool's canFill deferral instead') is gone — silently, with no log or test to catch it. There is also no test around canFill (line 476) in pool.test.ts.

**Fix**: Derive the deferral from the rows the concierge actually holds — e.g. `() => ![...ALLOWED].some((i) => handoff.windowOpen(i))` or have the store expose `anyWindowOpen()` — and add a pool test asserting fills are deferred while a window is open.

### The destroy not-found matcher is broad enough to untrack a still-running machine, and that path skips the name cleanup the success path does
**`concierge/src/pool.ts:104`** — found by robustness, tests
`/not found|no such|already (been )?deleted/i.test(String(e))` is matched against the whole `Command failed: ...` message from the injected destroy verb, which is `restInstance` (tinfoil container stop) followed by `tinfoil container delete` (index.ts:452-459). Any CLI-level error containing 'no such'/'not found' that does not mean the instance is gone (unknown flag/subcommand, a missing path, a wrapper's 'command not found') takes the branch that deletes the entry from `machines` — untracking a machine that still exists and bills, which is the exact orphaning the branch's own comment says it prevents. Secondarily, the branch declares success without running the success-path cleanup: `poolNames.delete(name)` lives after the exec inside deps.destroy (index.ts:457), so a not-found destroy leaves the name burned in poolNames forever while the pool boots a fresh index, drifting the name space that the operator's egress allowlist is pinned to.

**Fix**: Anchor the matcher on the platform's specific not-found signal (exit code / exact stderr text) instead of loose substrings, and free the name on the success path in a `finally` inside deps.destroy so 'gone' always recycles it.

### The sleep-gate escrow re-arm discards its success flag and uses an empty bearer when CONCIERGE_SHARED_SECRET is unset
**`server/src/index.ts:463`** — found by robustness
`await armHandoff(..., process.env.CONCIERGE_SHARED_SECRET ?? "", ...)` ignores the returned boolean. armHandoff returns false for a 401 (post() maps status 401 to null, server/src/concierge.ts:26-45), and with the secret unset it always sends `Bearer ` — a guaranteed 401. The unlock path treats the same result as warn-worthy (server/src/index.ts:277-279), but here a failed re-arm is silent, and the wake rows for the next occurrence were already written just above (index.ts:450-452): the concierge will boot the machine for the schedule with no credential in escrow, so the boot stays locked and the work is silently lost (burning a boot until the locked-boot backstop reaps it). Because the failure is indistinguishable from success in the logs, the degradation is invisible.

**Fix**: Log the re-arm result (`if (!ok) app.log.warn({ horizon }, 'sleep-gate escrow re-arm failed — next wake boot stays locked')`) and skip the call entirely when CONCIERGE_SHARED_SECRET is absent instead of sending an empty bearer.
