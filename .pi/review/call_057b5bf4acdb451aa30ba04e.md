## 🔴 Critical

### Boot scan adopts standbys by name alone, so a machine a user already claimed is re-assigned and then deleted
**`concierge/src/index.ts:372`** — found by security, robustness
On every concierge boot the scan adopts any platform instance matching STANDBY_NAME_RE whose probe fails (h === null) or reports locked:true (isUnclaimed). A machine a user already claimed via /assign keeps its `waddle-standby-N` name (name stays burned, but the instance name is unchanged), and a claimed machine hits BOTH adoption conditions across its normal life: on idle it exits (server/src/index.ts sleep → process.exit, restart policy "no"), so the probe fails → h === null → adopted; on every fresh boot Lock.unlocked=false, so /health reports locked:true (server/src/index.ts:136/649) → isUnclaimed → adopted. pool.adopt() then tracks it as a blank standby, and pool.ts promotes ANY machine that merely answers health (deps.health = instanceHealthy, concierge/src/index.ts:162, which ignores `locked`) to "warm"; assign() returns the next warm machine to whoever calls /assign. If another user claims it, the machine is removed from the pool (pool.ts assign) and /assign clears its stop row (table.userWake), so the pool never reaps it and the second user cannot unlock it (state.ts rejects a different secret with 401) — an orphaned, still-billing machine. If nobody claims it before the pool TTL, destroy() runs restInstance + `tinfoil container delete` (concierge/src/index.ts:341) and permanently deletes the original user's machine. So after any concierge restart, a user's standby-named machine is either handed to a different user or stopped-and-deleted after ~STANDBY_TTL_MS.

**Fix**: Do not infer ownership from locked/health across a mailbox wipe: persist a claim marker (per-standby record or an instance label) so a machine this process previously handed out is never re-adopted. Re-check `locked` immediately before assign(), and never point pool destroy() at a name that has been claimed.

## 🟠 Important

### A claimed standby that never unlocks loses its only backstop and is permanently invisible to the pool — it bills until the 24 h sweep
**`concierge/src/index.ts:261`** — found by robustness
/assign hands out a warm machine and then (a) `pool.assign()` deletes it from the pool map (pool.ts:104-113) and (b) `table.userWake(got.name)` (line 261) clears the pending stop row that the machine armed for itself at boot via the new locked-boot block (server/src/index.ts:649-656 → renewIdleStop → due = WADDLE_IDLE_MS + 30 s, server/src/concierge.ts:16-21). Until the user unlocks, nothing re-arms it: the machine's own idle gate returns early while `lastActivity === null` (server/src/index.ts:443-447) and renewIdleStop only runs on unlock, ws activity or autonomous boot (server/src/index.ts:246, 336, 536, 631). The pool cannot take it back either: scanLeftovers skips every name in `poolNames` (line 369) and assigned names are in `poolNames` (line 327/370), so the machine is neither adopted nor reaped for the life of the process. There is no release/return verb (only /health, /assign, /status exist). Consequence: a claimed-but-never-unlocked standby runs until the backstop sweep's HARD_STOP_MS (default 24 h, line 43) instead of STANDBY_TTL_MS (60 min) — 24x the budget the pool exists to enforce — and even then it is only stopped (line 411), never deleted. This is not a rare path: the new client fallback at client/src/App.tsx:250-253 abandons an assigned standby as soon as it fails verification (wakeCore posts /wake for instance "waddle", App.tsx:196, and never tells the concierge), and the ordinary 'user closes the tab at the lock screen' case does the same.

**Fix**: Give the claim a bounded grace instead of an unbounded one: at /assign, arm a fresh stop row (e.g. `table.setStop(name, CLAIM_GRACE_MS)`) rather than only clearing it, and/or let the leftover scan re-adopt a name whose /health still reports locked:true even if the name is in poolNames (skip only names currently tracked in the pool map), so an abandoned claim is reaped by the pool's TTL. Add a release/reap path the client can call when it walks away from an assigned standby.

### Every warm standby is created holding the concierge's shared control bearer, and /assign hands those machines to any authenticated caller
**`concierge/src/index.ts:337`** — found by security, robustness
Pool boot runs `tinfoil container create ... --secret CONCIERGE_SHARED_SECRET --secret TINFOIL_API_KEY` (STANDBY_SECRETS default at concierge/src/index.ts:66), so every standby's process.env carries CONCIERGE_SHARED_SECRET — the same secret server/src/index.ts:649 sends as a Bearer to the concierge and that verifyExternal accepts as SHARED_SECRET (= CONCIERGE_TOKEN) whenever JWKS is unset, authorizing /wake, /handshake and /timer for EVERY name in ALLOWED, not just the machine that holds it. GET /assign (concierge/src/index.ts:253) returns such a machine's URL to any caller who passes verifyExternal, and the in-machine agent ships a `bash` tool that runs arbitrary commands (server/src/agent.ts:293; server/src/approvals.ts always asks for bash), so the assignee can read process.env and exfiltrate the operator-wide concierge control bearer (and TINFOIL_API_KEY). The pool therefore multiplies an operator-scoped credential into N machines that any authenticated user can obtain, defeating the concierge's per-instance scoping.

**Fix**: Do not inject CONCIERGE_SHARED_SECRET into pool standbys. Give each standby an instance-scoped credential (mint a session via /handshake with the user's betterbase JWT) or drop the locked-boot shared-secret handshake for standbys and rely on the pool TTL for reaping.

### Adoption test bakes in "leftover = unclaimed": a standby a user is already using is adopted and then stopped+deleted after TTL
**`concierge/src/pool.test.ts:132`** — found by security, robustness, tests
Still valid in the working tree. `adopt()` (concierge/src/pool.ts:142-147) takes any name unconditionally, and the only claimed/unclaimed discriminator (`isUnclaimed` on the machine's own /health) lives in the untested wiring at concierge/src/index.ts:371-372. This test asserts the pool's side of that contract without ever modelling an unlocked machine: it adopts "s3"/"s4" and asserts (test lines 143-149) that an adopted standby is destroyed by TTL — ratifying destruction of a machine whose health the pool never checked. In the real wiring scanLeftovers feeds `pool.adopt()` for every leftover whose 4s probe returned **null** (unreachable) as well as locked ones, so a claimed/unlocked standby that blips (redeploy, DNS, platform hiccup at concierge-restart time, when poolNames is empty again) is adopted as `booting`, promoted to `warm` on the next healthy probe, handed to another user by `/assign` (pool.assign() returns any warm machine), and then 60 min after adoption destroyed via `restInstance` + `container delete` (pool.ts:97-103) — mid-session. No test states "an unlocked leftover is never adopted", so the dangerous path has no protection and the test suite actively legitimizes it.

**Fix**: Model claimed-vs-blank in the harness (locked state or a claim marker) and add a case asserting a claimed standby is never adopted, assigned, or destroyed by the pool.

## 🟡 Suggestion

### The rewritten standby authorization gate and pool wiring have no tests — pool.test.ts injects fakes and never loads index.ts
**`concierge/src/index.ts:215`** — found by robustness, tests
Still valid. `allowedInstance`'s new branch (`POOL_ENABLED && STANDBY_NAME_RE.test(instance) && poolNames.has(instance)`, index.ts:209-216) depends on `poolNames` being populated by the pool's boot/scan callbacks (index.ts:327, 370), and none of that runs in any test: concierge/src contains only table.test.ts and pool.test.ts, and pool.test.ts constructs `createPool` with its own fakes. Consequently the entire wiring this change adds is unprotected: `/assign`'s auth and 404-when-disabled paths (index.ts:253-266), the `table.userWake(got.name)` stop-row clear, the boot argv (`--secret` list, `WADDLE_IDLE_MS`), `urlFor`/`nextName` collision behaviour, `ensureInstance`'s health-first `/wake` (index.ts:170-175, which changes when the zombie stop-deploy dance runs), the new `allowedInstance` branch for the backstop sweep (index.ts:402), and scanLeftovers' adopt/ignore decision. A regression in any of these (e.g. accepting a standby name that is not in `poolNames`, or losing the stop-row clear) ships silently.

**Fix**: Extract the pure name-set/gate logic (name registration, nextName over the set, the allowedInstance predicate) into a module with no server side effects and test it directly: prefix-shaped but unknown names rejected, burned names skipped by nextName, names created by boot/scan accepted.

### No test covers a booting standby that never turns healthy — the code holds it for the whole TTL and blocks its replacement, contradicting pool.ts's documented contract
**`concierge/src/pool.test.ts:80`** — found by tests
pool.ts's header promises "A booting machine that never turns healthy ... is stopped-and-deleted, and replaced on a later tick", but the reaper only fires on `expired || (m.state === "warm" && !health)` (pool.ts:96-103): a `booting` entry that never answers is kept until TTL and, because it still counts in `live().length < cfg.size` (pool.ts:115), no replacement is booted. That path is reachable today, not hypothetical: scanLeftovers explicitly adopts leftovers whose probe returned null — i.e. stopped/dead machines — as `booting` (index.ts:371-372, `h === null || isUnclaimed(h)`). Impact: with WARM_POOL_SIZE set, a single dead leftover after a concierge restart leaves `/assign` answering 404 "no warm standby" for up to an hour while the slot is occupied. The existing tests only cover the warm-+ -unhealthy case (this test) and immediately mark adopted leftovers healthy (line 136), so booting+health:false is never exercised.

**Fix**: Add a case that adopts/boots a machine that never becomes healthy and pin the intended behaviour (prompt destroy + replacement vs. TTL), then align the reaper and the module doc with each other.

### The new locked-boot stop backstop is untested, and its success branch can never fire against a JWKS-configured concierge
**`server/src/index.ts:649`** — found by tests
The block arms the backstop only when `handshakeConcierge(process.env.CONCIERGE_SHARED_SECRET)` resolves true (server/src/index.ts:649-655). `/handshake` requires `verifyExternal` (concierge/src/index.ts:302-305), and with `CONCIERGE_JWKS_URL` set verifyExternal returns false for any non-JWT bearer (concierge/src/index.ts:196-206) — the documented prod posture, and the same posture the concierge warns about at boot. So in prod the standby's shared-secret handshake 401s, `handshakeConcierge` returns false, no stop row is armed and the promised "reaped one idle-window after boot" degrades to the 24h HARD_STOP sweep — exactly the billing hole this change exists to close. Nothing tests either branch: server/src has tests only for approvals/archive/bb-backup/input-map/memory/schedules, there is no test for concierge.ts (`stopBackstopMs`, `handshakeConcierge`) or for the boot path in index.ts, and the failure branch (no accepted bearer) is the one that matters.

**Fix**: Cover the locked-boot path with a unit test around concierge.ts (handshake rejected → assert the backstop is not armed and the failure is logged) and make the block degrade safely — e.g. a local self-stop/expiry when no concierge bearer is accepted — instead of silently no-op'ing.
