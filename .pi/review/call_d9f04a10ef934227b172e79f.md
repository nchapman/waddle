### /handoff/pull k=1 fallback releases the open fire window's escrowed master credential to any shared-secret holder, unbound to the intended machine
**`concierge/src/app.ts:655`** — found by security, robustness
The pull route authenticates only the fleet machine secret (app.ts:644 `requireSecret`), then `legacyCaller` (app.ts:655) is true for ANY instance string that matches neither the user nor standby shape — "x", "", or the sentinel. That bypasses `allowedInstance` entirely (app.ts:656) and falls through to `handoff.singleOpenWindow()` (app.ts:659), which returns the sole armed row with an open release window and hands back its payload via `handoff.release(open)` (app.ts:661) and `{ credential: via.cred, instance: open }` (app.ts:664). The escrow payload is the user's master credential bag — handoff.ts documents it as `{ secret, schedules[], snapshot? }`, and app.ts:686-688 logs it only as `keys` — so this is a full-delegation secret. The comment at app.ts:666-670 assumes "that fire's boot is this puller", but nothing enforces it. Because CONCIERGE_SHARED_SECRET is injected into every managed machine (STANDBY_SECRETS defaults to `CONCIERGE_SHARED_SECRET,TINFOIL_API_KEY` in app.ts:99, and the same `createInstance` builds standbys and user machines), any tenant's compromised machine can poll `POST /handoff/pull {"instance":"x"}` and, whenever exactly one wake window is open (default releaseWindowMs 3 min, handoff.ts), win the one-shot release and receive another user's master secret. That directly violates the stated threat model ("Compromise costs availability and money, never confidentiality") and turns a shared machine token into cross-tenant credential theft. Recommendation: do not release a window to a caller whose presented instance is unverified — bind the release to the fired instance (require the caller to prove the open window's name, or carry a per-machine token in the credential so the pull can be authenticated as that instance) rather than resolving "any single open window" for an anonymous sentinel caller.

**Fix**: Add route tests: arm + markWakeFired for one allowed instance, pull as "unadopted" with the shared secret and assert the credential plus the served instance name; then arm/mark two instances and assert the pull denies (no credential, 404).

### /ws message path performs no authorization — auth is enforced only in onOpen
**`server/src/app.ts:799`** — found by security
The session check for the websocket lives entirely in onOpen (`const authed = requireSession(...)` at line 743; `if (!authed) ws.close(4401, ...)` at 746). onMessage (799-802) does not consult `authed` and forwards every frame straight to handleIntent (line 818), which itself contains no session/lock check anywhere — it parses the frame and acts on `sleep_now`, `preference`, `session_restore`, `history_restore`, `browser_input`, etc. Calling `ws.close(4401)` only initiates a close handshake; a client that pipelines ws frames right after the 101 upgrade (or sends them before the close frame is processed) has those frames delivered to onMessage while the socket tears down. The consequences need no key material: `sleep_now` calls `void sleep("user requested")`, which unconditionally sets `sleeping`, writes a sleep event and calls `process.exit(0)` (lines ~604-651) — an unauthenticated remote shutdown of the enclave. `session_restore` with an arbitrary `jsonl` calls stageSessionJsonl (agent.ts:94) which mkdirs and writeFileSync's attacker-controlled content into DATA_DIR/SESSIONS before any unlock, seeding the agent transcript that will be resumed on the next boot. Tests confirm handleIntent is invoked with no auth context (app.test.ts:119-210), so nothing downstream re-checks.

**Fix**: Defense in depth: re-check the session inside onMessage (guard with the captured `authed` before calling handleIntent), or pass an auth flag into handleIntent and reject unauthenticated frames; also `ws.terminate()` on the unauthenticated branch of onOpen so no frames can be processed after the 4401.

### Defaulting the machine identity to "unadopted" silently breaks the locked-boot stop-backstop and the wake-boot credential pull
**`server/src/concierge.ts:32`** — found by correctness, security, robustness
`let INSTANCE = process.env.WADDLE_INSTANCE ?? UNADOPTED` makes every boot that has not yet adopted a name send the sentinel on every concierge call. Against concierge/src/app.ts that sentinel is refused by the namespace gate at /handshake (line 560) and cannot be adopted from /handshake either (the JWT tier resolves the name from the registry; the secret tier returns the validated name). The locked-boot backstop at server/src/app.ts:1032-1038 fires `handshakeConcierge(CONCIERGE_SHARED_SECRET)` with the sentinel, receives 403, and `renewIdleStop()` is never reached, so the stop row that is supposed to bound a machine nobody unlocks is never written — the machine runs until the concierge's 24h HARD_STOP sweep instead, which is the billing/zombie outcome the backstop exists to prevent. The only way a boot escapes the sentinel is adoption via `adoptInstance()` on a handshake/pull response, so any boot path where the response teaches no name stays identity-less and row-less. Recommendation: keep the sentinel for the wire, but stop treating it as a live identity — e.g. give the locked boot a name before the backstop handshake, or explicitly arm the concierge-side claim-grace/quiet clock for identity-less boots so the backstop is not silently skipped.

**Fix**: Exempt the sentinel from allowedInstance for the shared-secret tier (mirroring the /handoff/pull legacyCaller handling) so the locked-boot handshake can mint and renewIdleStop() can arm the backstop; otherwise drop the UNADOPTED early return and the now-unreachable arming block so the identity-less degrade is stated intent rather than dead code.

### Unauthenticated /probe discloses container capability/runtime fingerprint
**`server/src/app.ts:287`** — found by security
/probe has no requireSession gate (unlike /state, /session, /debug/log at 463-481) and is reachable on the 0.0.0.0 listener before any unlock (app.test.ts:52-59 pins this). It returns uid, effective capability mask (capEff), seccomp mode, NoNewPrivs, the cgroup line from /proc/mounts, dataDirWritable and the Node version. **Fix**: Gate /probe behind requireSession like the other debug endpoints, or drop the capability/seccomp/cgroup fields from the unauthenticated response and keep only the lock-screen-relevant facts.
