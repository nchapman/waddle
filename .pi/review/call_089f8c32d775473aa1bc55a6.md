## 🔴 Critical

### Generation counter restarts at 0 on every unlock while shelf files are immutable, so pushes silently no-op and the shelf goes stale
**`server/src/bb-backup.ts:84`** — found by correctness
setBbGrant resets `gen: -1, lastPushedDigest: null` and index.ts:130 calls it on *every* /unlock. The only other writer of state.gen is pullMachineBackup (:227), which index.ts:136-137 runs only when the sealed log holds nothing but `sleep` events. So whenever the pull is skipped — any later unlock in the same enclave (a browser refresh auto-resumes at App.tsx:408-410 while the enclave is still up, and its log holds real events so the `every(e => e.type === 'sleep')` gate is false), or a restore that failed/timed out — the counter restarts at 0 while the shelf already holds generations 0..M. pushMachineBackup then PUTs deterministic ids derived from that counter (shelfSlotId/shelfManifestId, :192), but betterbase files are immutable: the server maps AlreadyExists to created=false and returns 204 (audit/reviews/03-sync.md:64: 'Upload first creates the object, then commits file metadata. If the object already exists, it returns 204'; the fake server in bb-backup.test.ts encodes the same), and putFile accepts 201/204 as success. Each colliding push therefore returns {pushed:true} and sets lastPushedDigest/state.gen (:197-198) although nothing was written, so for the first M+1 changed pushes after such an unlock *no* new state reaches the shelf while the enclave logs success. The next cold boot restores the newest (stale) manifest, and since this diff deleted client/src/lib/backup.ts and removed the client's history relay, the restore is the only recovery path — everything written since the last real push is lost. The same reuse-of-immutable-id applies to a slot PUT that fails after the server stored it: the retry re-PUTs the same gen id with a different body and then records the new fingerprint in the manifest, so the manifest names bytes it does not describe.

**Fix**: Do not derive the counter from a pull that can be skipped: discover the shelf's high-water mark (the same HEAD walk) before the first push of every session, or persist the counter outside the grant. Also treat a repeated PUT as failure (HEAD+digest verify) instead of success.

### Shelf generation resets on every unlock, so checkpoints re-PUT immutable ids and silently never reach the shelf (session lost on next cold boot)
**`server/src/bb-backup.ts:192`** — found by robustness
`setBbGrant` arms the grant with a fresh counter every unlock (`state = { grant, dekWrapKey, lastPushedDigest: null, gen: -1 }`, line 84), and `pushMachineBackup` derives its target from that counter (`const gen = state.gen + 1;` line 192) through deterministic name-based ids (`shelfSlotId`/`shelfManifestId` → `fileUuid("waddle-shelf-v1:…:${gen}")`). The counter is carried forward in exactly one place — `pullMachineBackup` (line 231) — and index.ts runs the pull only when the sealed log holds nothing but `sleep` events (index.ts:135). So on any reload/auto-resume with a non-empty log (the client auto-resumes on every page load), and on every path where the restore fails or hits its 60 s timeout, `gen` restarts at -1. Files are write-once: the module header and the test's mock both state that a repeat PUT is a silent no-op, and `putFile` treats 201/204 as success without verifying anything. The second session therefore re-PUTs generations 0..k-1 onto ids that already exist, the bytes are dropped, and yet `state.lastPushedDigest`/`state.gen` are advanced and the log prints `pushed: true`. Because pushes are change-gated, a session normally produces only a handful of generations (fewer than the previous session's total), so its work — including the final pre-sleep checkpoint in `sleep()` — never lands on the shelf; the next cold boot's `pullMachineBackup` walks to the highest existing manifest (the earlier session's) and restores stale state, silently losing everything since. If the real sync server answers 409 for a duplicate id instead of a no-op, the same collision makes every push after the first session fail outright.

**Fix**: Continue the generation from the shelf instead of resetting it: probe the latest manifest generation when the grant is armed (or persist it across unlocks), and treat a write-once no-op/409 as a failed checkpoint (HEAD-verify the write, or key the slot id off the archive digest) so `pushed: true` means the bytes are actually stored.

## 🟠 Important

### `replayed` is set only by a replay_done that the phase guard can discard, leaving the UI stuck on "replaying history…"
**`client/src/App.tsx:225`** — found by correctness, security, robustness
Still present in the current tree. `replayed` has one writer, the `replay_done` branch at lines 223-226, and it returns `s` unchanged whenever `s.phase !== "chat"` — while the reducer's own guard at line 231 drops every other event in the same window. `doUnlock` opens the websocket at line 358 (the gateway sends hello + backlog + `replay_done` as soon as the upgrade completes, index.ts:342-344) but only commits `phase: "chat"` after the awaited `getState` round trip at line 386, and it explicitly sets `replayed: false` when the restored log holds history (line 398). If the backlog/replay_done tasks are processed in that window they are discarded, so the surface never leaves the `replaying history…` branch and the composer is never mounted — dead until a manual reload. There is no timeout, retry or second source for the flag. This change makes the branch more common, since a restored machine now always seeds from the log (`historyEvents.length > 0` → `replayed: false`) instead of seeding from the client's own snapshot.

**Fix**: Set the flag before/independently of the phase guard: record the replay_done in a ref (or set replayed regardless of phase) and have doUnlock seed `replayed` from it, so the initial state and the late event cannot both end up false.

### Client-side persistence removed entirely: signed-out users (or any failed shelf restore) boot with an empty history and no way to re-seed it
**`client/src/App.tsx:386`** — found by robustness
This diff deletes client/src/lib/backup.ts and removes both client persistence paths: the per-message `saveSnapshot` (localStorage) and the unlock-time pull/relay (`readSnapshot`/`loadSnapshot` → `history_restore`/`session_restore`). The only remaining restore is the enclave's own shelf pull, which requires a bb grant (signed-in), runs only when the sealed log holds nothing but `sleep` events (index.ts:135), and is bounded by `withTimeout(…, 60_000)` — a failure just logs "machine restore failed — booting fresh" (index.ts:141) and the process continues. When the pull does not run, the `historyEvents.length === 0` branch (lines 385-389) leaves `seed = []` and the code that used to relay the client's own copy back into the sealed log is gone, so nothing can recover it. Per the file's own comment the enclave scratch is wiped on sleep ("Sleep wipes the scratch: a post-wake log may hold only bookkeeping"), so a signed-out unlock — or one transient shelf failure/timeout at wake — silently presents an empty conversation as if it were the machine's state, with the history unrecoverable.

**Fix**: Keep a client-side fallback for the no-grant and restore-failed cases (the device snapshot plus the `history_restore`/`session_restore` relay, which the server still implements), or surface the restore failure to the client so it can re-send its own copy instead of silently seeding nothing.

### Local-endpoint scheme inference is asymmetric with the library's, so a 127.0.0.1 dev domain discovers over https and silently disables backups
**`client/src/lib/bb-grant.ts:40`** — found by correctness, robustness
`resolveSyncEndpoint` performs a bare `await fetch(`${scheme}://${domain}/.well-known/betterbase`)` (line 41) with no `AbortSignal`/timeout; the surrounding `.catch` (lines 47-51) only handles a rejection. `doUnlock` awaits this value *before* calling `unlock()` (App.tsx:340-348), so a discovery host that accepts the connection and never answers (black-holed DNS/proxy, wedged service) leaves the promise pending forever: `unlock()`, `getState()` and the websocket connect are never reached and the UI sits in the `unlocking` phase with no error and no timeout to escape it. The same pattern (unbounded `client.fetch`) exists for the unlock/state calls in client/src/lib/session.ts, so there is no outer bound either.

**Fix**: Reuse the library's scheme rule (strip the port, accept localhost/127.0.0.1/*.localhost) and surface a visible warning when the grant cannot be built for a signed-in user.

### Chat stream has no terminal path when the socket is gone: the turn can hang forever with no error

Still valid, unchanged by this diff. The stream returned by sendMessages is closed only from the tap on `run_settled`/`error` or from options.abortSignal; nothing ties the WebSocket lifecycle to it (ws.ts:35 `socket.onclose = onClose`; App.tsx's close callback only flips `connected: false`, and transport.attach is never re-run). ### Eval enrolls a throwaway secret on a fresh volume, permanently locking the browser (and the eval's own reruns) out of that volume
**`scripts/eval-tools.mjs:17`** — found by correctness, security, robustness
Still valid: `const secret = crypto.randomBytes(64).toString("base64")` (line 17) is POSTed to /unlock (lines 27-33) under the premise 'volume fresh or any state; script enrolls its own secret' (line 9). Enrolment is trust-on-first-use and verifier.bin persists on the compose volume (compose.yaml DATA_DIR=/data; state.ts VERIFIER_FILE = <DATA_DIR>/verifier.bin), so on a fresh volume this call enrols the script's throwaway secret, after which Lock.unlock rejects every other secret with 401 'wrong secret' and never re-enrols. The dev browser's getSecret() generates a different secret, so it is refused on every attempt — including after 'forget secret & retry', which only mints another secret — and the only recovery is `docker compose down -v`. The eval itself cannot be re-run against that volume either.

**Fix**: Accept a secret from the environment (defaulting to the browser's stored secret) and treat the 401 'wrong secret' response as a hard error that explains the volume is already enrolled.

### Fingerprint exclude regexes are anchored with a './' prefix the walk never produces, so no exclude ever applies
**`server/src/archive.ts:42`** — found by correctness, robustness, tests
EXCLUDES entries are prefixed for tar (`.map(e => \`./${e}\`)`, :30) and EXCLUDE_RE is built from those same strings anchored with '^' — e.g. ^\./browser/[^/]*/Cache(/|$). machineFingerprint's walk builds childRel as `${rel}/${name.name}` starting from rel = "" (:51, :63), producing '/browser/Default/Cache', '/tmp', '/home/.cache' — paths that start with '/' and never match the '^./' anchors. So `tar` excludes caches/scratch correctly (as archive.test.ts asserts) while the fingerprint hashes them. Consequences: (1) the digest gate, whose entire purpose is 'unchanged machine → skip the re-tar + re-PUT', fires on regenerable churn (Chromium Cache/GPUCache, tmp, home/.cache) that is not in the archive, so an identical archived state still pushes a fresh generation every 10-minute tick, and since ids are gen-derived and files are never deleted ('no delete route in the files API', :49) the shelf grows without bound; (2) pullMachineBackup sets lastPushedDigest = manifest.digest (:226), a fingerprint computed over cache files the archive never contained, so after a restore the recomputed fingerprint can never match — an immediate redundant generation on every boot, contradicting the comment 'don't re-push what we just pulled'.

**Fix**: Build EXCLUDE_RE from the un-prefixed patterns (or normalise childRel to './<rel>') and add a test that asserts machineFingerprint ignores a change under browser/*/Cache and tmp.

### restoreArchive wipes the working directory before extracting, so a failed untar destroys the machine with only a log warning
**`server/src/archive.ts:110`** — found by robustness
After validating the tar listing, `restoreArchive` deletes every entry of `DATA_DIR` (lines 110-112) and only then runs `tar -xzf` (line 113). Any extraction failure — the tmpfs filling up (the archive can be up to the 1 GiB `maxBuffer`), a member tar refuses, a body that lists but does not extract — throws *after* the wipe, so the sealed log, `verifier.bin` and the workspace are gone and only a partially-extracted tree remains. The caller swallows it (`app.log.warn({ err: … }, "machine restore failed — booting fresh")`, index.ts:141-143) and keeps going with the pre-wipe in-memory `EventLog`, whose directory no longer exists (log.ts creates it only in the constructor), so the next `log?.append` from the socket handler hits `appendFileSync` ENOENT; a partially written `log/events.jsonl` makes the next `new EventLog` throw inside `/unlock` and the user is served an empty history. The wipe is also unrecoverable from the client because the snapshot fallback was removed (see the App.tsx finding).

**Fix**: Make the swap atomic: extract into a sibling staging directory (validating the tar the same way), and only after a successful extraction remove the old tree and rename the staged one into place — or at minimum do not wipe until the extract has been proven to succeed.

### Enclave holds a frozen one-hour bearer token with no refresh path, so periodic backups start failing silently mid-session
**`server/src/bb-backup.ts:130`** — found by correctness, security
This change makes the enclave itself an HTTP client. /unlock takes `bb` straight off the request body (server/src/index.ts:120-133) and hands it to setBbGrant (bb-backup.ts:78), which stores `endpoint`, `token`, `spaceId` and `anchorId` verbatim with no validation. Every shelf call then builds its URL by raw interpolation — `${g.endpoint}/spaces/${g.spaceId}/files/${fileId}` at bb-backup.ts:127 (PUT), :148 (GET) and :166 (HEAD) — and attaches `Authorization: Bearer ${g.token}`, `X-Record-ID: g.anchorId` and an attacker-sized body. Nothing constrains the scheme, the host, or the shape of spaceId (not checked to be a UUID, not escaped, so `/`, `..`, `?` retarget the path). Any caller who can unlock controls this: the secret, or first enrolment on a fresh volume (Lock.unlock enrols trust-on-first-use whenever verifier.bin is absent — state.ts:70-78, and `storage === "memory"` accepts any 64-byte secret). Consequence: the enclave becomes an authenticated request proxy from inside its network namespace to loopback, link-local (169.254.169.254) or sibling containers, with a blind PUT primitive against internal HTTP endpoints. Second path: the endpoint a *legitimate* client hands over is itself attacker-reachable — client/src/lib/bb-grant.ts:23 reads `waddle.bb-sync-endpoint` from localStorage and returns it verbatim (and VITE_BETTERBASE_SYNC_URL_ENCLAVE overrides it), so poisoning that cache sends the user's betterbase sync token (now scoped `files`, client/src/main.tsx:17) to the poisoned host on every push.

**Fix**: Either bound/refresh the credential (a small authenticated endpoint or re-unlock on 401 that re-arms the grant) or fail loudly when pushes start returning 401 and stop claiming backups are active.

### New GET /archive hands out the whole unsealed machine — Chromium cookies/logins, plaintext session transcript, workspace — to any session bearer
**`server/src/index.ts:100`** — found by security, tests
The route (index.ts:100-115) is gated only by requireSession and returns createArchive().body raw. That blob is the tar.gz of DATA_DIR — archive.ts's own header names 'sealed log, pi session transcripts, workspace files, the Chromium profile (logins ride with it)', and archive.test.ts:24-26 seeds `browser/Default/Cookies` to prove the profile rides it. The pi transcript is plaintext (agent.ts:28/87-90 write sessions/*.jsonl unsealed) and is exactly the payload the rest of this change insists on sealing before it travels (client/src/App.tsx comment and bb-backup.ts:1-21: 'the client is a pipe — it never opens the blob'). Nothing seals the HTTP response, in contrast to the shelf path, where the same bytes are sealed under HKDF(secret,'bb-dek') before they leave (bb-backup.ts:131-141). The endpoint also has no consumer: `grep archive client/src` returns no matches and this diff deleted the client's push/pull, so it is purely new surface. A leaked or replayed session bearer — 12 h TTL (state.ts SESSION_TTL_MS), also passed in the /ws query string (index.ts:274) which Fastify's request logger records — escalates from 'read the event log' to 'download every cookie, saved login and file the user's browser held'. EHBP encrypts the hop, but transport encryption is not the envelope the design relies on.

**Fix**: Delete the route — the enclave shelves itself now (index.ts:264-274), so no client needs it. If it must stay, seal the archive under the session secret before returning it, and stop serving the browser profile through an unscoped fetch.

### withTimeout around pullMachineBackup does not cancel it, so a late restore wipes a live machine's DATA_DIR after unlock returned
**`server/src/index.ts:137`** — found by correctness
withTimeout (index.ts:20-26) rejects after 60 s but leaves the wrapped promise running, and pullMachineBackup has no abort path. Its last act is restoreArchive(tar), which deletes every entry of DATA_DIR and untars over it (archive.ts:112-119). If the pull is slower than 60 s — the walk can issue up to 4096 sequential HEADs, and no fetch here sets a timeout (undici's default headers/body timeouts are minutes) — the unlock response has already been sent: the client connects, the agent boots and appends to the sealed log, Chromium starts writing its profile, and then the abandoned pull lands, wiping DATA_DIR out from under the live process (appendFileSync in log.ts:38 recreates the unlinked file, so events written after the sweep are lost to the restored log) and reassigning state.lastPushedDigest/state.gen (:226-227) from the stale manifest. The fresh-boot precondition the function documents ('only ever called onto a fresh enclave') is re-checked only before the 60 s window.

**Fix**: Make the restore cancellable/conditional: pass an AbortSignal into the file fetches and re-verify the 'nothing but sleep events' precondition immediately before restoreArchive (e.g. hand it a generation token that is invalidated when the unlock returns).

### Eval harness resolves only on close/90 s timeout, so every task races the clock

### Shelf push/pull fetches have no timeout, and the periodic/initial pushes are unbounded (withTimeout does not cancel)
**`server/src/bb-backup.ts:145`** — found by robustness
`putFile` (line 145), `getFile` (line 166) and `headFile` (line 187) call `fetch` with no `AbortSignal`/timeout. Only the sleep-time push is bounded (`withTimeout(pushMachineBackup(), 30_000, …)`, index.ts:239), and `withTimeout` does not cancel the underlying promise — a timed-out request keeps running and can still mutate `state.gen`/`state.lastPushedDigest` after the timeout fired. The initial push after unlock and the 10-minute interval (index.ts:259-264) are not bounded at all, and the "retrying in 30s" recovery is a `.catch` (index.ts:153-160) that a *hung* request never triggers, so one stalled connection leaves the promise pending forever while each later tick starts another overlapping push against the same generation id.

**Fix**: Pass an `AbortSignal.timeout(...)` to every shelf fetch, guard the interval against an in-flight push (single-flight flag), and make `withTimeout` abort the underlying request rather than only rejecting its wrapper.
