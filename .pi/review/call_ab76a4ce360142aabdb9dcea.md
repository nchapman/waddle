## 🟠 Important

### Untrusted instance name interpolated into outbound URL (SSRF from the concierge)
**`concierge/src/index.ts:150`** — found by security
`instanceHealthy` builds `https://${instance}.${DOMAIN_BASE}/health` from the raw instance string, and `ensureInstance` (line 160) is reached from POST /wake with `req.body.instance` after nothing more than `allowedInstance` (line 282 → 287). Since that check is only `startsWith(STANDBY_PREFIX)`, the string may contain `.`, `/`, `@`, `:`, `?` — e.g. `{"instance":"waddle-standby-x.attacker.tld/"}` yields `https://waddle-standby-x.attacker.tld/.<DOMAIN_BASE>/health` (host escapes the operator zone) and `{"instance":"waddle-standby-host:8443/"}` sets the port, so any JWT holder turns the concierge — a TEE that also holds TINFOIL_ADMIN_KEY/CONCIER_SHARED_SECRET and talks to the platform API — into an HTTP client for destinations of their choosing. The result is observable as an oracle: on `res.ok` ensureInstance returns `already running: <instance>` in the 202 body, otherwise `startInstance`'s CLI error is returned (502), so an attacker learns which probed host:port answers 2xx on /health over HTTPS — network reconnaissance of names inside DOMAIN_BASE (e.g. `waddle-standby-<internal>.DOMAIN_BASE`) and an outbound beacon with the concierge's egress identity. Before this diff the probe did not exist and the only names reaching the platform verbs came from the operator-set ALLOWED list.

**Fix**: Validate the name before use (`/^(?:<escaped STANDBY_PREFIX>\d+|<allowlisted name>)$/`, reject anything containing `/`, `@`, `:`, `?`, `#`, whitespace) and construct the probe from a validated hostname only — e.g. `new URL('https://' + encodeURIComponent-checked-name + '.' + DOMAIN_BASE + '/health')` after the regex check, failing closed on a miss.

### Standby-prefix bypass defeats the ALLOWED instance allowlist for any authenticated caller
**`concierge/src/index.ts:202`** — found by security, tests
The new clause `ALLOWED.has(instance) || (POOL_ENABLED && instance.startsWith(STANDBY_PREFIX))` makes `allowedInstance` the gate for /wake (line 282), /handshake (line 253), /timer (via `authorize`, line 209) and the backstop sweep (line 356) — the exact places the file documents as "Scoped to ALLOWED — never the whole docker host or platform account" (and ALLOWED's comment: "Anything else on the platform … is invisible"). The clause admits any string whose first characters are the prefix (default `waddle-standby-`); no charset/length check and no membership check against the pool's own `takenNames`. Auth is only `verifyExternal` (line 187), which for a JWKS concierge accepts *any* betterbase JWT for the configured issuer/audience — no per-user, per-instance or ownership binding — so every user of the product can name instances the operator never allowlisted: POST /wake {instance:"waddle-standby-<anything>"} is passed verbatim to `tinfoil container deploy` (startInstance, line 89) and to `restInstance`/`container delete` (destroy, line 315), and POST /timer {instance:"waddle-standby-X", action:"stop"} arms a stop that fires `tinfoil container stop X`. Names are guessable (`${STANDBY_PREFIX}${i}`), so warm standbys can be stopped/claimed by anyone, and because `table.entryFor()` creates a Map entry plus an armed setTimeout chain per unseen name (table.ts:31, 72), the widened namespace also removes the previous bound on table size: a token holder can create unbounded entries/timers with distinct standby-prefixed names (memory/timer exhaustion on the always-on concierge).

**Fix**: Keep the strict allowlist: have the pool register its names in a concierge-owned set (the existing `takenNames`) and accept an instance only if `ALLOWED.has(instance) || poolNames.has(instance)`, i.e. names this process actually created/seeded; additionally require the name to match `^${STANDBY_PREFIX}\d+$` so no URL/CLI metacharacters can ride along.

### Standbys that survive a concierge restart are neither adopted nor reaped — they bill forever
**`concierge/src/index.ts:337`** — found by robustness
The boot seed only copies platform names into the `takenNames` set (lines 335-341); they are never inserted into the pool's `machines` map, and the pool's reap loop iterates only tracked machines (pool.ts:59-79), so `pool.tick()` can never destroy them. Nothing else covers them either: the backstop sweep requires `table.entry(name)` and a never-unlocked standby never handshakes (see the server finding above), so it has no entry; and `nextName` merely skips the name. These leftovers run and bill indefinitely, directly contradicting pool.ts's stated invariant ('Unclaimed standbys are dropped after a TTL so idle time can't burn an unbounded budget'), and the seed comment itself acknowledges 'our memory is wiped on reboot — leftover standbys exist'. Secondary consequence of the same cache: `takenNames.add(name)` happens only after a successful `container create` (line 316), so if the seed fails (the `catch` at line 340 warns exactly this) while a leftover already occupies the first free name, every tick re-picks that same name, the create throws 'already exists', the entry is deleted from `machines` (pool.ts:93-95), and the pool livelocks on one failing boot per tick while the leftover is never destroyed.

**Fix**: Adopt seeded standby names as tracked machines (state `warm`/`booting` with `createdAt` set so the TTL applies) or destroy any standby-prefixed instance this process did not create; and mark an attempted name as taken (or use a random suffix) when `create` fails, so a name collision cannot loop forever.

### A failed destroy makes the pool forget the machine, so the orphan is never retried or reaped
**`concierge/src/pool.ts:63`** — found by correctness, tests
Both reap branches do `machines.delete(m.name)` and only then `await deps.destroy(m.name).catch(...)` (lines 63-64 and 73-74). If `destroy` rejects — realistic here, since index.ts's `destroy` awaits `restInstance`, which rethrows every tinfoil error except "is not running"/"already" — the machine is already gone from `machines`, so it is never retried by any later tick and the container keeps running. Nothing else reaps it: the backstop sweep skips names with no table entry (`if (!e) continue`, index.ts:361) and an unclaimed standby never handshakes, and the server-side locked-boot backstop that would have stopped it is unreachable (see server/src/index.ts:647). Every harness in pool.test.ts has `destroy: async (n) => { h.destroyed.push(n); ... }` that always resolves, so this failure path is asserted nowhere; the tests only prove the happy path.

**Fix**: Only delete the entry after destroy succeeds (or keep a `destroying` state and retry on later ticks), so a failed destroy is retried instead of silently orphaning the machine.

### Locked-boot stop backstop can never arm: `conciergeActive()` is always false at module-init time
**`server/src/index.ts:647`** — found by correctness, robustness, tests
The new block is the only thing that hands a locked boot to the concierge (comment: "handshake with the shared secret already in env and arm the stop backstop, so the concierge reaps it one idle-window after boot"), but it is guarded by `!lock.unlocked && conciergeActive()`. `conciergeActive()` is `sessionToken !== null` (server/src/concierge.ts:59) and `sessionToken` is set only by `handshakeConcierge`. The only other call sites are (a) inside the `/unlock` route (index.ts:241-242), which runs only after `lock.unlock(...)` has already set `lock.unlocked = true` (state.ts:89), and (b) the autonomous-boot branch (index.ts:630), which is `void handshakeConcierge(...)` and therefore cannot resolve before this synchronous module-level check. No request can have been served either, because `await app.listen(...)` is the last line (index.ts:659). So whenever `!lock.unlocked` is true, `conciergeActive()` is false and the branch is dead code. Consequence: a machine that boots/stays locked (exactly the wake-boot and the pool standbys handed out by /assign that nobody unlocks — the pool even removes claimed machines from its own TTL reaping, pool.ts:50/104) never handshakes, so it has no table entry; the concierge's backstop sweep skips any instance without an entry (`if (!e) continue;`, index.ts ~line 355) and the machine's own idle gate bails out on `!lock.unlocked` (index.ts:443, "A locked machine ... is the concierge stop row's problem"). The promised reap never happens and the machine burns compute until a human unlocks it.

**Fix**: Drop the `conciergeActive()` conjunct so a locked boot always attempts the shared-secret handshake (e.g. `if (!lock.unlocked) { ... }`). Take care that `handshakeConcierge` unconditionally assigns `sessionToken = r?.session_token ?? null` (concierge.ts:55), so only re-handshake when there is no live session, or change it not to clobber a good token on failure.

## 🟡 Suggestion

### `/assign` body is used unvalidated, and there is no fallback once `activeEnclave` is switched
**`client/src/App.tsx:264`** — found by robustness
`activeEnclave = m.url` trusts the raw JSON body: a 2xx response whose body lacks `url` (or is a non-object that still parses) sets `activeEnclave` to `undefined`, and every later request — including the immediately re-entered `run()` and the `onRetry`/`onForget` buttons that call `run()` — builds `undefined/health` / passes `undefined` into `verifyEnclave`. Because `autoWokeRef.current` was already set to true before the assignment, the unreachable-probe branch can never run again, so the session cannot recover to the primary; only the Wake button (`wakeCore`, which resets `activeEnclave = ENCLAVE_URL`) escapes. Nothing validates the URL shape (scheme/host) either.

**Fix**: Validate before switching: `if (typeof m?.url === "string" && /^https:\/\//.test(m.url))` → assign and re-run, else fall through to `wakeCore`; and reset `activeEnclave = ENCLAVE_URL` when the standby fails attestation so retries can reach the primary.

### nextName() only avoids names it has successfully created, so a colliding name wedges the pool forever
**`concierge/src/index.ts:324`** — found by correctness
`nextName()` scans only `takenNames`, which is populated from `listInstances()` at boot (index.ts:337) and appended after a *successful* `container create` (index.ts:316). It is never told about a name that exists on the platform but is missing from the set, and the pool's fill step deletes the machine record and re-reads `nextName()` on the next tick when boot throws (pool.ts:88-96). The code itself anticipates the gap ("pool seed failed — first boot may collide", index.ts:341): if `listInstances()` fails at boot while a leftover standby exists, every fill attempt deterministically picks the same colliding name, `container create` fails, the record is deleted, and the next tick tries the identical name again — the pool never boots a replacement (until the concierge restarts with a working seed).

**Fix**: Make name selection failure-aware: record the attempted name in `takenNames` before/after a failed create (or probe the platform), so a collision moves on to the next index instead of looping on the same name.

### Numeric pool env vars are unvalidated; a malformed POOL_TICK_MS turns the tick into a ~1ms hot loop
**`concierge/src/index.ts:342`** — found by robustness
`Number(process.env.POOL_TICK_MS ?? 30_000)` evaluates to NaN for values such as "30s" or an empty string; Node coerces a delay that fails `>= 1 && <= 2**31-1` (NaN included) to 1 ms, so while POOL_ENABLED the maintenance pass would fire roughly every millisecond, starting overlapping ticks that each issue 4-second `/health` probes (`instanceHealthy`) and `tinfoil` execs. The same pattern at line 60 (`STANDBY_TTL_MS`) makes `deps.now() - m.createdAt > cfg.ttlMs` always false, silently disabling the TTL/budget cap the pool exists to enforce, and `WARM_POOL_SIZE` NaN silently disables the pool with no warning because the guard at line 76 is `POOL_SIZE > 0`.

**Fix**: Parse with `Number.isFinite` plus a sane floor (e.g. `Math.max(1_000, Number(...))`), warn on invalid values, and disable/clamp rather than accept NaN.

### Claimed machines are never evicted — the pool map (and `/health`) grows without bound
**`concierge/src/pool.ts:103`** — found by robustness
`assign()` mutates `warm.state = "claimed"` but never deletes the entry, and no other code path removes claimed entries — `live()` only filters them out of iteration (pool.ts:55). So every assignment permanently retains an entry, `tracked()` returns all of them, and the `/health` payload published at concierge/src/index.ts:232 grows with every user; the corresponding name also stays in `takenNames` (index.ts:316), so names advance monotonically across the process lifetime. Per-item cost is small, but the concierge is long-lived and the pool test's stated intent ('the pool forgot it at claim time') does not match the implementation.

**Fix**: Delete the claimed entry from `machines` (and release its name from `takenNames`) at claim time, or bound the claimed set with its own expiry.
