### inWorkspace fails open: `..` is never resolved and an empty/absent path counts as inside the workspace, so write/edit auto-approve outside the workspace
**`server/src/approvals.ts:56`** — found by correctness, security, robustness
The diff's only write-side control is `needsApproval()` line 49 (`return !inWorkspace(String(input.path ?? ""))`), whose stated rule is 'write/edit: auto-allow when the target stays inside the workspace'. `inWorkspace()` (lines 54-58) builds `${WORKSPACE}/workspace/${p}` and only collapses duplicate slashes (`replaceAll(/\/+/g, "/")`); it never resolves `..` or symlinks, so any relative path traverses out while still matching the `startsWith('/data/workspace/')` prefix test. pi's own tools do resolve it: `resolveToCwd` → `resolvePath` → `nodeResolvePath` (dist/utils/paths.js:83-87, dist/core/tools/path-utils.js, dist/core/tools/write.js:36) is `path.resolve` against cwd `/data/workspace` (agent.ts:88-101 sets cwd: WORKSPACE). So a call `write({ path: "../log/events.jsonl" })` is auto-allowed by the gate yet lands on the real log file (`server/src/log.ts:11`, `join(DATA_DIR, "log", "events.jsonl")`), truncating the entire sealed history; likewise `../pi-agent/models.json` / `auth.json` in `/data` are overwritable as root with no human prompt — defeating the ask-gate that bash is gated to protect. Trigger is realistic: `read` is auto-allowed (approvals.ts:51) and runs unrestricted, so content the agent reads inside the workspace flows into its context and a prompt-injected instruction to write via `..` needs no approval. Secondary defect in the same expression: `String(input.path ?? "")` yields `""` for a missing/renamed path key, and `""` also passes `inWorkspace` (the built string `/data/workspace/` starts with `/data/workspace/`), so any write/edit whose path argument is not literally named `path` is auto-approved too (pi renderers accept `file_path` as an alias, per dist/core/tools/renderers/write.js:87).

**Fix**: Canonicalize before comparing — resolve against the workspace root (`path.resolve(root, p)`) and compare with `resolved === root || resolved.startsWith(root + path.sep)` — and reject empty/non-string paths (return them as "needs approval") instead of defaulting them into the allow branch; consider re-checking the resolved realpath to close symlink escapes.

### Socket close wipes the process-wide sink, so an in-flight turn's assistant reply is never written to the log (silent history loss)
**`server/src/index.ts:165`** — found by correctness, robustness
The sink is a single process-wide object (agent.ts `const sink` + `setSink` mutating it in place) and it is now the ONLY writer of assistant finals: index.ts:183-187 `onAssistantFinal: (text) => { ... log?.append({...evt}); send(evt); }`. The socket close handler at index.ts:163-167 calls `void setSink({})` unconditionally, and agent.ts `setSink` deletes every key before assigning `{}`, so after a close `sink.onAssistantFinal` is undefined and the final is dropped. Trigger: any client disconnect while a turn is in flight — e.g. the user reloads the page (or the tab is backgrounded and the socket drops) after sending a message; the server keeps running `session.prompt`, but the model's answer never reaches `log?.append`, so it is absent from `/state`, from the gateway backlog, from `initialMessages`, and from the device snapshot (`saveSnapshot` is only called from the client's `message` handler). Before this diff the assistant message was appended in the socket handler's continuation (`await chat(...)` then `log?.append({...assistantEvent})`), i.e. it was persisted regardless of connection state — this diff moves that write onto the connection-scoped sink and thereby introduces the loss. Second consequence of the same unconditional wipe: `denyAllPending()` runs even when other sockets are still connected (`sockets` is a `Set`, and `scripts/eval-tools.mjs` connects its own socket alongside the browser), so closing any one client auto-denies a pending approval another client is still looking at, and the surviving client goes silent because the sink was cleared out from under it (no deltas, no `run_settled`, so its transport stream never closes).

**Fix**: Only reset the sink / deny pending approvals when no clients remain (`if (sockets.size === 0) { void setSink({}); denyAllPending(); }`), and decouple transcript persistence from the live connection: keep a boot-scoped subscriber (or have index.ts append the assistant final in the `await chat(...)` continuation as before) so a completed turn is always written to the log even with no socket attached.

### `replayed` is set only by a replay_done that the phase guard can discard, leaving the UI stuck on "replaying history…"
**`client/src/App.tsx:126`** — found by correctness
`replayed` has exactly one writer: `if (event.type === "replay_done") return { ...s, replayed: true };` (App.tsx:126), reached only through `transport.dispatch` → `onServerEvent`, whose first statement is `if (s.phase !== "chat") return s;` (App.tsx:102-103), which drops every event while the phase is anything else. In `doUnlock` the WebSocket is opened (App.tsx:155-161) before the state is committed to `chat`: between `setState({ phase: "unlocking" })` and the final `setState({ phase: "chat", ..., replayed: false })` there are two awaited round trips — `await loadSnapshot(...)` and `await getState(...)` (App.tsx:167-168) — and the gateway sends hello + backlog + replay_done synchronously as soon as the upgrade completes (index.ts:189-192). Any ordering in which the backlog/replay_done tasks are processed inside that window drops them: `state.messages` stays empty and `replayed` stays false forever, the render falls to the `state.replayed ? ... : <p>replaying history…</p>` branch (App.tsx:316, 397) and the composer/send button (which now live inside ChatSurface) are never mounted, so the app is dead until a manual reload. There is no timeout, retry, or second source for this flag, and nothing else re-replays after phase `chat` is committed.

**Fix**: Do not gate the surface on an event that the same reducer can discard: commit the chat state before opening the socket (or move connectChat after the awaits), buffer/inspect events while `phase === "unlocking"` instead of dropping them, and/or have `connectChat` (which already tracks the replay boundary locally) hand the app a `replayed` signal or callback when the backlog ends.

### Chat stream has no terminal path when the socket is gone: the turn can hang forever with no error
**`client/src/lib/waddle-transport.ts:112`** — found by robustness
The stream returned by `sendMessages` is closed only from the tap on `run_settled` / `error` events, or from `options.abortSignal`. Nothing ties the WebSocket lifecycle to it: ws.ts:35 `socket.onclose = onClose` and App.tsx's onClose callback only flip `connected: false` — `transport.attach` is never re-run and no stream is errored. So in the state the UI already advertises ("⚠️ disconnected — reload to re-replay"), `sendIntent` still points at the dead socket; `WebSocket.send()` on a CLOSED socket silently discards the frame, the server never sees the message, no `error` or `run_settled` ever arrives, and the stream stays open indefinitely. `controller.close()` never runs, so useChat's status stays `streaming`, the assistant bubble is stuck mid-turn and (assistant-ui keeps the composer disabled while a run is active) the user cannot send anything else — a silent, unrecoverable dead-end that only a page reload clears. The same happens for any missed terminal event (server crash/restart mid-turn). There is no timeout anywhere in the client transport path (grep confirms no `setTimeout`/`AbortSignal.timeout` in ws.ts, waddle-transport.ts or ChatSurface.tsx).

**Fix**: Give the stream a terminal path independent of the server: wire the chat connection's close/error to `finish()`/`controller.error(...)`, and/or arm a bounded timeout (cleared in `finish`) that enqueues an `error` chunk and closes. Also guard the send: if no live connection is attached, immediately enqueue an error chunk instead of leaving the stream open.

### Eval enrolls a throwaway secret on a fresh volume, permanently locking the browser (and the eval's own reruns) out of that volume
**`scripts/eval-tools.mjs:17`** — found by correctness
The script generates `const secret = crypto.randomBytes(64).toString("base64")` (line 17) and POSTs it to `/unlock` (lines 27-33) under the documented premise "volume fresh or any state; script enrolls its own secret" (line 9). But the server's enrollment is trust-on-first-use and the verifier file persists on the compose volume (`compose.yaml` DATA_DIR=/data backed by the `waddle-data` volume; state.ts VERIFIER_FILE = `<DATA_DIR>/verifier.bin`): on a fresh volume this call enrolls the script's secret, and thereafter `Lock.unlock` (server/src/state.ts:70-78) rejects every other secret with 401 "wrong secret" and never re-enrolls. ### Eval harness resolves only on close/90s timeout, so every task races the clock
**`scripts/eval-tools.mjs:63`** — found by tests
ask() resolves only via ws.onclose (line 62) or the 90s setTimeout (line 63); the success/failure signal is `final !== null ? done() : reject(new Error("timeout"))`. But the gateway never closes the socket after a turn settles — it emits `run_settled` and leaves the connection open (socket close happens only on sleep, server/src/index.ts). So ws.onclose never fires during the suite and every task blocks the full 90s (5 tasks ~= 7.5 min), and a correct run whose final assistant message lands just after the window is recorded as `err: "timeout"` with `pass: false` even though the tool side effects succeeded (the `check()` file assertions run only inside the try after the await). The regression suite therefore has a wall-clock race baked into its pass/fail, and the timeout timer is never cleared (leaks a 90s handle per task).

**Fix**: Terminate on the terminal event instead of the clock: resolve when `run_settled` arrives (or when the assistant `message` for the turn is seen), clear the setTimeout on resolve/reject, and keep the timeout only as a failure backstop.

### Eval harness uses fixed waits instead of waiting for the condition, and never clears its 90 s timer
**`scripts/eval-tools.mjs:116`** — found by robustness
Line 116 sleeps a flat 500 ms after `ask()` resolves and *then* reads the file back with `docker exec`, so the pass/fail verdict depends on wall-clock timing rather than on the observed tool outcome (the harness already receives `tool_end`/`run_settled`, which is the condition to wait for). On a loaded machine a buffered/slow write turns a correct run into a FAIL. On the other side, the per-question `setTimeout(..., 90_000)` at line 63 is never cleared and the `WebSocket` is only closed in `done()`: every task keeps a live timer (and, on the timeout path, an open socket) after the promise settles, so the timer can fire and call `done()`/`reject()` after the fact and node will not exit until the last timer expires — up to 90 s of hang after the final `console.log`. Also, if `docker` is not installed, `spawnSync(...).stdout` is null and `env.stdout.trim()` (line 17) throws an unhandled TypeError instead of reporting the missing prerequisite.

**Fix**: Clear the timeout and close the socket in both `done()` and the reject path (keep a handle on the timer), poll for the expected file/condition with a bounded deadline instead of a fixed 500 ms sleep, and null-guard the `spawnSync` result.

### Approval timeout (and denyAllPending) deny without emitting an `approval` event, leaving a stale banner with dead buttons
**`server/src/approvals.ts:65`** — found by robustness

The browser only clears `pendingApproval` when an `approval` event with the matching callId arrives (App.tsx:121-126), so after the 180 s gate the UI keeps showing "🔓 waddle wants to run bash" with approve/deny buttons that now silently no-op — `answerApproval` sends the intent, `resolveApproval` returns null (entry gone), and nothing is sent back or logged.
