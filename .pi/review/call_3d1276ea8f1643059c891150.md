## 🟠 Important

### ensure() short-circuits on container status "Running", making start()'s zombie recovery unreachable for the zombie it describes
**`concierge/src/platform.ts:136`** — found by correctness, security, robustness
ensure() returns `already running: <instance>` whenever the status feed reports the instance `Running` (concierge/src/platform.ts:136). The only caller that boots a machine, POST /wake (concierge/src/index.ts:337 `await platform.ensure(instance)`), therefore never reaches start()'s zombie path — the stop → wait → redeploy sequence at platform.ts:88-108 — for the exact case that path exists to handle: an instance whose agent idle-exited but which the control plane still reports `Running` (start()'s own failure mode, a deploy 409 'cannot deploy a running instance'). Behaviour is unchanged from the pre-refactor ensureInstance(), so the diff moves the bug rather than introducing it, but it is still live: a user wake against a zombie gets 202 `waking` while nothing boots, the wake row's occurrence is consumed, and the client's wakeCore then polls /health 60 times and gives up (~2 min) with 'gave up waiting — try again' (client/src/App.tsx wakeCore → pollUntilHealthy). The new module comment hedges this as an 'accepted residual' and platform.test.ts locks the short-circuit in, but the user-visible symptom — a machine that reports itself up yet never comes up on wake — remains.

**Fix**: Make ensure() confirm liveness rather than trust the coarse `Running` status: either attempt the deploy and let the existing 409 path drive zombie recovery, or add a cheap health probe so a `Running`-but-dead agent falls through to start(). If the short-circuit is genuinely intended, return it as a distinguishable outcome from /wake (e.g. a non-2xx or a `stale` flag) so the client does not report a successful wake for a machine it never booted.

### New auth-tier map documents /handoff/pull as shared-secret-only, but the route is enforced at the external tier (bb JWT or shared secret)
**`sdk/src/index.ts:147`** — found by security
The concierge-wire comment added here states two mutually inconsistent tiers: `external  bb JWT or shared secret  (/handshake /wake /assign /handoff)` and `secret  shared secret only  (/handshake bearer, /handoff/pull)`. The enforcement in concierge/src/index.ts says otherwise: `/handoff/pull` is gated by `requireExternal(req, reply)` (concierge/src/index.ts:375), i.e. any valid betterbase JWT OR the shared secret, while `/handshake` is gated by `secretOk(bearer(req))` (secret-only) — the reverse of what the map implies for each. This matters because `/handoff/pull` is the route that releases the wake escrow, whose payload server/src/concierge.ts now documents as `{ secret, schedules[], snapshot? }` — the master unlock secret plus a sealed whole-machine snapshot (server/src/concierge.ts:113-120, and server/src/index.ts rearmEscrow arms `{ secret: armSecret, ... }`). A maintainer reading this contract would conclude the master secret can only be pulled by a shared-secret holder, when the code accepts any bb JWT holder (bounded only by the handoff fire-gate) — the exact class the session-tier rule elsewhere deliberately excludes from writing table rows. An incorrect statement of who can reach a credential-releasing endpoint in the shared wire contract is a security hazard even when the enforcement code happens to be correct.

**Fix**: Align the map with the code: `external  bb JWT or shared secret  (/wake /assign /handoff /handoff/pull)` and `secret  shared secret only  (/handshake bearer)`. If bb-JWT access to /handoff/pull is not intended, change the route to secret-only instead of documenting it as such.

### The "unreachable concierge" test cannot exercise the wake timeout it claims to cover — the fake fetch throws synchronously
**`client/src/lib/concierge.test.ts:49`** — found by robustness
The test is named "wakeInstance reports an unreachable concierge instead of hanging the wake flow", but `stubFetch(() => ({ throwErr: new Error("ECONNREFUSED") }))` makes the mocked `fetch` reject immediately, so the `signal: AbortSignal.timeout(10_000)` guard in wakeInstance (concierge.ts:20) never runs. The same stub shape (no per-call delay, no abort handling) means the other fetch wrappers' AbortSignal paths are equally unexercised.

**Fix**: Make the fake fetch honour `init.signal` (reject with the signal's reason on abort) and add a case that returns a promise which only settles long after a short injected timeout — or expose/parametrize the timeout so the test can pass a few milliseconds and await the abort. Then assert `{ ok: false }` arises from the timeout, not from a synchronously thrown error.

### SDK auth-tier comment refiles /handshake bearer under the external tier, but /handshake is shared-secret-only
**`sdk/src/index.ts:142`** — found by correctness, security, robustness
The diff deletes the SDK's `secret shared secret only (/handshake bearer, /handoff/pull)` line and re-groups `/handshake bearer` under `external  bb JWT or shared secret  (/handshake bearer, /wake /assign /handoff /handoff/pull)`. Auth-tier documentation for the one route that mints session tokens is security-relevant surface for integrators.

**Fix**: Keep /handshake bearer on a shared-secret-only tier line in the SDK comment (or drop it from the external line) so the published contract matches concierge/src/index.ts:166 and the secretOk check at index.ts:311.
