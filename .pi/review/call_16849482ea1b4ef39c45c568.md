## 🟠 Important

### ensure() short-circuits on container status "Running", making start()'s zombie recovery unreachable for the zombie it describes
**`concierge/src/platform.ts:136`** — found by correctness, robustness
platform.ensure() returns `already running: <instance>` as soon as the memoized status map reports "Running" (line 136), and only falls through to start() when the status is missing/other or the status call throws. start()'s zombie branch (lines 86-100, matching `cannot deploy a running instance` → rest → retry deploy) is therefore never reached for the exact condition its comment names: "the agent idle-exited but the instance still reads Running". Traced callers: platform.start has no direct production caller — concierge/src/index.ts calls platform.ensure at line 125 (wake row fire) and line 341 (`POST /wake`), and nowhere calls platform.start. Consequence: for a zombie the platform still reports Running, the scheduled wake row fires, ensure() logs "already running", the row is spent, and no boot happens — the occurrence is silently consumed and the user's /wake returns 202 "waking" with the machine still dead. start()'s recovery only ever runs when the status feed is stale or absent, not for the zombie case it was written for. The new doc comment on ensure() (lines 41-46) records this as an accepted residual, but the behaviour is unchanged and still a missed-work/incorrect-result path.

**Fix**: Make ensure() confirm liveness rather than trust the coarse `Running` status: attempt the deploy and let the existing 409 path drive zombie recovery, or add a cheap health probe so a `Running`-but-dead agent falls through to start(). If the short-circuit is genuinely intended, return it as a distinguishable outcome from /wake (e.g. a non-2xx or a `stale` flag) so the client does not report a successful wake for a machine it never booted.

### The "unreachable concierge" test cannot exercise the wake timeout it claims to cover — the fake fetch throws synchronously
**`client/src/lib/concierge.test.ts:49`** — found by robustness
The stub's `responses` are invoked synchronously inside the async fetch fake (`const r = respond(url, init); if (r.throwErr) throw r.throwErr;`), so the returned promise rejects immediately and the request is never pending. The test comment at lines 50-51 claims the structural AbortSignal guard "is what bounds a SILENT stall", but a request that never settles is the only thing that guard can catch, and no test creates one — not for /wake (10s), /assign (5s), or /health (4s). A regression that dropped the `signal` option would still pass this suite. The same gap applies to `assignStandby`'s throw test (line 78).

**Fix**: Add a stub case that returns a promise which never settles (or one that rejects only when `init.signal` aborts) and assert the request is aborted after the timeout, using fake timers or a short injected timeout so the test stays fast.

### assignStandby's zone-bind silently accepts any host when zone is empty
**`client/src/lib/concierge.ts:63`** — found by robustness
`return host.endsWith(zone) ? m!.url! : null` is the only thing preventing the TOFU pin from travelling to a host outside the primary's operator domain. When `zone` is the empty string this degenerates to `host.endsWith("") === true`, so the function returns whatever URL the concierge handed out. Today the only caller guards it (App.tsx: `const zone = standbyZone(); const standby = zone ? await assignStandby(conciergeAuth, zone) : null;`), but the exported contract advertises binding while the function itself has none, and `standbyZone()` produces degraded zones for non-FQDN hosts (single-label hostname → `"."`). A future caller that forgets the `zone &&` guard gets an unbound host with no error.

**Fix**: Reject the degenerate inputs inside assignStandby: return null (and log) when `zone` is empty or a bare dot, rather than falling back to an unconditional match.

### Concierge-wire comment claims every route is POST, but /assign (and /status) are GETs
**`sdk/src/index.ts:140`** — found by robustness
The new comment block states "Every route is POST with `instance` in the body (no GETs — no caching, no URL-borne secrets)" (sdk/src/index.ts:140-141), yet the same block's auth-tier line lists /assign (sdk/src/index.ts:142) and the concierge implements /assign and /status as GETs (concierge/src/index.ts:280, :352). A client written against this SDK contract would POST /assign and get a 404 instead of a standby URL — the SDK is documented as the single source of the cross-process wire shape ("if it crosses a process boundary, it lives in this file").

**Fix**: Scope the claim to the table/escrow routes (e.g. "every write route is POST with `instance` in the body") and call out the GET verbs (/assign, /status) explicitly in the tier list.
