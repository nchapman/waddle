## 🔴 Critical

### Postbox is sealed with a different key than it is opened with — return mail can never be decrypted
**`server/src/index.ts:273`** — found by correctness
The seal and open sides now derive the postbox key from different inputs. At sleep the blob is sealed with `sealPostbox(armSecret, INSTANCE, payload)` (line 495/504), where `armSecret` is the raw master secret (set at `armSecret = secret` line 290 and at autonomous boot line 820), and `sealPostbox` does `derive(Buffer.from(armSecret,'base64'), 'waddle/postbox')` = HKDF(master, "waddle/postbox"). At unlock it is opened with `openPostbox(postboxKeyFromSecret(secret), ...)` (line 273), and `postboxKeyFromSecret` returns `base64(derive(master,'waddle/postbox'))`; `openPostbox` then derives again: `derive(base64decode(that), 'waddle/postbox')` = HKDF(HKDF(master,"waddle/postbox"), "waddle/postbox"). The two keys differ, so AES-GCM auth fails and `openPostbox` throws on every blob. The catch at line ~285 logs 'postbox merge failed — degrading to re-fire delivery', so (a) the unattended run's transcript is never delivered, and (b) `mergeSchedules` never runs — the done-markers/tombstones that implement the no-re-fire/no-resurrect contract are lost, so a completed schedule re-fires at the next attended unlock (duplicate work). The unit tests pass only because server/src/postbox.test.ts feeds the same `postboxKeyFromSecret(MASTER)` value to both sealPostbox and openPostbox, masking the asymmetry. Before this diff both sides derived from `autonomyKeyFromSecret(secret)`, so this is introduced by the change.

**Fix**: Make the two call sites agree. Simplest: openPostbox(secret, INSTANCE, blob) at line 273 (pass the raw master, matching sealPostbox(armSecret, ...)); or, if the derived key is intended as the input, seal with `sealPostbox(postboxKeyFromSecret(armSecret), ...)` at lines 495/504. Add a round-trip test that seals with the exact value used at sleep and opens with the exact value used at unlock.

## 🟠 Important

### Postbox seal/open key derivation mismatch makes unattended-run mail unopenable (no-re-fire contract silently broken)
**`server/src/index.ts:495`** — found by security, tests
`sealPostbox(secretB64, ...)` and `openPostbox(secretB64, ...)` both run the input through `derive(input, "waddle/postbox")` (server/src/postbox.ts). At autonomous sleep the code seals with the raw master: `sealPostbox(armSecret, INSTANCE, payload)` (lines 495 and 504), i.e. key = HKDF(master, "waddle/postbox"). At the next user unlock the code opens with `openPostbox(postboxKeyFromSecret(secret), INSTANCE, blob)` (line 273), and `postboxKeyFromSecret(secret)` already returns HKDF(master, "waddle/postbox"), so `openPostbox` derives a second time: key = HKDF(HKDF(master,"waddle/postbox"), "waddle/postbox"). The two keys differ, so every sealed postbox blob fails to open; the failure is swallowed by the `catch` that logs "postbox merge failed — degrading to re-fire delivery". The pre-diff code was symmetric (both sides received `autonomyKeyFromSecret(secret)`, so both applied the same single HKDF), so this diff introduces the regression. Consequence: the run's transcript is never delivered and the done-markers/tombstones in the schedule table are never merged, so schedules the unattended run already completed (or cancelled) re-fire on the next unlock. `postbox.test.ts` does not catch it because it passes the same already-derived key to both seal and open.

**Fix**: Make both sides derive identically: pass the raw secret to both (seal with `armSecret` and open with `secret`), or pass the derived key to both (seal with `postboxKeyFromSecret(armSecret)`, open with `postboxKeyFromSecret(secret)`). Add a test that seals with the raw master secret and opens via `postboxKeyFromSecret` to pin the production contract.

### Wake rows and escrow arm are now gated by different conditions — background-off machines die into wakes they cannot service
**`server/src/index.ts:517`** — found by robustness
The sleep gate still writes a concierge wake row for every active schedule under `if (conciergeActive() && autonomyEnabled())` (index.ts:460-466), but the new escrow re-arm that produces the credential those wakes consume is gated additionally on `backgroundTasksEnabled()` (index.ts:517). Before this diff both the wake rows and the arm lived under the single `autonomyEnabled()` gate, so they could not disagree. Now a machine with WADDLE_WAKE_AUTONOMY=1 but the background preference off (a user who created a schedule, then toggled background off — `setPreferences` only flips the flag, it never cancels or disables existing schedule rows) writes wake rows and sleeps; the concierge reboots it for the due work, `readWakeCredential()`/`pullHandoff()` find no credential, and the boot falls through to the locked path (index.ts:785). The refusal branch that is supposed to prevent exactly this (index.ts:391) only checks `!autonomyEnabled()`, so it does not fire. Result: the scheduled run is missed and a locked enclave burns compute until the idle sweep reaps it.

**Fix**: Make the wake-row write and the escrow arm share one condition: gate the wake-row loop on `backgroundTasksEnabled()` as well (or extend the refusal check at index.ts:391 to `(!conciergeActive() || !autonomyEnabled() || !backgroundTasksEnabled())`), so a machine never books a wake it has no credential to survive.

### Master root secret written in cleartext to DATA_DIR on every sleep, contradicting the code's stated invariant
**`server/src/index.ts:546`** — found by security
The sleep gate calls `armWakeCredential({ secret: armSecret, schedules, snapshot, inferenceKey })`, and `armSecret` is the raw 64-byte master unlock secret (set at unlock, line 290, and inherited by the autonomous boot at line 820). `armWakeCredential` (server/src/wakeboot.ts) serializes the whole object with `JSON.stringify` to `join(DATA_DIR, "wake-credential.json")` at mode 0o600 — so the root key from which all key material is derived (verifier, session, snapshot, postbox, log) now sits at rest in cleartext on the enclave volume. This directly contradicts the comment added on the variable: `armSecret` is documented as "Memory-only, same lifetime as the lock's derived keys — never in DATA_DIR, never in archives" (lines ~759-761), and the previous design deliberately kept the escrow/at-rest material schedule-scoped (`autonomyKeyFromSecret`, "never the master"). The write is gated only by `armSecret && backgroundTasksEnabled()` with a pending horizon (line 517), not by `autonomyEnabled()`/the dev path it claims to be — so on any machine where the user enabled background tasks and has a live schedule, the master secret is persisted at rest even when `WADDLE_WAKE_AUTONOMY` is unset (in which case `readWakeCredential` is never even called and the file is pure liability). Any process or backup that can read DATA_DIR now recovers the master secret, defeating the earlier defense-in-depth.

**Fix**: Do not persist the master secret in the wake-credential file: keep the dev file arm scoped to a schedule-derived subkey (as before) or omit `secret` from the on-disk arm entirely and gate any file write behind an explicit dev flag rather than `backgroundTasksEnabled()`. If the master must ride the escrow, keep it exclusively in the concierge memory handoff and update the `armSecret` invariant comment to match reality.

### Autonomous boot never consults the restored verifier: `enrolled` is captured before restore, so the unlock TOFU-enrolls instead of verifying
**`server/src/index.ts:804`** — found by correctness
`const lock = new Lock()` runs at module top (line 117), and the Lock constructor sets `this.enrolled = existsSync(VERIFIER_FILE)` at construction (server/src/state.ts). The boot IIFE (lines 796-804) then calls `restoreArchive(...)`, which wipes DATA_DIR and moves the snapshot's files in — including verifier.bin — *after* that cache was computed. On a fresh volume (the normal prod case, per the comment 'every deploy is a fresh volume') `lock.enrolled` is false, so `lock.unlock(cred.secret, 'wake0')` takes the enroll branch and writes a new verifier rather than checking the just-restored one. The comment at lines 799-802 and wakeboot.ts's doc both assert that 'the restored verifier makes a wrong/corrupted secret 401 before touching anything' and that a stale credential 'yields a locked boot'; neither holds on a fresh volume — the boot silently accepts and enrolls whatever secret the credential carries and runs the due work under it. Since the verifier is deterministic, a correct secret still works, so the functional difference is limited to the failure cases the design relies on for rejecting a stale/rotated secret.

**Fix**: Recompute enrollment from disk after the restore, e.g. re-read `existsSync(VERIFIER_FILE)` (or construct/refresh the Lock) after `restoreArchive`, so the subsequent unlock is a real verification when the snapshot supplied a verifier.

### Postbox test uses the derived key on both sides, hiding a seal/open mismatch in the real call sites
**`server/src/postbox.test.ts:29`** — found by tests
The rewritten test does `const key = postboxKeyFromSecret(MASTER); sealPostbox(key, …); openPostbox(key, …)` — the same value goes in on both sides, so it stays green regardless of what key convention the production callers use. In the diff, `sealPostbox` internally derives `derive(arg, "waddle/postbox")` (server/src/postbox.ts:36-38) while `postboxKeyFromSecret` is itself `derive(master, "waddle/postbox")` (postbox.ts:20). index.ts seals with the raw secret but opens double-derived: sleep seals `sealPostbox(armSecret, …)` (server/src/index.ts:495, armSecret is the raw master from the unlock body / wake credential) while unlock reads `openPostbox(postboxKeyFromSecret(secret), INSTANCE, blob)` (index.ts:273). Those two keys differ (one vs two HKDF rounds), so the unattended run's mail can never be opened — the merge at index.ts:273-276 lands in the catch, the run's transcript is dropped, and the schedule table re-fires from the shelf (the duplicate-run failure the surrounding comments claim to prevent). Before this change both seal and open were called with the same `autonomyKeyFromSecret(secret)`, so the round-trip matched; the test's symmetric use of the key is exactly what fails to catch the regression.

**Fix**: Make the test drive the production convention: seal with the raw secret (`sealPostbox(MASTER, …)`) and open with `postboxKeyFromSecret(MASTER)` (or the reverse) so the mismatch fails the suite, and fix index.ts to pass the same form to both calls.

### Sleep-gate snapshot is sealed and escrowed with no size bound, unlike the postbox blob it sits beside
**`server/src/index.ts:532`** — found by robustness
`sealSnapshot(armSecret, INSTANCE, createArchive().body)` base64-encodes the whole tarball of DATA_DIR (archive.ts:111, maxBuffer 1 GiB) into the credential that `armHandoff` POSTs as JSON to the concierge. The postbox path two hundred lines above explicitly caps its blob at `MAX_BLOB = 6 * 1024 * 1024` with the comment 'gateway accepts 8MiB; stay under' and degrades with a notice; the snapshot has no equivalent cap, and a lived-in browser profile makes the archive tens of MiB (archive.ts notes ~34 MiB slots), i.e. a ~45 MiB base64 body. The failure is handled (armHandoff returns false → warn 'sleep-gate escrow re-arm failed'), but the wake rows for the next occurrence are already written, so the arm failure silently downgrades to a locked wake boot. Additionally `createArchive()` is synchronous spawnSync with no timeout, so a stalled tar/zstd blocks the exit path.

**Fix**: Apply the same size discipline: skip attaching the snapshot when the sealed blob exceeds a documented cap (arm context-free, with an explicit log line), and/or bound the archive step so a hung tar cannot block the sleep exit.

### WS `preference` handler calls setPreferences (synchronous fs write) unguarded — a write failure becomes an unhandled rejection
**`server/src/index.ts:703`** — found by robustness
The new branch calls `setPreferences({ background })`, which does `mkdirSync(DATA_DIR)` + `writeFileSync(FILE, …, { mode: 0o600 })` (preferences.ts:37-39). This runs inside the `socket.on("message", async (raw) => …)` handler (index.ts:659) with no try/catch. On a read-only or full DATA_DIR the synchronous throw rejects the async handler's promise; with Node's default unhandledRejection behaviour that terminates the server — taking down a live unlocked session over a preference echo. The unlock path already wraps its preference write in the route's try/catch; this path does not.

**Fix**: Wrap the `setPreferences` call in try/catch (log and still echo the previous value), or make setPreferences return a result instead of throwing, so a failed persistence cannot crash the process.
