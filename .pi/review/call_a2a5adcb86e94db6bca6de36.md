## 🔴 Critical

### Master root secret written in cleartext to DATA_DIR by the sleep-gate file arm
**`server/src/index.ts:622`** — found by correctness, security
At the sleep gate rearmEscrow() calls armWakeCredential({ secret: armSecret, schedules, snapshot, inferenceKey: armInferenceKey ?? undefined }) (index.ts:622). armSecret is the raw 64-byte master unlock secret (set at index.ts:346 `armSecret = secret`, inherited by an autonomous boot), i.e. the root of every derived key domain (verifier/session/log/snapshot/postbox). armWakeCredential (server/src/wakeboot.ts:44-47) does `writeFileSync(join(DATA_DIR, "wake-credential.json"), JSON.stringify(cred), { mode: 0o600 })`, so the master secret AND the inference API key land on disk in plaintext. The invariant comment above armSecret claims the secret is "memory-only … never in DATA_DIR", and the only guard is the runtime check `!process.env.TINFOIL_API_KEY && autonomyEnabled()`: any deploy without the platform-injected key (or a dev run with a mounted persistent volume) persists the master at rest. Anyone/anything able to read DATA_DIR — co-tenant process, volume snapshot, a backup that ignores the archive filter — recovers the master and can derive the verifier, log, snapshot and postbox keys, i.e. fully unlock and decrypt the machine.

**Fix**: Never serialize the master to the file arm. Scope the on-disk dev credential to a derived subkey that cannot decrypt the machine, or write only the already-sealed snapshot plus schedules and require the secret from the concierge escrow; at minimum gate the write on an explicit dev-only flag rather than the absence of TINFOIL_API_KEY.

## 🟠 Important

### Enabling the bb-JWT external tier in production authorizes every holder of an audience token to drive /wake and /assign against the operator's instances, with no subject binding
**`concierge/src/auth.ts:43`** — found by security, robustness
createVerifyExternal returns `true` for any token that `jwtVerify(token, jwks, {issuer, audience})` accepts (lines 41-43): the verified claims are discarded and nothing binds the caller to a machine — no `sub`/tenant check, no lookup tying the JWT holder to `instance`. In concierge/src/index.ts the external tier is exactly what gates the user-facing verbs (`requireExternal` on /wake, /assign and /status), and `allowedInstance('waddle')` admits the operator's singleton machine. The deployed config (config/concierge-tinfoil-config.yml) enables this tier (`CONCIERGE_JWKS_URL=https://accounts.betterbase.dev/.well-known/jwks.json`, pinned ISSUER/AUDIENCE), so any holder of a token for that betterbase client id — i.e. any user of the accounts service, not just the operator — can POST /wake to force repeated 75-95s deploys on the operator's instance (money/availability) and GET /assign to claim a warm standby URL from the pool. Those standby machines are created with STANDBY_SECRETS = CONCIERGE_SHARED_SECRET,TINFOIL_API_KEY, so the caller also obtains a live URL to a machine carrying operator secrets (it boots locked, so this is not direct confidentiality loss, but it is unauthenticated delegation of the operator's pool). The previous review flagged this at the config that turns the tier on; the new auth.ts is the code path that implements the unbound acceptance, so the finding stands.

**Fix**: Bind the JWT to the target resource before returning true: require and compare a subject/tenant claim against the instance being driven (or an operator allowlist of subjects), and keep /wake, /assign and /status off the blanket JWT tier until the per-user instance mapping in PLAN.md exists.

### Fire-mode probe budget (75s) is shorter than the documented boot time (~90s), so a legitimately booting replacement is declared a zombie and stopped+redeployed
**`concierge/src/index.ts:137`** — found by robustness
The wake-row path calls `platform.ensure(instance, 75_000, "fire")`, and ensure() calls `start()` as soon as the probe budget is exhausted without a healthy /health (platform.ts:195); start()'s tinfoil path stops the instance (`rest()`) before retrying the deploy. The diff's own comment states the requirement: 'a replacement boot mid-flight gets its ~90s to reach health before we call it a zombie and redeploy'. The budget actually granted is 75s, i.e. 15s less than the boot the comment says must be accommodated. A boot needing ~90s therefore trips the zombie branch at 75s, the machine is stopped mid-boot and redeployed, and because the new boot again needs ~90s the same misfire can repeat on every wake — the stop/deploy thrash the zombie recovery exists to avoid, now applied to a machine that was healthily booting. The release window (10 min) bounds the window, not the per-boot budget.

**Fix**: Make the budget at least the documented boot time (>=90s) — or better, base the zombie decision on an authoritative platform signal for 'boot in progress/not running' rather than a wall-clock probe cutoff, so a slow-but-legitimate boot is never stopped. Reconcile the 75_000 constant with the '~90s' comment either way.

### ensure()'s new /health probe cannot reach instance hosts under the concierge's egress allowlist, so every Running machine is treated as a zombie and stopped+redeployed
**`concierge/src/platform.ts:186`** — found by robustness
ensure() only trusts a Running machine when `probe(url, 5_000)` reaches `https://<domain>/health`; on failure it falls through to `start()` (platform.ts:195/197), whose tinfoil 409 path runs `rest()` (`tinfoil container stop`) and then redeploys — a destructive escalation of a single failed probe. The deploy target hosts are `<name>.ddg-waddle.containers.tinfoil.dev`, one level below the zone base. The config added exactly one mitigation, the zone base `ddg-waddle.containers.tinfoil.dev` (config/concierge-tinfoil-config.yml:39), while the code the diff deleted stated why the old path never probed: 'the allowlist pins IPs at boot' and instance hosts do not exist until the machines do. The 'no derivable domain — probe skipped' escape only fires when INSTANCE_DOMAIN_BASE is unset; production sets it, so the `row.domain ?? `${instance}.${domainBase}`` fallback makes every Running row probe-able and every probe failure destructive. A DNS/probe blip, a 5xx while the app is mid-boot, or the 5s per-attempt budget being too tight turns a live — possibly user-claimed, in-session — machine into a stop+redeploy. Triggered from POST /wake (user mode, 10s budget) and the wake-row fire path (index.ts:137, 75s, fire mode).

**Fix**: Do not escalate a negative probe to stop+redeploy on its own: require an authoritative non-Running status before calling rest()/start(), or distinguish transport/probe failures (unreachable, timeout) from a real dead-agent signal and surface the former as a retryable error. Verify live that the added allowlist entry actually covers `<instance>.<domainBase>` (subdomain, not just the zone base) before relying on the probe.

### Enabling the bb-JWT external tier in production authorizes every holder of an audience token to drive /wake and /assign against the operator's instances, with no subject binding
**`config/concierge-tinfoil-config.yml:25`** — found by correctness, security, robustness
The added CONCIERGE_JWKS_URL / CONCIERGE_ISSUER / CONCIERGE_AUDIENCE env lines (concier-tinfoil-config.yml:25-27) are what makes the bb-JWT leg of the external tier live in production; before this change the shipped concierge had no CONCIERGE_JWKS_URL, so createVerifyExternal's JWT branch was dead and the external tier was the fleet secret only. concierge/src/auth.ts:39-50 verifies signature+iss+aud and returns a bare boolean — no subject or claim is carried out of it. index.ts requireExternal (index.ts:236-240) guards the fleet-wide verbs /wake, /assign and /status, and the only further check is allowedInstance (index.ts:192-198), a static name allowlist whose entire content in this config is the singleton "waddle" (CONCIERGE_ALLOWED_INSTANCES). Any account able to obtain a token with audience d096d76d-d066-4ac9-956c-ad3f35c57450 can therefore POST /wake {instance:"waddle"} (clears the pending stop row, drives platform.ensure), GET /assign (takes a warm standby, learns its URL, and triggers a replacement boot at the operator's cost), and GET /status (schedule timing, standby names, escrow-armed state). Nothing binds a caller to an instance or to the user whose machine it is — a cross-tenant authorization gap on the shared singleton name.

**Fix**: Do not put the audience-only JWT tier in front of the fleet verbs as-is. Have createVerifyExternal return the verified subject and require it at the boundary (allowlist the subject(s) owning each instance name, or record the claiming subject at /assign and enforce it in allowedInstance), rejecting /wake and /assign for any subject not bound to the target instance; otherwise keep the shared secret as the machine tier for these verbs.

### Raw master unlock secret escrowed to the concierge by the sleep-gate re-arm
**`server/src/index.ts:612`** — found by correctness, security
rearmEscrow() calls armHandoff({ secret: armSecret, schedules: schedulableRows(activeSchedules()), snapshot }, bearer, horizon - Date.now() + 15*60_000) (index.ts:612). armHandoff posts the opaque credential bag to the concierge's /handoff endpoint (concierge.ts:108), where it is held in the concierge's memory for the TTL window. `armSecret` is the raw user master secret captured at unlock (index.ts:355 `armSecret = secret`) or inherited by the autonomous boot; it is the same root of all key derivation (derive(secret,"verifier"/"log"/"session")). Anyone with access to the concierge process/memory (operator, compromise, or a leaked concierge log) therefore obtains the master secret, which fully impersonates the user across unlocks and decrypts the sealed log. The TTL is next-due + 15 min, so this exists continuously while schedules are active, not just transiently. The diff preserves this behavior unchanged.

**Fix**: Escrow a snapshot-scoped subkey rather than the raw master (as handoff.ts documents), or explicitly record in PLAN/AGENTS that full delegation embeds the master; do not send the master and the key it seals in the same credential bag.

## 🟡 Suggestion

### The "silent stall" test never exercises wakeInstance's stalled branch — its mock error name doesn't match a real abort
**`client/src/lib/concierge.test.ts:50`** — found by robustness
The test named "wakeInstance bounds a silent stall by its abort signal" makes its fetch stub reject with `new Error("aborted")` (line 50). wakeInstance classifies a failure via `e.name === "TimeoutError" || e.name === "AbortError"` (concierge.ts), so a plain Error lands in the *non*-stalled branch and produces "concierge unreachable — is it running?". The assertion `assert.match(r.detail!, /concierge unreachable/)` (line 55) therefore passes on the wrong branch: the "concierge stalled — wake gave up after Ns (deploy still running?)" message — the entire point of the timeout work — is never asserted anywhere, and the test would still pass if that branch regressed or were removed. Real timeouts abort with a DOMException named "TimeoutError", which the mock does not reproduce. (Prior review flagged the sibling test at line 63 for the same class of gap.)

**Fix**: Make the stub reject with the real shape (`Object.assign(new Error("aborted"), { name: "TimeoutError" })` or a DOMException) and assert `r.detail` matches /concierge stalled/; optionally add a separate test pinning the generic unreachable message.

### The "wakeInstance reports a failed concierge call as unreachable" test still cannot exercise the wake timeout it references
**`client/src/lib/concierge.test.ts:61`** — found by correctness
Carried over and still valid. This test uses `stubFetch(() => ({ throwErr: new Error("ECONNREFUSED") }))` — the fake is `async` and throws synchronously, so the rejected promise settles immediately and `init.signal` is never observed. The sibling test at line 48 installs a never-settling fetch but rejects it with a plain `new Error("aborted")` (name `"Error"`, not `AbortError`/`TimeoutError`) and asserts `/concierge unreachable/`, so even that one pins the generic detail rather than the abort branch at concierge.ts:42-46. A regression that dropped `AbortSignal.timeout(timeoutMs)` from the /wake fetch, or that broke the stall/unreachable distinction, would leave this suite green; the same never-settling case is absent for `assignStandby`'s 5s signal and for each `pollUntilHealthy` 4s probe.

**Fix**: Add a stub that never settles (or one that rejects with a real abort-shaped error such as `Object.assign(new Error("aborted"), { name: "AbortError" })`) with a short injected timeout, and assert each call returns at its own bound and reports the stall detail — extend it to `assignStandby` and `pollUntilHealthy`.

### authHeaders swallows the session-token failure, sending an unauthenticated /wake that surfaces as a misleading 401
**`client/src/lib/concierge.ts:16`** — found by correctness
`const token = (await auth().catch(() => null)) ?? CONCIERGE_TOKEN;` (line 16) discards every error from the App-supplied thunk (`() => bbSessionRef.current?.getToken().catch(() => null)`, App.tsx:112) — the token fetch is swept twice, so a broken/expired session runner is indistinguishable from "signed out". In live builds `CONCIERGE_TOKEN` is `""` (config.ts:14), so the failure silently degrades to no `Authorization` header; `/wake` then 401s and the user is shown `concierge refused (401) …` (line 36) with no signal that re-signing-in is the fix. The same helper feeds `assignStandby` (line 79), where the missing header just yields a silent `null` and a fallback to the failing wake path. Still present, unchanged by this revision.

**Fix**: Stop folding an auth-thunk failure into the refusal string: let the error propagate to a distinguishable detail ("could not obtain your session token — sign in again") or at least log it, so a 401 caused by a stale session reads differently from a genuine refusal.

### JWT verification silently drops issuer/audience when the env vars are empty
**`concierge/src/auth.ts:35`** — found by security
`jwtVerify(token, jwks, { issuer: opts.issuer || undefined, audience: opts.audience || undefined })` — jose skips any claim whose option is undefined. If CONCIERGE_JWKS_URL is configured but CONCIERGE_ISSUER/CONCIERGE_AUDIENCE are unset or empty, every token signed by any key in that JWKS passes regardless of its `iss`/`aud`, i.e. the verifier degrades to signature-only. index.ts only emits a console.warn for an empty audience, so this misconfiguration is easy to ship silently into a TEE'd production concierge.

**Fix**: Fail closed: when a JWKS URL is configured, refuse to build the verifier (and decline all JWTs) unless both issuer and audience are set, instead of warning and continuing.
