## 🟠 Important

### Unguarded setPreferences in /unlock turns a preference-write failure into a failed unlock
**`server/src/index.ts:298`** — found by correctness, robustness
`if (typeof background === "boolean" && background !== getPreferences().background) { setPreferences({ background }); }` runs inside the /unlock try block, and `setPreferences` (server/src/preferences.ts:34-40) does an unguarded `mkdirSync(DATA_DIR, {recursive:true})` + `writeFileSync(FILE, …, {mode:0o600})`. Any failure (read-only or full DATA_DIR, or the documented `storage:"memory"` mode — `Lock`'s constructor catches the mkdir failure and reports `storage:"memory"`, but preferences.ts does not) throws and is caught by the outer `catch (e) { … return reply.code(err.statusCode ?? 500) }`. The trigger is ordinary: the client always sends the stored pref (`getBackgroundPref() ?? undefined`, client/src/lib/background.ts is the source of truth), so a device whose local pref is `true` unlocking a machine with no writable storage (or whose disk is momentarily full) sends `background:true`, differs from the cached `{background:false}`, and the write fails. Consequence: `lock.unlock` has already minted the session and set `unlocked = true`, but the client receives a 500, throws in `unlock()`, never stores the token, and the machine is unusable even though the unlock server-side succeeded. The sibling WS `preference` handler (line 724) deliberately wraps the identical call in try/catch precisely because "a failed persistence must never take a live session down" — the unlock path is the one place where failing persistence *does* take the session down, and it silently compounds: when the WS write fails the client is never told (no echo is sent), so client and server diverge and the next unlock re-attempts the same failing write.

**Fix**: Wrap the unlock-path `setPreferences({ background })` in a try/catch (warn and continue, matching the WS handler), so a preference-persistence failure degrades to the previous value instead of failing an otherwise-successful unlock.

### Master unlock secret is escrowed to the concierge, letting it decrypt all user state
**`server/src/index.ts:556`** — found by security
The sleep-gate re-arm now sends `{ secret: armSecret, schedules, snapshot }` to the concierge, where `armSecret` is the raw 64-byte master unlock secret (set at unlock: `armSecret = secret`). Previously the escrow carried only a schedule-scoped subkey derived via `autonomyKeyFromSecret`, which could run schedules but could not decrypt the machine. The sealed payloads use that same master: the snapshot is sealed under `HKDF(master,"waddle/snapshot")` (snapshot.ts) and the event log under `lock.logKey = derive(master,"verifier")`→log, and the concierge handoff doc now explicitly says the bag carries `{ secret, schedules[], snapshot? }` — the key travels together with the ciphertext it protects. Anyone with access to the concierge's memory (its operators, or an attacker who compromises it) can therefore open the whole-machine snapshot — browser logins, pi session transcripts, sealed log — and the master-sealed event log. This is a real confidentiality regression from the subkey scope, and it contradicts the consent dialog's own claim that "Operators still cannot read your data" (client/src/components/BackgroundDialog.tsx), which only warns a compromised concierge "could capture a wake."

**Fix**: Keep the escrow scoped to what the wake boot actually needs (a schedule/snapshot-scoped subkey that cannot decrypt the master-sealed log), or, if master escrow is truly intended, correct the dialog text and document that concierge memory access equals full user-data disclosure.

### Master root secret written in cleartext to DATA_DIR on every sleep, contradicting the code's stated invariant
**`server/src/index.ts:565`** — found by correctness
At the sleep gate the dev file arm does `armWakeCredential({ secret: armSecret, schedules: activeSchedules(), snapshot, inferenceKey: armInferenceKey ?? undefined })`. `armSecret` is the raw 64-byte master unlock secret (set at index.ts:293 `armSecret = secret` and inherited at index.ts:853). `armWakeCredential` (server/src/wakeboot.ts) serializes the whole object with `JSON.stringify` to `join(DATA_DIR, "wake-credential.json")` at mode 0o600. That secret is the root of every derived key: state.ts derives `verifierKey = derive(secret,"verifier")` and `logKey = derive(verifierKey,"log")`, and the diff adds `snapshot`/`postbox` domains under the same master. This directly contradicts the invariant comment added in this same diff at index.ts:786-787 ('Memory-only ... never in DATA_DIR, never in archives'). It is reached whenever TINFOIL_API_KEY is unset (all of dev — compose.dev.yaml sets CONCIERGE_URL/CONCIERGE_SHARED_SECRET/WADDLE_WAKE_AUTONOMY but no TINFOIL_API_KEY) and background tasks are on. The previous revision's file arm carried only the schedule-scoped subkey; this change promotes it to the master, so the regression is introduced here.

**Fix**: Do not persist the master secret in the wake-credential file — keep the dev file arm scoped to a schedule-derived subkey (as before), or omit `secret` from the on-disk arm entirely and gate any file write behind an explicit dev flag rather than the background preference. If the master must ride the escrow, keep it exclusively in the concierge memory handoff and correct the `armSecret` invariant comment to match reality.

### Warned delegation opt-in is client-side only — any authenticated session can enable full delegation
**`server/src/index.ts:720`** — found by security
The new WS `preference` intent calls `setPreferences({ background })` with the value taken straight off the wire from any session that passes `requireSession` (only the ordinary session bearer, index.ts:601). The same is true of the unlock path: `/unlock` accepts `background` from the request body and persists it (`if (typeof background === "boolean" && background !== getPreferences().background) setPreferences({ background })`). The only thing standing between tier 0 and tier 1 is `hasAcceptedWarning()` reading localStorage in the client (App.tsx toggleBackground) — the server has no notion that the warning was ever shown. The design comments call this warned opt-in "the delegation boundary" (preferences.ts, wakeboot.ts), yet a single WebSocket message `{type:"preference",background:true}` (or an unlock with `background:true`) arms tier 1, after which the sleep gate escrows the master secret and a sealed snapshot with the concierge. Any script injected into the client origin, or a buggy client, silently crosses the boundary without the user ever seeing the warning.

**Fix**: Record acceptance server-side as part of the transition (e.g. require an explicit, separately-authenticated acknowledgement before persisting background=true, or reject preference writes that were not the direct result of a confirmed dialog), rather than trusting a client-supplied boolean.

### New security-critical resyncEnrollment() has no test — a regression silently restores TOFU enrollment
**`server/src/state.ts:49`** — found by tests
This diff adds `Lock.resyncEnrollment()` and calls it once in the autonomous boot (server/src/index.ts:834), after `restoreArchive` brings back verifier.bin. Its whole purpose is to flip the module-load-cached `enrolled=false` to true so the subsequent `lock.unlock(cred.secret, "wake0")` VERIFIES against the restored verifier instead of silently TOFU-enrolling whatever the credential carries (the prior critical finding). Nothing tests it: `grep resyncEnrollment` matches only state.ts:49 (definition) and index.ts:834 (call). state.test.ts never invokes it, and its shared DATA_DIR means every `new Lock()` in that file already sees a persisted verifier.bin at construction, so the exact precondition resyncEnrollment exists to handle (verifier appears *after* the Lock was constructed) is never reproduced. The new test at state.test.ts:16 even claims in its assertion message that it covers 'a snapshot-restored boot unlocks verified', but it only asserts verifier.bin bytes are deterministic across two unlocks of the same lock — it never exercises the resync path. If resyncEnrollment is deleted or its `storage==="disk"` guard changes, the autonomous boot reverts to accepting any credential secret with no test failing.

**Fix**: Add a state.test.ts case that constructs a Lock against a DATA_DIR with no verifier (or a scratch dir), writes a verifier.bin out-of-band (sealed with the secret's 'verifier' key), calls resyncEnrollment(), and asserts unlock(secret) succeeds / verify throws 'wrong secret' for a non-matching secret — i.e. exercise the post-construction verifier appearance directly.

### Fresh-device preference adoption marks the warning accepted without ever showing it, untested
**`client/src/App.tsx:473`** — found by correctness, security, robustness, tests
On a fresh device (`getBackgroundPref() === null`) with the machine reporting `background: true`, the client calls `acceptWarning()` (App.tsx:473), which sets both `waddle.backgroundAccepted` and `waddle.background` in localStorage. That writes the sticky acceptance flag the warning gate checks (`hasAcceptedWarning()`), yet no BackgroundDialog is ever rendered on this path. The stated justification is that the snapshot carried another device's acceptance, but locally it means the one-time delegation warning can never be shown on this device for the inherited state, and there is no test covering the adoption branch (background.test.ts exercises only getBackgroundPref/setBackgroundPref/acceptWarning in isolation).

**Fix**: Adopt the value without setting the acceptance flag (e.g. `setBackgroundPref(unlocked.background)` only), or drive the decision through the dialog so the warning is actually surfaced; add a test for the adopting branch.

### schedule_create's new delegation gate has no test asserting the refusal path
**`server/src/agent.ts:263`** — found by correctness, security, robustness, tests
`schedule_create.execute` now returns the 'Background tasks are disabled …' refusal and skips `createSchedule` whenever `backgroundTasksEnabled()` is false (agent.ts:260-271). This is the server-side enforcement of tier 0 — without it the agent can book a wake-up the escrow will never arm. agent.ts has no test file, and schedules.test.ts exercises the schedule store directly, so nothing asserts that the refusal path fires when the preference is off (or that creation still succeeds when it is on). The guard could be reordered or dropped without any test failing.

**Fix**: Add a test that stubs `backgroundTasksEnabled()` false and asserts execute returns the refusal text and does not create a schedule, plus the enabled-path creation.

### Autonomous unlock uses a constant nonce, making the session token deterministic across boots
**`server/src/index.ts:836`** — found by security
`lock.unlock(cred.secret, "wake0")` passes a fixed literal nonce. In `Lock.unlock` the session token is `hmac(derive(secret,"session",nonce), "waddle-session-token")`, and the SDK documents the nonce as the value that "binds the session credential to this transcript" (sdk/src/index.ts). With a constant nonce every autonomous boot mints the identical bearer for a given secret (the removed `unlockAutonomous` path used `freshNonce()`), so a captured token stays valid for all future autonomous boots until the secret is rotated. Impact is limited today (the token is only used inside the enclave), but it silently discards the nonce-binding property.

**Fix**: Generate a fresh random nonce for the autonomous unlock (e.g. `freshNonce()`) so the session token is unique per boot.
