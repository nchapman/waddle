### User takeover of an autonomous boot keeps the subkey-sealed autonomous log, so the post-takeover conversation is never written to the master-sealed log
**`server/src/index.ts:191`** — found by correctness, robustness
An autonomous boot creates the session log with the subkey key and its own file at index.ts:754 (`log = new EventLog(aut.logKey, lock.storage, "events.autonomous.jsonl")`, where `aut.logKey = derive(subkey, "log")` from state.ts:121-124). When the user later unlocks that same machine (the documented takeover path — `/unlock` runs `lock.unlock(secret, nonce)`, sets the master-derived verifier/log key and flips `autonomous = false`, index.ts:181-190), line 191 is guarded by `if (!log)`, so the master-sealed `new EventLog(lock.logKey, lock.storage)` is never created: the now-full user session keeps appending every event to `events.autonomous.jsonl` under the subkey key. The bb restore cannot fix it either — its freshness gate is `(log?.all ?? []).every((e) => e.type === "sleep")` (index.ts:215) and the autonomous log's first event is the boot marker, so the restore/log-swap at index.ts:218 is skipped. Consequences: (a) every `/state`/restore/next deploy reads `events.jsonl` (index.ts:191, 218) and therefore cannot see the user's post-takeover turns — silent history loss, and `pushMachineBackup` even gates on `events.jsonl` size (bb-backup.ts:244), so the session's state may never be shelved; (b) the takeover turns sit in the file a later autonomous boot reads and posts verbatim (`log.all` at index.ts:496 → `sealPostbox`), so user speech can be re-delivered as unattended mail. The pre-diff code did not have this split (the autonomous boot unlocked with the master and reused `events.jsonl`), so this is introduced by the new file/key separation.

**Fix**: In the takeover branch, recreate the log with the master key when `wasAutonomous`: e.g. after `const wasAutonomous = autonomous;` set `if (wasAutonomous) log = new EventLog(lock.logKey, lock.storage);` (re-appending the autonomous tail if the live user should keep seeing it), so a user session always writes to the master-sealed `events.jsonl`.

### Global bodyLimit raise to 8 MiB buffers unauthenticated request bodies before the auth check
**`concierge/src/index.ts:195`** — found by security
This diff raises the concierge's global `bodyLimit` from Fastify's 1 MiB default to 8 MiB to carry the postbox blob. Fastify parses/buffers the body before any handler runs, and the auth checks live inside the handlers (`verifyExternal`/`authorize` at index.ts:246, 275), so any request that reaches the app — including through the shim paths (e.g. POST /handshake, /timer) by an unauthenticated caller — can force an 8 MiB allocation before being rejected. The concierge container is 2 GB (config/concierge-tinfoil-config.yml:3); a modest number of concurrent 8 MiB bodies can OOM it, taking down all wake/sleep coordination. The concierge's documentation accepts availability loss, so this is nonblocking, but the increase is 8x the prior surface for a limit only the /handoff/post route needs.

**Fix**: Keep the default limit and set the larger `bodyLimit` only on the /handoff/post route (Fastify per-route `bodyLimit`), or cap the sealed blob's byte size client-side to the intended ceiling.

### The 'no re-fire' merge is not ordered ahead of the due-ticker, so a restored schedule can fire before/against the postbox done-markers
**`server/src/index.ts:268`** — found by correctness, security, robustness
The comment above this block claims the postbox is collected 'BEFORE the ticker can fire', but the ticker guard (index.ts:72) is `if (sleeping || refusing || !lock.unlocked || firing) return;` — it does not check `restoring`, unlike the sleep gate (index.ts:546), while `lock.unlocked` is already true from `lock.unlock` at index.ts:181. Between that point and this merge there are up to three network round-trips (two handshakes plus the mail pull, each bounded only by the 10 s AbortSignal.timeout in server/src/concierge.ts) and up to a 60 s shelf pull; prod gets TINFOIL_API_KEY from the container env (config/tinfoil-config.yml:18), so agentReady() is true immediately and the 10 s ticker can legitimately fire an overdue restored row inside that window. fireSchedule calls markRun (index.ts:60) and then this merge writes the older postbox row over the just-marked local row, reverting lastRun/enabled → the row is due again → the work runs a second time.

**Fix**: Add `restoring` to the ticker guard (index.ts:72) so no schedule can fire until the unlock's merge has completed, or apply the merge before the restored schedule table becomes readable by the ticker.

### Postbox blob is bounded only by event count, so above the 8 MiB body limit the run's mail is still rejected
**`server/src/index.ts:499`** — found by robustness
The cap added at index.ts:491-498 limits the number of events (200), not bytes: `events = log.all` keeps every event's full payload, and the body sent to the concierge is base64(AEAD(JSON)) ≈ 1.37×. The concierge's bodyLimit is now 8 MiB (concierge/src/index.ts:198), so a single large event (a tool result from reading a big file/page, a long assistant turn) still produces a 413; `post()` returns null, postPostbox() returns false, and the only trace is the warn at index.ts:502 — the run's output is lost and, because the done-markers never merge, the schedule re-fires, which is precisely the case the postbox exists to prevent.

**Fix**: Bound the payload by serialized size (truncate the tail to a byte budget and say so in the truncation marker) or chunk the post; keep the count cap as a secondary bound.

### Autonomous boot no longer sets an inference key, so a dev wake-boot silently can never run its seeded schedule

### mergeSchedules union still resurrects schedules the unattended run cancelled, and the new merge test asserts that behaviour as intended
**`server/src/postbox.test.ts:55`** — found by tests
mergeSchedules (server/src/postbox.ts:47) now builds an id-union: local rows not mentioned by the payload survive. The test at server/src/postbox.test.ts:55 asserts exactly that (`assert.equal(merged.find((s) => s.id === "j2")?.enabled, true, "unmentioned rows survive")`), and no test covers the inverse. The payload is 'the full schedule table as the run left it' (server/src/postbox.ts:20 / schedules.ts readAll()), and the agent's schedule_cancel tool (server/src/agent.ts:275, in the tools list at :293) is not blocked in restricted mode (index.ts:644 only refuses user_message/browser_input/browser_release). So when the unattended run deletes a row, that row is absent from the payload, the restored shelf copy still contains it, and the union keeps it — the cancellation does not propagate and the schedule fires again at its next due. The docstring at server/src/postbox.ts:43-46 claims the union fixes 'resurrected unattended cancellations'; it does not (it only fixes dropped chained creations), and the test enshrines the surviving-local-row case as the contract, so the code and its stated guarantee can diverge undetected.

**Fix**: Either carry a tombstone list (the ids the run deleted) in PostboxPayload and have mergeSchedules remove those ids, or make the payload's schedule table authoritative for deletions; add a test case asserting a row cancelled in the unattended run is gone after the merge.

### mergeSchedules cannot express deletion: a schedule cancelled during the unattended run is resurrected at the next unlock
