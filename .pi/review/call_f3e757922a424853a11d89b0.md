## 🟠 Important

### User machines enter the hard-stop sweep but nothing refreshes their table entry, so an actively-used machine is stopped after HARD_STOP_MS
**`concierge/src/index.ts:212`** — found by correctness
`allowedInstance` now returns true for user-machine names (`USER_NAME_RE.test(instance) && users.known().has(instance)`), and the backstop sweep (index.ts ~line 620-640, `if (!allowedInstance(name)) continue; const e = table.entry(name); ... if (quietMs < HARD_STOP_MS) continue; await platform.rest(name)`) therefore now stops user machines. But the only writer of a user machine's table entry is `/boot`'s `table.userWake(name)` (line 381, sets `lastContact` once). The machine's own agent cannot refresh it: it is created with the committed config and no `--variable` overrides (`createInstance`, line ~331, explicitly passes none), so its `WADDLE_INSTANCE` is `waddle` and every handshake/`/timer` row the agent writes is keyed under the shared identity `waddle` — the file itself documents this in the `/assign` comment ('machines self-report the config's shared identity and cannot know their own'). Consequently a machine the user is actively running (browser/ws session, unattended background work) is 'quiet' from the concierge's point of view and is hard-stopped 24h after the last `/boot`, killing the in-memory unlocked session and any running work. The trigger is ordinary long-lived use; no misconfiguration is required. Standbys had the same identity blind spot, but this diff is what makes user machines sweep-eligible and long-lived (they have no self-sleep gate of their own).

**Fix**: Attribute the machine's own contact to its name: pass the machine name as an env/`--variable` (or have the agent report its real instance name in handshake/timer requests) so `authorize()` refreshes the entry under the machine name, or exempt user machines from the quiet-based sweep and bound them by an explicit /boot-driven TTL row instead.

### New /boot hands every signed-in user a machine that carries the concierge's shared control bearer
**`concierge/src/index.ts:348`** — found by security, robustness, tests
The new /boot endpoint is the only public path that mints/claims a user machine, and it returns that machine's URL to any holder of a waddle-audience JWT (requireJwtUser). Machines are created by the shared createInstance(), which injects every name in STANDBY_SECRETS via `--secret` (line 339). STANDBY_SECRETS defaults to `CONCIERGE_SHARED_SECRET,TINFOIL_API_KEY` (line 84), and the concierge treats CONCIERGE_SHARED_SECRET as its own service-wide bearer: SHARED_SECRET = process.env.CONCIERGE_TOKEN (line 52) and requireSecret compares against it (line 277); /handshake accepts exactly that bearer (line 409) to mint a session for ANY allowed instance. The machine the user now owns can read its own env (the agent runs a bash tool, and the user answers its approval gate), so a signed-in user can lift CONCIERGE_SHARED_SECRET from their machine and present it as the machine tier: mint session tokens (/handshake) and then arm stop/wake rows via /timer for any ALLOWED instance (including the shared primary `waddle`), and reach the SECRET-only escrow verbs /handoff and /handoff/pull to read or overwrite another session's parked credential (the master unlock secret). Previously this class required a user to call /assign for a warm standby; /boot now hands the same bearer-bearing machine to every authenticated user by default and for their own per-sub machine, so the exposed principal set grows from 'standby claimers' to 'every signed-in user'. The bearer is a service-wide credential, so the exposure is cross-tenant.

**Fix**: Do not inject the concierge-wide shared bearer into machines handed to end users. Give a machine only a credential scoped to itself (e.g. mint a per-instance bootstrap token at claim time, as /handshake already does for sessions) and have /handshake+escrow verify that scoped token rather than the concierge-wide CONCIERGE_SHARED_SECRET; keep TINFOIL_API_KEY out of STANDBY_SECRETS unless a machine truly needs it. If the shared bearer must remain, bind machine authority to the verified /boot subject so one user cannot act on another user's machine (or the primary) with it.

### Fresh /boot creates the machine and then immediately re-deploys it through platform.ensure
**`concierge/src/index.ts:383`** — found by robustness
In the fresh path the handler runs `await createInstance(name)` (line 372), which per the pool design and the live evidence in .pi/evidence/wake/wake-proofs.md:181-184 (`tinfoil container create ... --tag` → '77s to live') already boots the instance. It then unconditionally calls `platform.ensure(name)` (line 383). platform.ensure (platform.ts:172-195) reads `container list`: the just-created name is at best 'Deploying' and is usually absent from the 10s listRows cache (the scanUsers/sweep intervals prime it), so `row?.status === 'Running'` is false and it takes the `return start(instance)` branch — a SECOND `tinfoil container deploy --tag` against a machine that is currently deploying. On tinfoil this can 409 ('cannot deploy a running instance' is the documented deploy precondition), which send the deploy into the zombie stop/wait/re-deploy loop (platform.ts:100-115, up to 60s) or throw 'zombie instance would not accept a deploy after stop', which propagates to the 502 branch at line 390-392. Either way the client sees `ok:false`, falls back to the legacy /wake path (App.tsx wakeCore), and never learns the URL of the machine that createInstance actually booted — the fresh user machine is left running and unattended until the 24h backstop sweep reaps it, while the session is served by the primary. The `ensure` comment ('Later boots return the existing machine, ensured') describes only the rebind/claim paths, not this fresh path.

**Fix**: Do not call platform.ensure on a name this request just created (create already boots it) — skip ensure when `fresh` and return status 'waking' directly, or gate ensure on the row missing from the platform list rather than on status !== 'Running'.

### assignStandby's new label-boundary guard is untested, unlike bootInstance's twin
**`client/src/lib/concierge.ts:67`** — found by tests
This diff rewrites assignStandby's host check to `host === z || host.endsWith('.'+z)` with leading-dot normalization (concierge.ts:57,67). The added bootInstance test suite covers the equivalent guard (`evil<tinfoil.dev>` refused, concierge.test.ts), but the assignStandby tests only cover a wholly different domain (`https://evil.example.net` rejected) and a positive in-zone case. Neither the label boundary (`evilddg-waddle.containers.tinfoil.dev` vs zone `ddg-waddle.containers.tinfoil.dev`), the exact `host === z` match, nor the leading-dot normalization added here is exercised — so the standby handout, which the TOFU pin depends on, has no regression test for the boundary that was just changed.

**Fix**: Add an assignStandby case mirroring the bootInstance boundary test: respond with a URL whose hostname shares the zone as a suffix without a label boundary (e.g. `evilddg-waddle.containers.tinfoil.dev` for zone `ddg-waddle.containers.tinfoil.dev`) and assert null; optionally assert an un-dotted zone string is normalized and accepted.

### jose { payload } unwrap is only half-tested — every JWT-leg test injects bare claims
**`concierge/src/auth.ts:49`** — found by tests
The default JWT leg was changed to `const { payload } = await jwtVerify(...); return payload;` (auth.ts:49) so both the real jose leg and the injected test legs hand bare claims to the outer `payload.sub` check (auth.ts:61). But auth.test.ts never runs the default leg: every test that takes the JWT path injects `verifyJwt` returning a bare object (`{ sub: "user-1" }`, `{ sub: 12345 }`, or throwing), and the jwksUrl tests also pass an injected verifyJwt. This was exactly the shape of the previous critical defect (reading `sub` off the jose `{ payload, protectedHeader }` wrapper). A regression that reintroduced the wrapper mismatch would make every real betterbase JWT fail in production while the whole suite stays green.

**Fix**: Add a test that drives the default leg's contract — e.g. inject a verifyJwt that resolves `{ payload: { sub: "user-1" }, protectedHeader: {} }` and assert createVerifyExternal returns `{ kind: "jwt", sub: "user-1" }`, or otherwise pin the unwrap boundary so the wrapper-vs-bare-claims contract is protected.

### /boot's claim-grace stop row is immediately cleared by table.userWake, so an abandoned warm-claimed standby is never reaped on the claim-grace clock
**`concierge/src/index.ts:358`** — found by correctness
In the warm-claim path `/boot` does `users.claim(sub, got.name); table.setStop(got.name, CLAIM_GRACE_MS); ...; name = got.name;`, and then, a few lines later, unconditionally `table.userWake(name)` with `name === got.name` (line 381). `userWake` (table.ts:108-112) does `e.stopRow = undefined`, so the grace row just written is discarded and the claimed machine ends up with no stop row at all. That directly contradicts the route's own comment ('Same claim-grace contract as /assign: a claimed machine the user abandons dies within grace') and differs from `/assign`, which keeps its `CLAIM_GRACE_MS` row (index.ts:318). Since `pool.assign()` removes the machine from the pool, the grace clock is the only concierge-side bound; the abandoned machine is now only reaped by the 24h backstop sweep (and, per the finding above, that sweep is the same knob). Effect: a claimed-then-abandoned machine burns resources for up to 24h instead of the configured 12h grace, and the code's stated claim-grace invariant is false.

**Fix**: Do not clear the claim-grace row for a machine that was just claimed: either drop the unused `table.setStop(got.name, CLAIM_GRACE_MS)` if 'user present ⇒ no reap row' is intended (and fix the comment), or call `userWake` before `setStop` so the grace row survives for the claimed name.
