## 🟠 Important

### Concierge shared secret (with a "waddle-dev" default) is baked into the shipped browser bundle
**`client/src/lib/config.ts:9`** — found by security
This new module is documented as "the single source for every VITE_ read" and exports `CONCIERGE_TOKEN = env.VITE_CONCIERGE_TOKEN ?? "waddle-dev"`. Vite statically inlines every `import.meta.env.VITE_*` value into the built JS, so whatever secret is configured (plus the literal default) ships to every browser that loads the app. That token is the bearer the client sends in `Authorization` to the concierge (client/src/lib/concierge.ts:16 and :57) and the concierge treats it as the shared secret on the external auth tier — `secretOk(token, SHARED_SECRET)` — which authorizes /wake, /assign, /handoff (arm/clear), /handoff/pull and /status (concierge/src/index.ts:226, :69-73, :343-365). Anyone who reads the bundle therefore holds a concierge credential: they can wake/redeploy the machine, claim a standby, read the instance/escrow timing snapshot, and — via `/handoff` with `clear: true` — disarm the owner's wake escrow (concierge/src/index.ts:361-365), a durable denial of the user's scheduled work. The AGENTS.md addition in this same diff confirms the exposure and even proposes making it permanent ("its VITE_CONCIERGE_TOKEN predates the vault-only rotation" / "rotating the shared secret into the client env"), and concierge/src/auth.ts:39-49 keeps the shared secret valid even when JWKS is configured, so migrating to the bb-JWT path does not retire it. Callers `wakeInstance`/`assignStandby` fall back to this env token whenever `bb getToken()` returns null.

**Fix**: Do not ship a concierge shared secret to the client: drop `CONCIERGE_TOKEN` (and its default) from the client build, make `wakeInstance`/`assignStandby` fail closed when no betterbase JWT is available, and let the concierge's external tier require the per-user JWT (or a client-scoped, revocable token) rather than the machine secret. If a dev fallback is needed, gate it behind the DEV flag so it can never be inlined into a production bundle, and require an https CONCIERGE_URL.

### External tier (any betterbase JWT) can pull the escrowed master secret and overwrite the escrow
**`concierge/src/index.ts:384`** — found by security
/handoff/pull is guarded only by requireExternal (index.ts:384), and this diff also switches the prod config to enable CONCIERGE_JWKS_URL/AUDIENCE (config/concierge-tinfoil-config.yml), which activates the bb-JWT leg of createVerifyExternal (auth.ts) that was previously dead in production (no JWKS_URL → shared-secret only). The released payload is not a scoped key: the sleep gate arms the escrow as { secret: armSecret, schedules, snapshot } (server/src/index.ts:612), i.e. the master unlock secret, and handoff.release returns the whole bag. So any signed-in user holding a valid bb JWT (audience d096d76d-…, i.e. any user of this app) can POST /handoff/pull with instance "waddle" and, whenever a release window is open (10 min per WAKE_RELEASE_WINDOW_MS: 600000), receive the user's master secret. The code itself treats bb-JWT holders as a wider, less-trusted class — /handshake was deliberately narrowed to secret-only "to shrink exactly that class" — yet /handoff/pull (and /handoff, index.ts:361, which arms/clears the escrow with no fire-gate at all) remain reachable by that class. Nothing legitimate needs it: both the sleep-gate arm (server/src/index.ts:612) and the wake-boot pull (server/src/concierge.ts pullHandoff) authenticate with CONCIERGE_SHARED_SECRET.

**Fix**: Gate /handoff and /handoff/pull on the shared secret only (secretOk(bearer(req), SHARED_SECRET)), mirroring /handshake, so a bb-JWT holder cannot read or overwrite the escrowed master-secret bag; keep requireExternal for the routes clients actually use (/wake, /assign, /status).

### ensure()'s new /health probe cannot reach instance hosts under the concierge's egress allowlist, so every Running machine is treated as a zombie and stopped+redeployed
**`concierge/src/platform.ts:161`** — found by correctness
The new ensure() only returns early when the probe reaches `https://${row.domain}/health`; otherwise it falls through to start(), whose 409 path runs rest() (platform stop) and redeploys. The concierge runs on the `control` network with `egress: allowlist` and only `api.tinfoil.sh` + `accounts.betterbase.dev` are allowed (config/concierge-tinfoil-config.yml:35-38, added in this diff for JWKS). The instance hosts it probes (`<name>.ddg-waddle.containers.tinfoil.dev`) are not in that allowlist, and the code this diff deletes states the constraint outright: 'the control plane is the only egress the concierge needs — probing machine URLs would require allowlisting hostnames that don't exist until the machines do, and the allowlist pins IPs at boot.' With egress blocked, realProbe's fetch throws → probe() returns false for the whole probeMs budget, so ensure() always takes the silent-machine branch. On the wake-row fire path (index.ts:130, `platform.ensure(instance, 75_000)`) and POST /wake (default 10s) a machine that is genuinely Running/healthy now gets `tinfoil container stop` + redeploy — an abrupt platform stop with no checkpoint, ~90s+ outage, and loss of the live in-memory session — instead of the no-op the doc comment ('a machine the platform reports Running needs nothing') promises. The platform.test.ts cases inject a stub probe, so the suite stays green regardless of whether the real probe can ever succeed.

**Fix**: Either add the instance domain base to the concierge egress allowlist (and verify the probe live) before relying on it, or make ensure() fail safe: gate the destructive start() path on positive evidence of a dead machine rather than on a probe the deployment cannot make, e.g. keep the Running short-circuit when the probe is unreachable and only redeploy when the probe answers with a non-OK/attestation failure, or treat an unprobeable-but-Running machine as healthy.

### standbyZone() returns "." (truthy) for a single-label ENCLAVE_URL, so assignStandby's new unbound-zone guard does not fire
**`client/src/App.tsx:71`** — found by robustness
The new helper computes `.${new URL(ENCLAVE_URL).hostname.split(".").slice(1).join(".")}`. For a hostname with no dot (e.g. VITE_ENCLAVE_URL=http://enclave), slice(1) is empty and the result is exactly ".", which is truthy, so App.tsx:189 calls assignStandby(conciergeAuth, ".") instead of skipping the standby path. The guard the previous review asked for (`if (!zone) return null` at concierge.ts:56, commented "never accept a host unbound") only rejects empty strings, so it is bypassed here; assignStandby then accepts any handed-out host whose hostname satisfies `host.endsWith(".")` (the absolute-FQDN spelling of any host, e.g. `https://attacker.`), i.e. exactly the in-zone host-switch the zone-bind exists to prevent. The doc comment claims the helper is "Empty on a malformed ENCLAVE_URL", which this case contradicts.

**Fix**: Return "" when the hostname contains no dot (e.g. `const host = new URL(ENCLAVE_URL).hostname; return host.includes(".") ? `.${host.split(".").slice(1).join(".")}` : "";`), and/or tighten assignStandby to require a zone of the form ".x" with length > 1.

### The "wakeInstance reports a failed concierge call as unreachable" test still cannot exercise the wake timeout it references — the fake fetch throws synchronously
**`client/src/lib/concierge.test.ts:49`** — found by robustness
stubFetch's stub (line 17: `if (r.throwErr) throw r.throwErr;`) throws synchronously from the fetch call, so the `AbortSignal.timeout(150_000)` on /wake (concierge.ts:22) is never observed; the test comment (lines 50-51) still cites "the structural timeout guard (AbortSignal on the /wake fetch)" even though nothing in the suite covers a silent stall that the abort would bound. A real stall regression (timeout removed / wrong value) would still pass this suite. Still valid from the previous review.

**Fix**: Either drop the timeout mention from the test comment, or add a stub whose fetch returns a promise that only settles when the passed signal aborts (asserting AbortError converts to `{ ok: false, detail: /unreachable/ }`), so the timeout path is actually pinned.
