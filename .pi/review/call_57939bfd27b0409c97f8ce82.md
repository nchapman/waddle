## 🔴 Critical

### Postbox calls authenticate with the session token against an external-tier-only endpoint (401), and the 401 handler then kills the concierge session
**`server/src/concierge.ts:134`** — found by correctness, robustness
`postPostbox()` (line 134) and `pullPostbox()` (line 142) send the concierge *session* token as the bearer, and the client comment even says 'Session-tier auth like every table write'. But `/handoff/post` and `/handoff/post/pull` gate on `verifyExternal(token)` (concierge/src/index.ts:431, used at 463 and 481), which accepts only a bb JWT (JWKS-verified) or the shared secret — a handshake token is `randomBytes(32).toString('base64url')` (concierge/src/table.ts:40) and matches neither. Dev concierge is started with `CONCIERGE_TOKEN=devsecret` and no JWKS (justfile:26), so the compare is against 'devsecret' → 401; prod with JWKS → jwtVerify fails → 401. So the mail is never posted or pulled: `post()` returns null on !ok and postPostbox() returns false, i.e. every unattended run degrades to the pre-postbox 'output dies with the machine' path. Worse, `post()` treats *any* 401 as 'session died' and does `sessionToken = null` (server/src/concierge.ts:37-42). `pullPostbox()` is awaited inside every user `/unlock` (server/src/index.ts:264), so on the dev/E2E path (no shim) — and in prod as soon as the shim entries are added — the session is nuked a few hundred ms after handshake: `conciergeActive()` goes false for the rest of the boot, which (a) makes the sleep gate take the stay-alive refusal branch whenever a schedule is due soon and hold a burning machine alive (index.ts:403), (b) makes `if (conciergeActive() && autonomyEnabled())` skip the death flare, every wake row and the escrow re-arm at sleep (index.ts:472), and (c) turns `renewIdleStop()`/`touch()` into no-ops (concierge.ts:69 returns false without an HTTP call), so the stop row armed at unlock fires at idle+30s and the concierge stops the container mid-session.

**Fix**: Make the two sides agree: either gate /handoff/post and /handoff/post/pull with the session-tier `authorize(req)` (matching the client's 'like every table write' comment), or send the external bearer the machine already holds (bb JWT / CONCIERGE_SHARED_SECRET) in postPostbox/pullPostbox. Also stop letting an unrelated endpoint's 401 clear the shared session token (only clear it when the failing call was session-authenticated).

## 🟠 Important

### New postbox endpoints authenticate at the external tier, not the session tier their caller uses
**`concierge/src/index.ts:463`** — found by security
/handoff/post (line 459, guard at 463) and /handoff/post/pull (line 477, guard at 481) both call verifyExternal(), i.e. the fleet-wide CONCIERGE_TOKEN shared secret or any JWKS-verified betterbase JWT (concierge/src/index.ts:244). Their only callers, postPostbox (server/src/concierge.ts:132) and pullPostbox (:140), send the concierge *session* token minted by /handshake (concierge/src/table.ts:40 — randomBytes(32).base64url), which is neither the shared secret nor a JWT. Consequences: (a) any holder of the fleet shared secret (every machine in the deployment) or any verified bb JWT can POST /handoff/post/pull for any allowed instance ('waddle'); postbox.pull() (concierge/src/postbox.ts:49) deletes the row and returns the blob with no decryption required, so it destroys a machine's pending return mail, and /handoff/post can overwrite it — a cross-machine DoS on delivery, reached at a weaker tier than the session-only table writes (/timer uses authorize(), line 275). (b) The legitimate calls 401, and the concierge client's 401 handler clears the session (server/src/concierge.ts:52 sets sessionToken = null), so pullPostbox at unlock (server/src/index.ts:264) tears down the machine's own concierge session right after handshake; conciergeActive() then stays false, skipping the sleep gate's wake-row/death-flare block (server/src/index.ts:481) so schedules silently stop re-arming. The caller's own comment ('Session-tier auth like every table write') shows the intended tier.

**Fix**: Gate /handoff/post and /handoff/post/pull with the session-tier authorize() helper (as /timer does), matching both the caller's bearer and the stated model; if external-tier auth is genuinely intended, have postPostbox/pullPostbox send the external bearer instead, and stop the 401 path from nulling the machine's concierge session.

### Autonomous boot uses a different log key against the same shared event-log file, breaking the log's single-key invariant
**`server/src/index.ts:743`** — found by correctness, security
`unlockAutonomous()` returns `logKey = derive(autonomyKey, 'log')` (server/src/state.ts:121) while the user path's log key is `derive(derive(master,'verifier'),'log')` — yet both write `DATA_DIR/log/events.jsonl` (server/src/log.ts:12, and only `wake-credential.json` is excluded from the shelf, archive.ts:22-26). Two concrete failures: (1) Boot/volume reuse — `readWakeCredential()` picks up the dev file first (index.ts:735) and a volume that still holds a previous master-sealed log (dev compose mounts `waddle-data:/data`; the concierge's docker backend `docker start`s the same container) makes the `new EventLog(...)` constructor throw on the first `open()` tag mismatch, the throw is caught at index.ts:760-762, `clearWakeCredential()` deletes the credential and the machine boots locked — wake autonomy is silently disabled in the E2E loop and the credential is destroyed. (2) Takeover — the user unlock keeps the autonomous EventLog (`if (!log) log = new EventLog(...)` at index.ts:191, and `log` is non-null from line 743), so the takeover session appends subkey-sealed lines to the shared file and that tree is shelved; on the next boot `new EventLog(lock.logKey, …)` after `restoreArchive` (index.ts:218) throws on those lines, is caught as 'machine restore failed — booting fresh', and the enclave's event log/history is unreadable on every subsequent boot while the contaminated file keeps being re-pushed (the client-side mirror masks the visible history, but the shelf restore is permanently broken).

**Fix**: Give the autonomous session its own log file (e.g. `log/autonomy-events.jsonl` keyed off the same DATA_DIR) or derive the autonomous log key from the same root the master path uses, so `events.jsonl` never holds lines two keys can't both open.

### New security-critical Lock.unlockAutonomous has no test coverage
**`server/src/state.ts:112`** — found by tests
unlockAutonomous is the sole entry point of the autonomous boot path (server/src/index.ts:742) and its docstring carries load-bearing safety claims: 'Deliberately TOFU — no verifier file is read or written ... the subkey must never touch the master's enrollment', plus a 32-byte guard that throws statusCode 400. ### arm()'s new empty-payload guard is untested; route validates more weakly (500, not 400)
**`concierge/src/handoff.ts:57`** — found by tests
arm() now throws 'credential payload required' for a falsy, non-object, or empty bag, but the /handoff route only checks `!credential || typeof credential !== "object"` (concierge/src/index.ts:428). An empty object {} passes the route check and then throws inside arm() → uncaught in the async handler → 500 instead of the route's own 400. concierge/src/handoff.test.ts was updated for the opaque-bag shape (CRED/cred) but adds no case for the new guard, and there is no route-level test harness anywhere (no app.inject/supertest in the repo), so the store's and the route's validation can disagree without any test failing.

**Fix**: Add cases to handoff.test.ts asserting arm() rejects {} / '' / null, and align the route's check with the store (reject an empty object with 400 before calling arm, or map the store's error to 400) so the failure path a test exercises matches the response code the route actually returns.

### /handoff accepts an empty credential object and then throws inside handoff.arm, returning 500 instead of 400
**`concierge/src/index.ts:428`** — found by robustness
The route validates only `!credential || typeof credential !== "object"` (line 428), but `handoff.arm()` now rejects empty payloads (`Object.keys(cred).length === 0` → `throw new Error("credential payload required")`, concierge/src/handoff.ts:57). A body of `{"instance":"waddle","credential":{}}` passes the route check and throws uncaught out of the async handler, so the caller sees a 500 rather than the intended 400 — an unhandled-throw edge case on the new empty-input guard.

**Fix**: Validate emptiness at the route (`!credential || typeof credential !== "object" || Object.keys(credential).length === 0` → 400) or wrap the arm call and map its validation error to 400.

### The 'no re-fire' merge is not ordered ahead of the due-ticker, so a restored schedule can fire before/against the postbox done-markers
**`server/src/index.ts:268`** — found by correctness
The comment above this block claims the postbox is collected 'BEFORE the ticker can fire', but the ticker's guard is `if (sleeping || refusing || !lock.unlocked || firing) return;` (index.ts:72) — it does *not* check `restoring`, unlike the sleep gate (index.ts:535), and `lock.unlocked` is set at the top of `/unlock` (index.ts:183). Between the shelf restore becoming visible (index.ts:218, up to a 60 s pull) and this merge there are up to three network round-trips (two handshakes + the mail pull, each with a 10 s AbortSignal timeout in concierge.ts:44), and in prod `TINFOIL_API_KEY` comes from the container env (config/tinfoil-config.yml:18), so `agentReady()` is true immediately and the 10 s ticker can legitimately fire an overdue restored schedule in that window. The consequence compounds: `fireSchedule` calls `markRun` (index.ts:60), then this merge replaces that just-marked local row with the older postbox row, reverting `lastRun`/`enabled` and leaving the row due again — a second run.

**Fix**: Add `restoring` to the ticker guard (index.ts:72) so no schedule can fire until the unlock's merge has completed, or merge the postbox payload before the restored schedule table becomes visible.

### Postbox blob is unbounded and will be rejected by fastify's default 1 MiB body limit on any sizeable unattended run
**`server/src/index.ts:488`** — found by correctness
The sealed payload is the session's entire event log (`{ events: log.all, schedules: listSchedules() }`), base64-encoded after AEAD (~1.4x the JSON), and `postPostbox` sends it as a JSON body to the concierge, whose app is `fastify({ logger: true })` (concierge/src/index.ts:214) — Fastify's default `bodyLimit` is 1048576 bytes with no override in this repo. A scheduled run that reads pages/files or streams tool output past roughly 750 KB of JSON gets a 413, `postPostbox` returns false and the only trace is the 'postbox post failed — unattended output degrades to re-fire delivery' warn: the run's output is lost and the schedule re-fires, which is precisely the case the postbox exists to prevent.

**Fix**: Cap the blob by tail-limited events (or chunk the post) and raise/parameterise the concierge's bodyLimit for /handoff/post to match the intended payload ceiling.

### mergeSchedules is not a union: schedules created unattended are dropped, schedules cancelled unattended are resurrected
**`server/src/postbox.ts:47`** — found by correctness, robustness
`return local.map((s) => byId.get(s.id) ?? s)` only walks the local table, so any row present in the postbox payload but not on the shelf is silently discarded — the payload's contract is 'the full schedule table as the run left it' (postbox.ts:27) and the agent's `schedule_create` tool is available during an unattended run (agent.ts:248, tools list at agent.ts:293; restricted mode only blocks ws chat/browser intents, index.ts:634), so a wake-up booked by the unattended run never reaches the user's table and is lost with the ephemeral volume. The inverse also bites: `schedule_cancel` (agent.ts:275) removes a row from the run's table, so it is absent from the postbox, `byId` has no entry and the stale shelf row survives and fires again at its next due.

**Fix**: Build the merged table as a union keyed by id (postbox wins on conflict, local-only rows kept) and carry an explicit list of ids the run deleted so cancellations propagate.
