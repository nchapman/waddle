## 🔴 Critical

### Master root secret written in cleartext to DATA_DIR by the sleep-gate file arm
**`server/src/index.ts:622`** — found by security
The new rearmEscrow() block calls armWakeCredential({ secret: armSecret, schedules, snapshot, inferenceKey: armInferenceKey ?? undefined }) (index.ts:622). armSecret is the raw 64-byte master unlock secret (set at index.ts:346 `armSecret = secret` and inherited at the autonomous boot), i.e. the root of every derived key domain (verifier/session/log/snapshot/postbox). armWakeCredential (server/src/wakeboot.ts:52-54) does `writeFileSync(WAKE_FILE, JSON.stringify(cred), { mode: 0o600 })` to `DATA_DIR/wake-credential.json`, so the master secret AND the inference API key land on disk in plaintext. This contradicts the invariant comment above armSecret ("memory-only … never in DATA_DIR"), and the only guard is the runtime check `!process.env.TINFOIL_API_KEY && autonomyEnabled()`: a prod deploy that is missing the platform-injected key (or a dev run with a mounted persistent volume) persists the master at rest. Anyone/anything that can read DATA_DIR — a co-tenant process, a volume snapshot, a backup that ignores the archive filter — recovers the master and can derive the verifier, log, snapshot and postbox keys, i.e. fully unlock and decrypt the machine.

**Fix**: Never serialize the master to the file arm. Scope the on-disk dev credential to a derived subkey that cannot decrypt the machine, or write only the already-sealed snapshot plus schedules and require the secret to come from the concierge escrow; at minimum gate the write on an explicit dev-only flag rather than the absence of TINFOIL_API_KEY.

## 🟠 Important

### The DOMAIN column's dot-heuristic lets a dotted TAG be used as the probe host, so a live Running machine is still stopped+redeployed
**`concierge/src/platform.ts:144`** — found by correctness
listRows() accepts a column as the domain with `cols[2] && cols[2].includes(".") ? cols[2] : undefined` (platform.ts:144), intended to stop a drifted/absent DOMAIN column from smuggling the TAG in as a probe host (comment at 140-141). But `tinfoil container list` columns are NAME STATUS DOMAIN TAG REPO, and an empty/absent DOMAIN collapses under `line.trim().split(/\s+/)`, putting TAG at index 2 — and version tags contain dots (config/concierge-tinfoil-config.yml sets `STANDBY_CONFIG_TAG: v0.0.48`, which also becomes the default CONCIERGE_DEPLOY_TAG). So the tag passes the dot-check and is stored as `row.domain`. ensure() (platform.ts:171) then does `const domain = row.domain ?? (domainBase ? `${instance}.${domainBase}` : undefined)` — the truthy bogus value shadows the good `instance.domainBase` fallback — and probes `https://v0.0.48/health`, a host that never answers. After the probe budget (10s default, 75s on the wake fire path) ensure falls to start(), whose tinfoil 409 path runs rest() (`tinfoil container stop`) and redeploys: a healthy, possibly user-unlocked machine is stopped. This is the exact outcome the guard, the comment, and platform.test.ts's 'A column-drifted `container list`' case claim to prevent — but those fixtures use TAG `v1` (no dot) and LIST_OUTPUT likewise uses `v1`, so the suite stays green on the real `v0.0.48` tag shape.

**Fix**: Validate the parsed column against the operator zone before trusting it (accept only a value that `endsWith('.' + domainBase)` when domainBase is set, else treat it as absent), or always build the probe host from the validated instance name + domainBase and ignore the raw column; and change the test fixtures' TAG to the production shape (`v0.0.48`) so the drift case is actually exercised.

### ensure()'s new /health probe cannot reach instance hosts under the concierge's egress allowlist, so every Running machine is treated as a zombie and stopped+redeployed
**`concierge/src/platform.ts:176`** — found by robustness
ensure() now verifies `Running` with an outbound `GET https://<domain>/health` and, on failure, falls through to start() (line 181), whose tinfoil path calls rest() (stop) before redeploying. Any probe failure is thus destructive: the concierge's control network is `egress: allowlist`, and the comment this diff deleted stated the reason the old code never probed — 'the allowlist pins IPs at boot' while standby/instance hosts do not exist until the machines do. The added `ddg-waddle.containers.tinfoil.dev` entry is the only mitigation, and it does not cover the case where a Running machine's /health is transiently unreachable for any other reason (DNS blip, a 5xx while the app is still booting, a probe timed out by the 5s per-attempt budget with probeMs=10s on /wake). Previously ensureInstance trusted the platform's Running status and did nothing to a live machine; the diff turns one failed probe into a stop+redeploy of a machine that may be a user's claimed, in-session instance. The 'no derivable domain → trusted' escape only fires when INSTANCE_DOMAIN_BASE is unset; production sets it, so the domain fallback makes every row probe-able and every probe failure destructive.

**Fix**: Do not escalate a probe failure to stop+redeploy on its own: require the platform status to confirm non-Running before calling rest(), or distinguish transport/probe errors (unreachable, timeout) from an authoritative 'not running' signal, and surface the probe failure as a retryable error instead of a destructive action.

### ensure()'s blanket catch swallows a start()/deploy failure and re-runs the deploy
**`concierge/src/platform.ts:181`** — found by robustness
The `try` in ensure() (167-182) encloses not only the status lookup it was written for but also `return start(instance)` on line 181 (the path taken when a Running machine never answers /health within the probe budget). The `catch {}` on line 183 therefore swallows any failure from start() as well, and line 186 immediately issues a second `start(instance)`. start()'s tinfoil path is a stop + 30×2s retry zombie dance (~60s) or a plain `deploy`; a genuine deploy failure (bad tag, `auth failed`, CLI missing, zombie dance exhausted) is thus attempted twice — up to ~120s of duplicate stop/deploy against the same instance, the first error's detail discarded, and for the fire path (index.ts `platform.ensure(instance, 75_000)`) the duplicate stop can run against a machine the first attempt already redeployed. Triggered by any Running-but-unprobeable machine, which is exactly the case the new probe makes reachable.

**Fix**: Scope the catch to the status lookup only, e.g. `const row = await listRows().get(instance).catch(() => undefined)` (or a try/catch that rethrows from the Running branch), so a start() failure propagates instead of being retried.

### Enabling the bb-JWT external tier in production authorizes every holder of an audience token to drive /wake and /assign against the operator's instances, with no subject binding
**`config/concierge-tinfoil-config.yml:25`** — found by security
The three new env lines (CONCIERGE_JWKS_URL/JWKS, ISSUER, AUDIENCE at lines 25-27) are what makes the bb-JWT leg of the external tier live in production: before this change the shipped concierge had no CONCIERGE_JWKS_URL, so createVerifyExternal's JWT branch was dead and the external tier was the fleet secret only. auth.ts:39-50 now verifies signature+iss+aud and returns a bare boolean — no subject/claim is carried out of it. index.ts requireExternal (index.ts:236-240) is wired to the three fleet-wide verbs (/wake, /assign, /status) and the only further check is allowedInstance (index.ts:200-208), a static name allowlist whose whole content in this config is the singleton name "waddle" (CONCIERGE_ALLOWED_INSTANCES). So any account able to obtain a token with audience d096d76d-d066-4ac9-956c-ad3f35c57450 can: POST /wake {instance:"waddle"} -> table.userWake clears the pending stop row (keeping the machine burning) and platform.ensure runs the probe/stop-redeploy path (platform.ts:158-186, whose zombie branch calls rest()+start(), i.e. stop a live machine and redeploy it); GET /assign -> take a warm standby, get its URL, and trigger a replacement boot at the operator's cost, with the claim encoded only as a 12h stop row (index.ts:296-299); GET /status -> schedule timing, standby names and escrow-armed state. Nothing in verifyExternal (auth.ts:53-66) or in the route handlers binds a caller to an instance or to the user whose machine it is, so this is a cross-tenant authorization gap on a single shared instance name, not per-user isolation — PLAN.md:357 records per-boot/per-user instance identity as still-planned work.

**Fix**: Do not put the audience-only JWT tier in front of the fleet verbs as-is. Have createVerifyExternal return the verified subject (and claims) and require it at the boundary: allowlist the subject(s) that own each instance name (or record the claiming subject at /assign and require it in authorize/allowedInstance for that name), and reject /wake and /assign for any subject not bound to the target instance. If the intent is only to let the owner's client through while the k=1 singleton holds, at minimum gate the JWT leg behind an env-pinned subject and keep the shared secret as the machine tier.

### Raw master unlock secret escrowed to the concierge by the sleep-gate re-arm
**`server/src/index.ts:612`** — found by security
rearmEscrow() calls `armHandoff({ secret: armSecret, schedules: schedulableRows(activeSchedules()), snapshot }, bearer, …)` (index.ts:612) with armSecret being the raw master unlock secret. The escrow payload therefore carries the master that derives every key domain, and the sealed snapshot in the same bag is sealed under HKDF(master,"waddle/snapshot"), so the seal gives no confidentiality against the holder. This turns the concierge (and its operators, or anyone who compromises its memory) from a ciphertext-holder into a full-master holder — able to decrypt the whole-machine snapshot and derive the log/postbox/session keys. It directly undercuts the consent dialog's promise that operators cannot read the user's data.

**Fix**: Escrow a snapshot-scoped subkey instead of the raw master (as handoff.ts documents), or explicitly record in PLAN/AGENTS that full-delegation embeds the master so concierge capture == master compromise; do not send the master and the key it seals in the same credential bag.

### authHeaders swallows the session-token failure, sending an unauthenticated /wake that surfaces as a misleading 401
**`client/src/lib/concierge.ts:16`** — found by robustness
`const token = (await auth().catch(() => null)) ?? CONCIERGE_TOKEN;` (line 16) discards any error from the App-supplied auth thunk (`() => bbSessionRef.current?.getToken().catch(() => null)`, App.tsx:110-113 — so the token fetch is swept twice). In live builds `CONCIERGE_TOKEN` is "" (config.ts:14), so a failing/expired betterbase session silently degrades to no `Authorization` header; the request 401s and the user is told "concierge refused (401)" (line 36) with no signal that they need to sign in, while a broken session runner looks the same as "signed out". This is the over-broad-catch pattern: an unrelated auth failure is hidden behind a generic refusal.

**Fix**: Do not swallow the thunk error: let it propagate to a distinguishable detail ("could not obtain your session token — sign in again") or at least log it, instead of folding it into the same refusal string as an unauthenticated request.

### wakeInstance collapses a 150s deploy timeout into "concierge unreachable — is it running?"
**`client/src/lib/concierge.ts:38`** — found by robustness
The bare `catch { return { ok: false, detail: "concierge unreachable — is it running?" } }` (line 37-38) maps every failure — DNS/ECONNREFUSED, a 5xx, and the `AbortSignal.timeout(150_000)` abort at line 32 — to the same message. `/wake` is deliberately synchronous (the module's own comment at line 18-20: the concierge runs the deploy 75–95s before answering), and the concierge's `start()` zombie-recovery path adds the 409 dance, `rest()` (stop) plus up to 30×2s retries before redeploying (concierge/src/platform.ts:100-116), so a legitimate wake can exceed the 150s client bound. When it does, wakeCore shows the user "concierge unreachable — is it running?" and leaves `waking:false` (App.tsx:131-134), inviting a retry against a concierge that is actually still deploying; the true cause (timeout vs. refused vs. 5xx) is discarded.

**Fix**: Distinguish the abort from a transport failure (e.g. catch and check `err.name === "TimeoutError"`/`AbortError`) and return a distinct detail such as "wake timed out after 150s — the concierge may still be deploying", so the retry guidance is correct; keep the HTTP status in the refusal detail as is.
