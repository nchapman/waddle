### Concierge shared secret (with a "waddle-dev" default) is baked into the shipped browser bundle
**`client/src/lib/config.ts:9`** — found by correctness, security, robustness
config.ts:9 exports `CONCIERGE_TOKEN = env.VITE_CONCIERGE_TOKEN ?? "waddle-dev"`. Vite statically inlines every `import.meta.env.VITE_*` value into the built JS, so whichever value is configured is readable by anyone who loads the app (view-source / devtools / any XSS). concierge.ts:19 and :57 use it as the Authorization bearer fallback for the concierge `/wake` and `/assign` calls, and per AGENTS.md this env token is meant to carry the same shared secret the server compares in `secretOk` (index.ts:59). If it is ever set to the real server `CONCIERGE_TOKEN`, the entire external tier opens to any bundle reader: `/wake`, `/assign`, `/handoff` (arm/overwrite the escrow), `/handoff/pull`, `/status`, and `/handshake` — the last mints a session token and therefore table-write rights. This is the same issue raised in the prior review and it is not fixed; moving the constant into a shared module makes the leak the single source rather than eliminating it.

**Fix**: Do not compile a shared secret into the client. Send only the betterbase JWT on /wake and /assign and reject the client when the session is absent (no `?? CONCIERGE_TOKEN` fallback in client/src/lib/concierge.ts); if a dev default is needed, gate it behind `DEV` so production builds cannot contain it.

### External tier (any betterbase JWT) can pull the escrowed master secret and overwrite the escrow
**`concierge/src/auth.ts:45`** — found by security
createVerifyExternal returns `true` for any token that passes `jwtVerify` against the accounts JWKS, checking only signature/issuer/audience (auth.ts:44-46) — no per-user or per-instance binding. The concierge applies this same tier to `/handoff` (index.ts:363) and `/handoff/pull` (index.ts:386) via `requireExternal`. So once `CONCIERGE_JWKS_URL` is configured (the exact next step AGENTS.md/PLAN.md push toward), any account holder on the shared accounts service — not just the waddle operator — can POST `/handoff {instance:"waddle", credential:<arbitrary>}` to replace the escrowed credential, and can POST `/handoff/pull` to retrieve the escrowed master secret whenever a release window is open. The code comment at index.ts:175-176 claims the fire-gate bounds a pull, but release windows open automatically when a wake row fires (index.ts:128 `handoff.markWakeFired`), and the arm/overwrite path has no gate at all. The `/handshake` route deliberately shrinks the JWT class to secret-holders (index.ts:218-223), but /handoff and /handoff/pull do not. This is the previously-flagged finding; the extracted auth.ts preserves the dual-path tier rather than fixing it.

**Fix**: Do not accept the general bb-JWT tier on the escrow routes. Require the machine shared secret or a per-user/per-instance authorization (session tier or an explicit owner binding on the instance) before arming, overwriting, or releasing handoff credentials.

### External tier (any betterbase JWT) can pull the escrowed master secret and overwrite the escrow
**`concierge/src/index.ts:363`** — found by correctness, security, robustness
/handoff (index.ts:363) and /handoff/pull (index.ts:386) remain protected only by `requireExternal` — a shared secret or any valid betterbase JWT for the configured audience, with no binding between the JWT subject and the `instance` in the body (allowedInstance only checks the global ALLOWED set / pool namespace). The escrowed credential is now the MASTER unlock secret rather than a schedule-scoped key: sdk/src/index.ts drops `autonomyKey` for `BbGrant`/handoff types and the new/updated docs describe the bag as `{ secret, schedules[], snapshot? }` (wakeboot.ts:27-28 "The master unlock secret — full delegation"; server/src/concierge.ts `PulledCredential.secret`; the /handoff comment in index.ts). release() returns that whole bag, and it is gated only by `markWakeFired` — i.e. whoever POSTs /handoff/pull inside the release window of a fired wake row (WAKE_RELEASE_WINDOW_MS is set to 600000 in config/concierge-tinfoil-config.yml) receives the user's master secret, with no proof the caller is the machine the concierge booted. The same external tier can also arm (`credential`) or `clear: true` the escrow, so a JWT holder can overwrite or delete the user's autonomy credential at will. Net effect: an escalation over the previously noted finding, because the asset at stake is now the master secret (root of the sealed log, snapshot, and postbox key material) rather than a derived schedule key.

**Fix**: Require the secret-only key for /handoff and /handoff/pull (the same `secretOk(bearer(req), SHARED_SECRET)` used by /handshake), or bind the escrow row to the per-user identity from the verified JWT instead of accepting any valid audience.

### ensure()'s new /health probe cannot reach instance hosts under the concierge's egress allowlist, so every Running machine is treated as a zombie and stopped+redeployed
**`concierge/src/platform.ts:161`** — found by correctness, security, robustness
platform.ts:158-173 now requires a successful reachability probe before trusting platform status: `if (row?.status === "Running" && row.domain) { const url = `https://${row.domain}`; ... if (await probe(url, 5_000)) return "already running (healthy)" ... return start(instance); }`, with realProbe doing `fetch(`${url}/health`, {signal: AbortSignal.timeout(...)})` (platform.ts:19-26). The shipped concierge runs on the `control` network with `egress: allowlist` limited to `api.tinfoil.sh` and `accounts.betterbase.dev` (config/concierge-tinfoil-config.yml) — instance hosts live under `*.containers.tinfoil.dev`, which is not allowlisted. The probe therefore always fails/aborts, the budget expires (10s default; 75s on the wake path, index.ts:133), and control falls to `start()`, whose tinfoil path deploys, gets the `cannot deploy a running instance` 409, calls `rest(instance)` (stops the machine) and redeploys. Result: a healthy, possibly user-unlocked machine is stopped and redeployed on every /wake (index.ts:330 uses the 10s default) and on every wake-row fire, exactly the behavior the removed `ensureInstance` comment warned about ("the old path would have run the zombie stop-deploy dance on a healthy machine"). Since /wake is external-tier (any valid betterbase JWT), this is also a repeatable remote stop/redeploy DoS against a live user machine.

**Fix**: Make liveness detectable from inside the concierge's egress policy (probe the platform API for Running/last-seen and treat that as healthy, or probe through the tinfoil verified proxy), or only run the health probe when an explicit zombie signal exists; never stop-and-redeploy on a negative probe that the network policy guarantees.

### standbyZone() returns "." (truthy) for a single-label ENCLAVE_URL, so assignStandby's new unbound-zone guard does not fire
**`client/src/App.tsx:71`** — found by correctness, robustness
`return `.${new URL(ENCLAVE_URL).hostname.split(".").slice(1).join(".")}`` yields "." whenever the hostname has no dot (e.g. VITE_ENCLAVE_URL=http://waddle): split(".") → ["waddle"], slice(1) → [], join(".") → "", so the template returns ".". The caller (App.tsx:191) guards with `const standby = zone ? await assignStandby(conciergeAuth, zone) : null`, which is truthy for ".", and concierge.ts:60's `if (!zone) return null;` ("no zone to bind to — never accept a host unbound") therefore never triggers; the intended "skip the standby path" behavior documented in the comment only happens on the URL-parse throw. The request still goes out, and the zone-bind test at concierge.ts:66 becomes `host.endsWith(".")`, which accepts a trailing-dot hostname that is not in the primary's operator domain.

**Fix**: Return "" unless the hostname actually has a parent label (e.g. `const parts = new URL(ENCLAVE_URL).hostname.split("."); return parts.length > 1 ? `.${parts.slice(1).join(".")}` : ""; `), and/or harden concierge.ts's guard to `if (!zone || zone === ".") return null;`.

### The "wakeInstance reports a failed concierge call as unreachable" test still cannot exercise the wake timeout it references
**`client/src/lib/concierge.test.ts:48`** — found by robustness
Carried over and unchanged. The test comment claims it covers the `AbortSignal.timeout(150_000)` stall guard, but `stubFetch(() => ({ throwErr: new Error("ECONNREFUSED") }))` makes the stub reject immediately (`grep`: the stub is an `async` function that `throw`s, so it returns a rejected promise). Both a silent stall and an instant connection refusal land in the same `catch { return { ok: false, detail: "concierge unreachable…" } }`, so neither the abort path nor the signal is ever observed; a regression that deletes `signal: AbortSignal.timeout(150_000)` would keep this test green.

**Fix**: Add a stub that never settles (or honours the passed signal) and assert that wakeInstance returns within the bound, or capture `init.signal` and assert it is an AbortSignal with the expected timeout.

### A Running machine whose DOMAIN column is missing/renamed skips the health check entirely and falls straight into stop+redeploy
**`concierge/src/platform.ts:170`** — found by robustness
The new guard is `if (row?.status === "Running" && row.domain)` (platform.ts:161). `row.domain` is just `cols[2]` of a whitespace-split `tinfoil container list` line (platform.ts:136-141), so any change to that CLI's column set/order, or a row where the domain is blank and the split collapses columns, yields `domain === undefined` for an otherwise Running machine. The code then exits the if-block and calls start(instance) at platform.ts:170 with no probe and no Running check — for a live machine that is the 409 'cannot deploy a running instance' path, i.e. rest() (stop) + redeploy (platform.ts:96-117). The only coverage of this parse is a hand-written fixture in platform.test.ts, so a format drift would silently convert the health-first path into 'stop a live machine on every wake'.

**Fix**: Treat a missing domain as an explicit error (throw or log and return 'already running' / skip the deploy) rather than falling through to start(); and make the deploy path itself re-read status so it can never stop a machine the platform still reports Running.
