## 🟠 Important

### Standby-failure fallback can never run: autoWokeRef is already true whenever a standby URL is active
**`client/src/App.tsx:248`** — found by correctness, tests
The added branch (App.tsx:246-252) exists so a bad standby cannot strand the session. The only code that sets `activeEnclave` away from `ENCLAVE_URL` is the /assign success path at App.tsx:271-273, and that path already ran `autoWokeRef.current = true` at App.tsx:260, before fetching /assign. `run()`'s entire auto-recovery block is gated on `!autoWokeRef.current` (App.tsx:245), so when `verifyEnclave(activeEnclave, ...)` throws on the assigned standby the catch skips straight to `setState({ phase: "error" })` (App.tsx:284) and lines 248-251 never execute — the exact outcome the comment says must not happen (only a component remount, where the module-level `activeEnclave` survives but the ref resets, can reach it). There is no test protection for any of this: client/package.json's test script is `node --import tsx --test src/lib/*.test.ts` and the only client test is src/lib/bb-grant.test.ts, so the assign/fallback flow has zero coverage.

**Fix**: Handle the standby case before/independently of the autoWokeRef guard (e.g. `if (!DEV && activeEnclave !== ENCLAVE_URL) { autoWokeRef.current = true; void wakeCore(...); return; }` as the first statement of the catch), so a standby that fails attestation always falls back to the primary.

### Every warm standby is created holding the concierge's shared control bearer, and /assign hands those machines to any authenticated caller
**`concierge/src/index.ts:338`** — found by security
STANDBY_SECRETS defaults to `CONCIERGE_SHARED_SECRET,TINFOIL_API_KEY` (line 80) and the pool's boot passes each of them to `tinfoil container create --secret ...` (line 338), so every standby's environment contains the concierge credential. That credential is a concierge-wide bearer, not an instance-scoped one: `verifyExternal` compares it against `process.env.CONCIERGE_TOKEN` (lines 200-213), and server/src/index.ts:239-246 (plus the new locked-boot block at 649-655) relies on the machine's `CONCIERGE_SHARED_SECRET` being accepted by `/handshake`, i.e. the value injected into machines must equal the concierge's own shared secret for this deployment to work. Meanwhile `/assign` authorizes with nothing but `verifyExternal` (line 262) — no ownership binding, no per-user scope — and the machine handed out is blank, so the claimer picks the unlock secret and owns the box; the agent it then drives has a real `bash` tool (server/src/agent.ts:293) whose approval gate the same claimer answers (server/src/approvals.ts `needsApproval` → bash asks the client that requested it). Impact: any holder of a JWT for the concierge's configured issuer/audience can claim a standby, read `CONCIERGE_SHARED_SECRET`/`TINFOIL_API_KEY` from its env, and then present that bearer to `/timer`, `/wake` and `/handshake`, which accept it for every entry of ALLOWED and every name in `poolNames` (lines 217-224, 262, 274, 303) — so one user can arm stop rows against another user's machine (including the primary `waddle`) or against unclaimed standbys, reaping them and forcing fresh boots. The name-shape/membership fix at line 222 correctly closes the arbitrary-name vector, but the standbys' control authority does not depend on it: names are sequential (`${STANDBY_PREFIX}${i}`) and are additionally published unauthenticated via /health (line 253). Note the concierge is deployed with `CONCIERGE_ALLOWED_INSTANCES=waddle` and no JWKS (config/concierge-tinfoil-config.yml), so this bearer path is the live a…

**Fix**: Do not inject the concierge-wide bearer into machines handed to users. Give a standby only a credential that authorizes writing its own stop row (the concierge already mints per-instance session tokens at /handshake — mint a bootstrap token scoped to that instance), and bind machine authority to the caller: record the claiming subject from the verified JWT at /assign and have `authorize`/`allowedInstance` require that subject for standby names, so no user can stop, wake or reap another user's machine. Drop TINFOIL_API_KEY from STANDBY_SECRETS unless standbys genuinely need inference at boot.

### Boot scan adopts standbys by name alone, so a machine a user already claimed is re-assigned and then deleted
**`concierge/src/index.ts:362`** — found by correctness
The restart scan takes every platform container whose name matches STANDBY_NAME_RE and feeds it to pool.adopt (index.ts:359-362). A claimed machine is indistinguishable from an unclaimed leftover by name: pool.assign only deletes the in-memory entry (pool.ts:104-113) and never renames the container, the client's wake path always posts instance "waddle" (App.tsx:196), and nothing durable records the claim. So after any concierge restart (routine deploys) a machine a user is using is re-tracked as booting with a fresh clock: if it still answers /health (unlocked, live) the promote step makes it warm (pool.ts:81-88) and the next /assign hands its URL to a different user, whose unlock must then fail — the machine's verifier file is TOFU-enrolled to the first user's secret and Lock.unlock rejects a wrong secret (state.ts:60-90) — i.e. /assign no longer hands out a blank machine. If it is stopped (idle-slept), the TTL branch calls destroy, which is `restInstance` + `tinfoil container delete` (index.ts:340-343), deleting a machine that is still the user's; pool.ts's own contract says an assigned machine 'leaves the pool — its own gate, stop rows, and the client own it from there'.

**Fix**: Make the claim visible to the boot scan: mark the container durably at assign time (platform variable/label, or move it out of the standby namespace) and skip marked machines in the scan; at minimum never adopt/delete a leftover that reports itself unlocked/enrolled.

### Adoption test bakes in "leftover = unclaimed": a standby a user is already using is adopted and then stopped+deleted after TTL
**`concierge/src/pool.test.ts:132`** — found by tests
The new adoption test (pool.test.ts:132-150, asserting `h2.destroyed === ["s4"]` for "adopted + unclaimed = reaped by TTL") only covers the unclaimed case. index.ts:360-362 treats every platform instance matching `STANDBY_NAME_RE` as a pool leftover, `pool.adopt()` re-stamps it with a fresh clock (pool.ts:116-121), and tick destroys anything past `STANDBY_TTL_MS` (pool.ts:69-77) via `destroy` = `restInstance(name)` + `tinfoil container delete` (index.ts:341-344, TTL default 3_600_000 = index.ts:81). Assignment is only an in-memory delete from the pool map (pool.ts:112) and poolNames is rebuilt from the platform scan after a restart, so a claimed (in-use) standby is indistinguishable from an unclaimed leftover: once the concierge restarts, a standby a user is actively talking to is reaped and its container DELETED at the one-hour mark, killing a live session. The pool never consults the concierge table, even though the backstop sweep guards against exactly this class (index.ts:382 `const e = table.entry(name); if (!e) continue;` — "an unseen instance may belong to a session that predates our reboot"). No test exercises the adopted-but-claimed path, so nothing catches it.

**Fix**: Before reaping an adopted machine, ask the machine whether it is still unclaimed — server /health already returns `{ locked }` and a claimed machine is unlocked — or keep a durable claim record; then add a test that adopts a name which reports locked:false and asserts it survives a tick past TTL.

### Locked-boot stop row also fires on warm standbys, so the pool's TTL is overridden and /assign hands out machines with a live self-destruct
**`server/src/index.ts:649`** — found by correctness, tests
The block arms `renewIdleStop()` at boot, i.e. a stop row due at boot + WADDLE_IDLE_MS + 30s (concierge.ts:16-21, default 10.5 min), and the stop verb is `restInstance` (concierge index.ts:196-200, table.ts:64-75). Nothing renews it for a machine nobody has unlocked: the server's own gate bails out on `lastActivity === null` (index.ts:443-447), and renewal only happens at the end of /unlock (index.ts:336) or on ws activity (index.ts:536). Consequence for the pool: a warm standby stops itself ~10.5 min after boot, the pool then reads it as `dead` (pool.ts:70), destroys it (`restInstance` + `container delete`) and boots a replacement in the same tick — a slot cycles roughly every 11 minutes instead of STANDBY_TTL_MS (default 60 min), so the pool's documented budget cap is never reached and the pool pays ~6x the intended boot churn plus a no-warm-standby window during each replacement boot. Consequence for a user: /assign writes nothing to the table (concierge index.ts:259-268), unlike /wake which clears pending stops via `table.userWake(instance)` (concierge index.ts:308), so a machine that has already been warm for ~9 minutes is handed out with its self-destruct still ticking and can be stopped mid-attest/unlock — the exact failure mode the file warns about ('the gate fired mid-unlock').

**Fix**: Clear/re-arm the machine's stop row at claim time (call `table.userWake(name)` in /assign, like /wake does) and keep the pool's warm machines out of the locked-boot backstop — e.g. skip arming for STANDBY-name instances or have the pool set WADDLE_IDLE_MS/backstop per machine so the pool's TTL, not the idle window, owns unclaimed standbys.

## 🟡 Suggestion

### `/assign` body is used unvalidated, and there is no fallback once `activeEnclave` is switched
**`client/src/App.tsx:272`** — found by security
The recovery half of this finding is fixed (the `typeof m.url === "string"` guard at line 271 and the standby-failure fallback to `wakeCore` at lines 245-249), but the validation half is unchanged: the handed-out URL is accepted on a scheme-only regex `/^https:\/\//` and the session then unlocks against it — `doUnlock` sends the user's unlock secret and the scoped betterbase grant to `activeEnclave` via `unlock(result.client, activeEnclave, keyInput, grant)` (lines 439-444). Nothing binds that host to the operator's zone, and the TOFU pin cannot catch a host switch: `verifyEnclave` stores `enclaveHost`/`configRepo` in the pin but only compares `codeFingerprint` (client/src/lib/attestation.ts:92). So whatever can answer `/assign` (CONCIERGE_URL defaults to plaintext `http://localhost:5390` at line 39, so an on-path attacker wherever that is not HTTPS, or a compromised concierge) chooses which origin receives the secret and grant, gated only by that origin presenting the pinned code fingerprint — a fingerprint which, per the change's own rationale, is identical for every machine built from the same config repo. The blast radius is therefore any TEE deployment of that same config that the user is not the operator of.

**Fix**: Constrain the handed-out URL before switching: parse it and require the hostname to be the operator's zone (e.g. `new URL(m.url).hostname.endsWith('.' + DOMAIN_BASE)` or an explicit allowlist of `ENCLAVE_URL` + standby hosts), and refuse to unlock when the attested `enclaveHost` differs from the pinned one (surface it as `blocked` with the repin flow rather than silently continuing).

### The rewritten standby authorization gate and pool wiring have no tests — pool.test.ts injects fakes and never loads index.ts
**`concierge/src/index.ts:217`** — found by tests
`allowedInstance` (index.ts:217-224) now grants instance access to any name in `poolNames` that matches `STANDBY_NAME_RE` (index.ts:94) — the gate the previous review found bypassable — and the name set is fed by `boot` (index.ts:328-329, which burns the name before `exec`), `nextName` (index.ts:347-352) and the boot-time platform scan (index.ts:356-364). None of these are covered: pool.test.ts supplies its own `nextName`/`health`/`boot` (`nextName: () => names[i++] ?? ...`), so the collision logic, the regex construction from `STANDBY_PREFIX`, the `envInt` validation and `/assign` (index.ts:259) are exercised nowhere. index.ts ends in a top-level `await app.listen(...)`, so any import starts a server and no unit test can reach the module; a regression in the allowlist branch would be silent.

**Fix**: Move the pure pieces into a testable module (e.g. `envInt`, the standby-name gate/`STANDBY_NAME_RE` construction, and `nextName` over a name set) and add unit tests: prefix-shaped but unknown names rejected, regex metacharacters in `STANDBY_PREFIX` not exploitable, malformed env values falling back to defaults, and a name burned after a failed boot so `nextName` advances.

### Unauthenticated /health now publishes the pool's standby names, states and boot times
**`concierge/src/index.ts:253`** — found by security
`app.get("/health", ...)` has no auth (lines 248-254) and the new payload adds `pool.tracked()`, i.e. every tracked machine's `name`, `state` and `createdAt`. Names are exactly what authorizes the standby namespace (`POOL_ENABLED && STANDBY_NAME_RE.test(instance) && poolNames.has(instance)`, line 222), so this endpoint publishes the identifiers `/wake` and `/timer` accept for standbys; it is also reachable through the public ingress (config/concierge-tinfoil-config.yml: `shim.paths` lists `/health`), and with names sequential (`${STANDBY_PREFIX}${i}`) this confirms which standbys are warm and when they booted. That turns the first-claim-wins semantics of `/assign`/unlock (`/assign` requires only a valid JWT, line 262) into a targeted action — an early caller can claim or stop a specific known-warm machine (its URL is `https://<name>.<DOMAIN_BASE>`, line 346) before the intended user, and in the worst case obtains that machine's injected credentials before anyone unlocks it. /status (line 316) already leaked allowlisted instance names, so this is an incremental disclosure, not a new class of endpoint.

**Fix**: Return counts only from /health (e.g. `{ size, warm, booting }`) or redact names, and require authorization before exposing `pool.tracked()`; alternatively gate the names behind the same token check used by /assign.

### Standbys that survive a concierge restart are neither adopted nor reaped — they bill forever
**`concierge/src/index.ts:357`** — found by correctness
The adoption added for the earlier review only runs inside `if (POOL_ENABLED)` and only if `listInstances()` resolves. If the pool is turned off later (WARM_POOL_SIZE=0 is the default and a plausible cost response) or the platform list fails at boot (the catch at index.ts:366 explicitly gives up: 'leftovers will be adopted on a later restart' — there is no later scan, only a later process restart), leftover standbys are in neither the pool's map nor `poolNames`. Then: pool.tick never sees them (no TTL reap), the backstop sweep rejects the name because allowedInstance requires `POOL_ENABLED && poolNames.has(instance)` (index.ts:223) so `if (!e) continue`/stop never applies, and their own locked-boot handshake is answered 403 — they cannot even arm their own stop row. They run and bill until a restart with a working scan.

**Fix**: Run the leftover scan regardless of POOL_ENABLED (adopt/reap leftover names even with size 0), and retry the scan periodically instead of only at boot so a transient listInstances failure cannot orphan billing machines indefinitely.
