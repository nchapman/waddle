## 🟠 Important

### wakeInstance fetch has no timeout — a stalled concierge hangs the wake flow forever
**`client/src/lib/concierge.ts:16`** — found by robustness
The new concierge module bounds every network call except the one that matters most: `assignStandby` uses `AbortSignal.timeout(5000)` (line 56) and every `pollUntilHealthy` probe uses `AbortSignal.timeout(4000)` (line 38), but the `/wake` POST (line 16) is issued with no abort signal. `wakeCore` (App.tsx:114-121) `await`s `wakeInstance` before it can reach `pollUntilHealthy` or clear the `waking` flag: `setState({ phase: "asleep", waking: true, note })` is set at the top and `waking: false` is only assigned on the `!woke.ok` path or after the poll exhausts. So if the concierge accepts the TCP connection but never responds (a wedged local dev server, a proxy holding the socket, a stalled container), the promise never settles, the UI stays on the AsleepScreen spinner indefinitely, and the catch inside wakeInstance that would have produced "concierge unreachable" is never reached. The only recovery is a manual page reload, and a stalled request also occupies the user's wake path (there is no cancel).

**Fix**: Pass `signal: AbortSignal.timeout(...)` to the `/wake` fetch (e.g. 10s) so a non-responding concierge falls into the existing `catch` and returns `{ ok: false, detail: "concierge unreachable …" }`, matching the other two calls in this module.

### ensure() short-circuits on container status "Running", making start()'s zombie recovery unreachable for the zombie it describes
**`concierge/src/platform.ts:121`** — found by correctness
The new `ensure` documents "Health-first start: Running needs nothing (no zombie dance on a healthy machine)" (platform.ts:22-24) and returns early whenever `tinfoil container list` reports `Running` (platform.ts:121). But container status is not health: `start`'s own comment defines the zombie as "the agent idle-exited but the instance still reads Running" (platform.ts:71-73) and its recovery (deploy → 409 "cannot deploy a running instance" → `rest` → poll/redeploy, platform.ts:74-84) only executes if a deploy is attempted. `ensure` is the only entry point — no caller invokes `platform.start` directly; the wake-row fire hook (concierge/src/index.ts:125) and POST /wake (concierge/src/index.ts:338) both call `platform.ensure(instance)`. So for the canonical zombie (status Running, agent dead) `ensure` returns `already running: <name>` without deploying, the fire hook treats the wake as delivered, and the scheduled occurrence is silently consumed with no boot; likewise /wake returns 202 on a dead machine. The recovery branch is reachable only via the 10 s status-cache staleness or a thrown status call, not via the condition its comment names.

**Fix**: Do not treat "Running" as health: either probe the instance's /health before short-circuiting, or on "Running" still attempt the deploy and let the existing 409 zombie path (stop → poll → redeploy) decide, so a Running-but-dead instance is actually recovered.

### Dropping the optional chain on bb.token turns a logging line into a session-wide backup disable
**`server/src/index.ts:263`** — found by robustness
The diff changes `tokenLen: bb.token?.length ?? 0` to `tokenLen: bb.token.length` inside the `/unlock` grant block. `bb` is untrusted wire input (`(request.body ?? {}) as UnlockRequest`); `setBbGrant(secret, bb)` (bb-backup.ts:77) never touches `token`, so a grant missing `token` (or any of the other dereferenced fields) now throws a TypeError from the log call itself. That throw is swallowed by the surrounding `catch`, which logs it as 'bb grant rejected' and calls `clearBbGrant()` — discarding the grant that `setBbGrant` had just armed and disabling shelf backups for the whole session, even though the only real failure was a logging read. This is exactly the 'broad catch swallows an unrelated failure' pattern: a data-safety feature is silently turned off because of a logging bug, and the reported reason ('grant rejected') misleads the operator.

**Fix**: Restore a defensive read for the debug log, e.g. `tokenLen: bb.token?.length ?? 0` (or move the `app.log.info` out of the try so a logging failure cannot trip `clearBbGrant()`).

### Zone computation moved outside the try/catch — a malformed ENCLAVE_URL now rejects run() instead of falling back to wake
**`client/src/App.tsx:176`** — found by robustness
Before this change the `.${new URL(ENCLAVE_URL).hostname…}` zone string was computed inside the `try { … } catch { /* concierge unreachable — fall through to the wake path */ }` that wrapped the `/assign` call, so any throw (notably `new URL(ENCLAVE_URL)` on a value without a scheme, e.g. VITE_ENCLAVE_URL="waddle.example.com") was swallowed and control fell through to `wakeCore`. The diff hoists the zone computation to the top level of `run`'s outer `catch (e)` block (line 176), where nothing encloses it in a try. Since `run` is invoked as `void run()` (App.tsx:193), a throw here escapes the catch handler and rejects the fire-and-forget promise — an unhandled rejection with no state transition, leaving the UI stuck on the `verifying` screen rather than the previous fallback-to-wake behaviour. Reachable: with a malformed ENCLAVE_URL, `verifyEnclave`/the `/health` fetch throw first, `unreachable` becomes true at line 173, and then `new URL(ENCLAVE_URL)` throws.

**Fix**: Compute the zone defensively (try/catch around `new URL(ENCLAVE_URL)`, defaulting to no zone filter / skipping standby assignment) or move the zone computation back inside a guarded block so a bad ENCLAVE_URL still reaches `wakeCore`.

### New platform module (~120 moved lines, plus a behavior change) has no test file
**`concierge/src/platform.ts:30`** — found by tests
platform.ts is a brand-new 129-line module introduced by this diff and is now the single seam through which the concierge deploys/stops/lists instances (concierge/src/index.ts imports createPlatform at line 46 and calls start/rest/ensure/statuses/list). Every other extractable module in concierge/src has a dedicated unit test — pool.test.ts, table.test.ts, postbox.test.ts, handoff.test.ts — and pool.ts's own header states the modules exist 'so its semantics are testable without the service or a platform backend'. A repo search confirms no concierge/src/platform.test.ts exists. The untested logic is not trivial: statuses() parses `tinfoil container list` stdout (skips the header row, splits columns, and guards `cols[0] !== "NAME"`), rest() decides idempotent success by substring-matching the CLI error text (`msg.includes("is not running") || msg.includes("already")`), ensure() short-circuits on a 'Running' status and falls through on a statuses() rejection, and start() runs the 30-iteration/2s zombie-recovery loop keyed on `msg.includes("cannot deploy a running instance")`. **Fix**: Add concierge/src/platform.test.ts (inject or stub the exec seam) asserting ensure() does not deploy when statuses() reports 'Running', that rest() swallows already-stopped errors, and pin the intended staleness semantics of list()/statuses().

### Docker start/list shell-outs have no timeout while every other exec in the new seam is bounded
**`concierge/src/platform.ts:35`** — found by robustness
