## 🔴 Critical

### Backstop sweep stops every platform instance/container it has no row for
**`concierge/src/index.ts:296`** — found by correctness, security, robustness
`const quietMs = e ? Date.now() - e.lastContact : Infinity;` treats any instance missing from the memory-only table as silent for Infinity, so `if (quietMs < HARD_STOP_MS) continue;` is always passed and the instance is stopped. `listInstances()` is not scoped to the concierge's own instances: the docker backend returns `docker ps -a --format {{.Names}}` (every container on the host, running or not) and the tinfoil backend returns every instance on the operator account. The table is wiped on every concierge restart by design, so after any (re)start the first sweep (default every 15 min) issues `docker stop` / `tinfoil container stop` for every listed instance that has not handshaked — including unrelated workloads on the host/account, and a live waddle machine in active use: the agent only handshakes at `/unlock`, and after a concierge restart its stored session token no longer matches any table entry, so it can neither re-handshake nor renew its stop row (`post` simply returns null and `conciergeActive()` stays true).

**Fix**: Scope the sweep to the set the concierge manages (e.g. a name prefix/filter or an explicit configured instance list), and only treat an instance as reapable when you have positively identified it as a managed instance that went quiet — not when you have never seen it.

### Wake autonomy writes the master unlock secret and model API key to disk in plaintext
**`server/src/wakeboot.ts:35`** — found by security, tests
armWakeCredential() persists `{secret, inferenceKey, conciergeBearer}` as plaintext JSON at `DATA_DIR/wake-credential.json` (mode 0600), and it is called from the unlock handler at server/src/index.ts:236 whenever WADDLE_WAKE_AUTONOMY=1 — set in compose.dev.yaml:18 and, per the PLAN.md entry in this diff, in prod config too. The 64-byte `secret` is the root of every derived key: state.ts derives `verifierKey = derive(secret,"verifier")` and `logKey = derive(verifierKey,"log")`, and keys.ts documents the invariant this breaks ("Everything user-visible is derived from the 64-byte client secret; nothing derived is ever written plaintext"), as does log.ts ("without the secret there is no history"). A plaintext copy of the secret on the volume therefore decrypts the entire sealed event log and pi transcripts, and hands over `inferenceKey`. DATA_DIR is a persistent, ordinary volume (compose.yaml `waddle-data:/data`; Dockerfile `VOLUME /tmp/waddle-data`), so any volume snapshot, host/backup read, or non-TEE deployment — including the documented `just up-dev` flow — yields the keys. The same file also carries the betterbase bearer, which bb-backup.ts explicitly promises is "Memory-only; never in DATA_DIR, never in the archive"; because archive.ts tars all of DATA_DIR (`tar -C DATA_DIR .`), the plaintext secret now rides every machine-backup generation pushed to betterbase. The module's justification ("prod rides the encrypted shelf") does not hold: the local DATA_DIR copy is plaintext, and the shelf is only a copy of it.

**Fix**: Do not persist the master secret. Derive a separate, scope-limited wake credential (e.g. the concierge-issued renewal token described in PLAN.md, with the inference key fetched per wake instead of stored), seal the file at rest with a chip/host-bound key rather than plaintext JSON, and add wake-credential.json to the archive EXCLUDES in archive.ts.

## 🟠 Important

### Auto-wake treats any load failure as "enclave unreachable" and can stop a healthy instance
**`client/src/App.tsx:233`** — found by robustness
The catch wraps the whole run() body: verifyEnclave does real network work (`SecureClient.ready()` fetches the config repo/attestation, attestation.ts:61-63) plus `/health` + JSON parse. A transient failure — network blip, config-repo error, non-JSON body — while the enclave is alive and healthy still sets autoWokeRef and POSTs /wake, which on the tinfoil backend reaches `startInstance`: its "zombie" recovery (concierge/src/index.ts:88-105) reads "cannot deploy a running instance", calls `restInstance` (a platform stop) and then retries `container deploy` for up to 60 s. So one flaky page load can stop and redeploy a running machine, killing in-flight work and replacing the container, with no user confirmation. The once-per-page-load guard only bounds repeats inside one load.

**Fix**: Fire the auto-wake only on a genuine unreachability signal (e.g. a direct short-timeout fetch of ENCLAVE_URL failing at the network level) and route all other errors to the error screen; additionally have the concierge confirm the instance is actually stopped/idle before treating a deploy error as a zombie.

### Audience validation for betterbase JWTs disabled by default
**`concierge/src/index.ts:37`** — found by security
`AUDIENCE` default changed from `"waddle-concierge"` to `""`, and verifyExternal passes `audience: AUDIENCE || undefined` (line 165), so with the default configuration jose's jwtVerify no longer checks the `aud` claim at all. Any token signed by the configured JWKS issuer for any audience — e.g. a betterbase JWT minted for a different relying party or service — passes verification and can call the new /handshake, /timer (arm or cancel stop/wake rows → docker/tinfoil stop+start) and /wake endpoints on any instance name. Before this diff the audience was always enforced (the old code passed `audience: AUDIENCE` with a non-empty default), so this is a regression in the only authn gate the service has.

**Fix**: Restore a non-empty default audience and fail closed when CONCIERGE_AUDIENCE is unset (reject at startup), rather than silently downgrading to no audience check.

### Instance name is caller-supplied and never bound to the authenticated principal
**`concierge/src/index.ts:186`** — found by security
authorize() returns `entryFor(instance)` for any caller that passes verifyExternal, taking `instance` verbatim from the request body, and /timer then turns a `stop` row into `restInstance(instance)` → `exec("docker", ["stop", instance])` (or `tinfoil container stop`) and `wake` into `exec("docker", ["start", instance])`. There is no check that the JWT subject owns the named instance and no validation of the name, so any holder of a valid token (including one for another audience, per the finding above, or the static dev shared secret) can stop or start any container by name — a cross-scope DoS/lifecycle primitive that also applies to /wake (lines 253-270). The same gap makes /handshake (lines 208-216) return the instance's session token to any externally-authenticated caller, so the advertised "instance-scoped, memory-only" session token provides no isolation: it is issued on request to anyone who already passes verifyExternal.

**Fix**: Bind the target to the authenticated principal before invoking the platform backend: derive/validate the instance against the JWT subject (or an operator-configured allowlist / name-prefix check) and reject anything else with 403.

### Wake rows due further out than ~24.8 days fire immediately (setTimeout 32-bit overflow), losing the booked run
**`concierge/src/index.ts:246`** — found by robustness
`setTimeout(..., due_ms)` with a delay > 2**31-1 ms overflows in Node: the timer is clamped to ~1 ms (TimeoutOverflowWarning) and fires at once. The agent registers one wake row per enabled schedule with `dueMs = Math.max(0, d - Date.now())` (server/src/index.ts:378), and /timer only rejects `due_ms < 0` — no upper bound. A one-shot booked more than ~24.8 days ahead (the repo's own test books `2027-01-01`, schedules.test.ts:61; `schedule_create` accepts any ISO date) or a recurring `every_ms` longer than 24.8 days therefore triggers an immediate spurious wake-boot, while `fireWake` deletes the row (line 168) so the real due time never fires — the machine already died believing a wake row covered the work, so the scheduled work is silently skipped with no durable record. With the non-expiring dev bearer the machine re-registers the same over-long row at every sleep, so wake→boot→idle→sleep repeats (billing churn).

**Fix**: Cap the delay (schedule `min(due_ms, MAX_DELAY)` and re-arm on fire) or reject `due_ms > 2**31-1` in /timer with 400 and let the client's /wake own far-future wakes.

### schedule_create reads params.everyMs but the schema declares every_ms — recurring schedules always fail
**`server/src/agent.ts:259`** — found by correctness, robustness, tests
The tool's schema declares `every_ms` and `at_iso` (`parameters: Type.Object({ ..., every_ms: Type.Optional(Type.Integer(...)), at_iso: ... })`), and that snake_case name is what the model is told to use (tool description, promptSnippet, and SYSTEM_PROMPT all say `every_ms`). pi passes the validated arguments straight through to `execute` (dist/core/tools/tool-definition-wrapper.js: `execute: (toolCallId, params, ...) => definition.execute(toolCallId, params, ...)`; this tool sets no `prepareArguments`, and I found no camelCase conversion anywhere in the package). So execute receives `{ title, prompt, every_ms }`, reads `params.everyMs` (undefined) and `params.at_iso` (undefined), and calls `createSchedule({ everyMs: undefined, at: undefined })`, which throws 'either everyMs (recurring) or at (one-shot) is required' (schedules.ts:88). Only the one-shot `at_iso` path works; recurring schedules — the feature this diff ships — can never be created via the tool. The new test only exercises schedules.ts directly, so it does not catch this wiring mismatch.

**Fix**: Read `params.every_ms` (and type the execute params accordingly), or rename the schema property to `everyMs`; match whichever name the model is instructed to send.

### `firing` latch is never cleared if fireSchedule rejects, permanently disabling the ticker and the sleep gate
**`server/src/index.ts:72`** — found by correctness, robustness
The interval sets `firing = true` and clears it only after the loop completes normally (`for (const s of due) await fireSchedule(s); firing = false;`). `fireSchedule` runs `markRun(s.id)` (which calls `writeFileSync` in schedules.ts) and `log?.append(...)` *before* its own try/catch, so a throw there rejects the async IIFE and `firing = false` is skipped. `firing` then stays true forever, which (a) permanently short-circuits the due-ticker (`if (sleeping || !lock.unlocked || firing) return;`, line 67) and (b) permanently blocks the idle-sleep gate (`if (sleeping || !lock.unlocked || firing) return;`, line 395), so the machine can never sleep — billing runs on. Any filesystem error writing schedules.json triggers this.

**Fix**: Wrap the loop body in try/finally so `firing = false` always runs (and/or move markRun/log-append inside fireSchedule's existing try).

### Sleep-gate refusal has no test protection — the core safety behavior of this change is unverified
**`server/src/index.ts:309`** — found by tests
The whole point of this diff is that the machine must not die into a missed schedule: `sleep()` now refuses to exit when `!conciergeActive()` and an active schedule is due within the horizon (index.ts:309-328), and at exit registers a wake row per active schedule (index.ts:374-379). This logic lives inline in the server entrypoint and is untested — `schedules.test.ts` covers only the pure math in schedules.ts; nothing imports `concierge.js` or drives `sleep()`. A regression (inverted condition, wrong horizon, or a wake row computed from `Date.now()` instead of `nextDueMs`) would only surface in production, where the failure modes are severe and opposite: either booked work is silently missed, or the machine never sleeps and billing runs. The dead-end `await new Promise(() => {})` hold path (line 326) is likewise unreachable in any test.

**Fix**: Extract the due-soon selection and the per-schedule wake-row computation into pure helpers (e.g. `schedulesDueWithin(horizon)` and `wakeRowsFor(active)`) and unit-test both branches — due-soon → refuse, none → proceed — plus the due math fed to `writeTimer`.

### Overdue schedule's wake row is cancelled (due_ms 0), so the machine is never woken for it
**`server/src/index.ts:378`** — found by correctness
`writeTimer({ action: 'wake', dueMs: Math.max(0, d - Date.now()), jobId: s.id })` clamps an already-due/overdue schedule to 0, but the concierge defines `due_ms === 0` as cancel: `/timer` does `if (due_ms > 0) { set row } else { delete row }` and answers `{ok: true, wake: 'cleared'}`, which `writeTimer` reports as success (concierge/src/index.ts:243-254, server/src/concierge.ts:61-64). At the sleep exit this drops the wake row for any enabled schedule whose `nextDueMs` is ≤ now — a past-but-unrun one-shot, or a recurring row whose period elapsed while the ticker could not fire it (the due-ticker returns early when `agentReady()` is false, index.ts:69). The machine then dies without any wake registration and the booked work runs only if something else boots it. The clamp exists to avoid sending the negative `due_ms` the concierge rejects with 400, but 0 is the wrong floor.

**Fix**: Clamp to a small positive value (e.g. `Math.max(1, d - Date.now())`) so an overdue row fires immediately, or make the concierge treat `due_ms === 0` on a wake row as fire-now rather than cancel.

## 🟡 Suggestion

### wakeCore ignores the POST status, so auth/start failures hide behind a 2-minute wait
**`client/src/App.tsx:188`** — found by robustness
`await fetch(...)` is not checked: a 401 (the concierge rejects the token — the client defaults to `waddle-dev`/localhost:5390 while the dev concierge the diff wires up runs on 8091 with `devsecret`, justfile:26 / compose.dev.yaml:13) or a 502 from a failed startInstance is treated as success, so the client polls /health for the full 60×2 s and ends on "gave up waiting — try again" with the real cause invisible. The `bb.session` read is inside wakeCore, which `run` (useCallback, deps []) and `wake` capture from the mount-time render scope, so the "prefer the betterbase session token" branch sees the pre-hydration `bb` — the same stale-closure hazard the bbLoadingRef comment at line 160 documents — and silently falls back to the dev token.

**Fix**: Check `res.ok`, surface `status`/body (or the concierge error) and abandon the poll on 401/403/502; read the session token via a ref so a hydrated betterbase session is actually used.

### Timer-table contract has no tests, and the concierge package has no test script
**`concierge/src/index.ts:221`** — found by tests
This rewrite is entirely the timer-table contract the agent's client depends on (`server/src/concierge.ts` `writeTimer`/`renewIdleStop`/`deathFlare`): stop rows are singleton-per-instance (replace = debounce), wake rows are job-keyed one-shots, `due_ms` is relative, `0` cancels, `/wake` clears the stop row, and `/timer` requires `job_id` for wake rows. None of these rules is tested. `concierge/package.json` declares no `test` script, so root `pnpm -r test` never runs the package, and there are no `*.test.ts` under `concierge/`. The `/stop` endpoint this diff removes also had no test, so the deletion is unaudited as well.

**Fix**: Add a `test` script and table-semantics tests: replace debounces (one stop row survives), `due_ms: 0` clears, wake without `job_id` → 400, `due_ms < 0` → 400, and `/wake` cancels a pending stop.

### armWakeCredential's unguarded disk write can fail the whole unlock
**`server/src/index.ts:236`** — found by robustness
This runs inside /unlock's try after `lock.unlock` already succeeded, and wakeboot.ts:35 does a bare `writeFileSync` (no mkdir, unlike schedules.writeAll) — so ENOENT on a machine with no writable DATA_DIR (Lock.storage "memory", state.ts:36-41, the code's own ephemeral mode) or ENOSPC/EROFS on a full volume lands in the unlock catch and returns 500. The client then reports "unlock: ENOENT ..." and never receives the session token, even though the secret was correct, `unlocked` is true, a session token was minted and the log was initialized — the user is locked out of a machine the enclave thinks is unlocked.

**Fix**: Wrap the arm in try/catch (log and continue) and skip it when `lock.storage !== "disk"`.

### Sleep-gate refusal re-enters every 10 s, appending a sealed-log line on each pass
**`server/src/index.ts:326`** — found by correctness
The refusal branch (`!conciergeActive()` with schedules due inside the horizon) never sets `sleeping`; it only awaits a never-resolving promise. The 10 s idle interval (lines 395-398) therefore calls `sleep()` again on every tick while the machine stays idle (`sleeping` is still false), and each pass re-runs the branch: it appends another `[system] sleep refused: …` message to the sealed log (which shelves) and again broadcasts to sockets, and leaks another hung promise. This repeats for as long as the condition holds (e.g. an hour of horizon ⇒ ~360 duplicate log rows; a day ⇒ ~8600), instead of the intended single 'stay alive' notice.

**Fix**: Guard the refusal with a flag (set once, cleared when the gate proceeds) so the message is logged/broadcast once, or set a dedicated 'refusing' state the ticker checks before calling sleep().

### Shared mutable schedules file and module-scope cleanup make the suite order/clock-dependent
**`server/src/schedules.test.ts:68`** — found by tests
All five tests share one global `DATA_DIR/schedules.json`, and test 2 asserts a whole-table `dueSchedules(NOW).length === 0` (line 33) that depends on the exact set and order of rows earlier tests wrote and on real wall-clock (`createdAt`/`lastRun` are `new Date()`), not just on the schedule under test. The cleanup is a bare `rmSync(DIR, …)` at module scope (line 68) instead of a teardown hook — the repo's other suites clean up inside tests (bb-backup.test.ts:107,134,176; archive.test.ts). Node's test runner executes top-level `test()` bodies only after the module finishes loading, so this statement runs before the tests and leaves the temp dir behind.

**Fix**: Move cleanup into `test.after(() => rmSync(DIR, { recursive: true, force: true }))` (or use a per-test temp dir) and assert due-ness by filtering to the specific schedule id rather than a global `dueSchedules(NOW).length`.

### readAll swallows every IO/parse failure and writeAll is non-atomic — booked work can vanish silently
**`server/src/schedules.ts:38`** — found by robustness
The bare `catch { return [] }` treats EACCES/EIO/ENOSPC/EBUSY and truncated JSON the same as "no file", and writeAll (line 45) is a plain `writeFileSync`, so a crash or ENOSPC mid-write leaves a partial file. On the next call readAll reports `[]` — dueSchedules() says nothing is due, activeSchedules() registers no wake rows — and the next createSchedule overwrites the file with only the new row, discarding every booked schedule and its pending wake debt without any error or log line.

**Fix**: Treat only ENOENT as empty (quarantine/log on parse failure and on non-ENOENT read errors) and write atomically via temp file + rename.
