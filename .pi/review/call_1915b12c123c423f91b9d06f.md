**`client/src/lib/bb-grant.ts:28`** — found by tests

### New /debug/log serves a ring buffer that captures the live session bearer token from /ws query strings
**`server/src/index.ts:182`** — found by security, robustness, tests
The new tee (index.ts:34-44) copies every fastify log record into an in-memory ring (`logRing.push(line.trimEnd())`, :39) which the new GET /debug/log returns verbatim (:182-185). Fastify's default request serialization logs the full URL: server/node_modules/fastify/lib/logger-pino.js:50 emits `url: req.url` and lib/log-controller.js:50 logs `request.log.info({ req: request }, 'incoming request')` at info level for every request. The client always carries the session credential in the WS query string — client/src/lib/ws.ts:21 builds `${enclaveURL}/ws?token=${encodeURIComponent(token)}` using the same token `getToken()` returns from /unlock, which is also the bearer that `requireSession` accepts (server/src/index.ts:299-301). So every unlock/connect writes a line like `"url":"/ws?token=…"` into logRing, and that ring is exactly what /debug/log hands out. The route is session-gated, so this is not a pre-auth leak, but the endpoint's stated purpose (index.ts:32-33; .pi/evidence/shelf/shelf-proofs.md:188-190 "tinfoil exposes no logs/exec — the ring buffer is the observability bridge") is to be copied out of the enclave for debugging, screenshots and bug reports: an operator/user tool or a copied log block then transits a live bearer credential. The token is valid until its session TTL (12h, state.ts SESSION_TTL_MS) or process exit, and it authenticates /state, /session and /ws. Recommendation: redact secrets before they enter the ring — in the tee, scrub the query string (`line.replace(/([?&]token=)[^"&]+/g, '$1<redacted>')`) and any Authorization value, or stop putting the WS credential in the URL (use the Sec-WebSocket-Protocol header / a one-time ticket) so it is never serialized into logs in the first place.

**Fix**: Redact the query string before it reaches the ring (e.g. a `serializers.req` that logs `url.split("?")[0]`, or log only path), and drop the `[dbg] bb grant armed` payload to `debug` level or omit the anchor/space fields.

### Restore slot is written into the persistent DATA_DIR outside the try/finally, so a failed write leaks a partially decoded tarball on the volume and the restore needs the archive twice in the same volume
**`server/src/archive.ts:163`** — found by robustness, tests
The slot moved from `os.tmpdir()` to `DATA_DIR/tmp` (archive.ts:160-163), which is the container's persistent volume (compose.yaml `DATA_DIR: /data`, `waddle-data:/data`) and also Chromium's TMPDIR (server/src/browser.ts:23,156 writes scratch there). `writeFileSync(slotPath, detarBody(body))` sits *outside* the `try/finally` that removes the slot (archive.ts:163-167), so a write that fails mid-way (ENOSPC, signal) leaves a partial file that can be as large as the decompressed machine tar (`maxBuffer: 1 << 30`), and nothing reaps it — previously it lived in /tmp; now it is on the volume and only disappears if a later *successful* restore happens to wipe `DATA_DIR/tmp` (archive.ts:198-200). Second-order: restore now needs the decoded archive twice inside one filesystem — the slot plus `.restore-staging` (archive.ts:188-192) — where previously the slot was on `/tmp`, so a volume with less free space than the decoded archive turns the restore into a throw *before* the swap, and `pullMachineBackup`'s caller swallows it as `"machine restore failed — booting fresh"` (index.ts:147) — the same silent-fresh-boot class the new comment says this change exists to fix.

**Fix**: Move `writeFileSync(slotPath, detarBody(body))` inside the `try` (or wrap it in its own try/catch that unlinks `slotPath` on failure) so a failed/partial slot never survives, and stage the slot under a dedicated subdirectory (e.g. `DATA_DIR/.restore-slot`) that is force-removed on entry and exit.
